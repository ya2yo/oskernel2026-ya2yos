# 使用指南

## 编译和运行的环境？

本项目使用的编译环境是2025年系统能力大赛提供的docker image：

```bash
docker.educg.net/cg/os-contest:20250714
```

对应的仓库为

```bash
https://gitlab.educg.net/wangmingjian/os-contest-2024-image
```

## 如何编译和运行

### 准备你的文件系统镜像

我们建议你在项目根目录下新建文件夹2025_testsuits_img，并按照如下的方式组织文件系统镜像

```bash
2025_testsuits_img/
├── final-2025
│   ├── sdcard-la.img
│   └── sdcard-rv.img
├── onsite-2025
│   ├── sdcard-la.img
│   └── sdcard-rv.img
└── pre-2025
    ├── sdcard-la.img
    └── sdcard-rv.img
```

你可以通过编辑`make_scripts/loongarch64.mk`和`make_scripts/riscv64.mk`中的DISK_IMG来选择使用哪个镜像。

这些镜像是[oscomp/testsuits-for-oskernel](https://github.com/oscomp/testsuits-for-oskernel/)的不同分支编译并解压得到的，如何编译这些东西在这里不做介绍。你也可以在该仓库的Releases中找到现成的版本。

### 选择内核的features

在`os/Cargo.toml`中，定义了如下的features：

```rust
# 级别相关定义在./os/src/logger.rs
error = []          # 启用 error 级别
warn = []           # 启用 warn 级别
info = []           # 启用 info 级别
debug = []          # 启用 debug 级别
trace = []          # 启用 trace 级别
# 定义和架构相关的条件编译
riscv64 = ["riscv", "sbi-rt"]  # 列表中的库，表示如果启用这个feature则加载这些库
loongarch64 = ["loongArch64"]
board = []      # 这个feature被启用时，代表上板而不是qemu。具体上哪个板，取决于loongarch64/riscv64这个feature
cached_block_dev = []   # 这个feature被启用时，对外存的写永远不会真的写，而是被写入一个永远不会写回的cache中
ramdisk = []   # 这个feature被启用时，文件系统镜像会被直接包括到内核数据段中，避免对真实外存的访问。你很可能用不到这个……
```

其中，error/warn/info/debug/trace不需要你关心。它们用于控制`debug!`等宏是否会被打印。你可以简单地理解为，当你`make log`时，`debug!`会被打印，而`make`时则不会。

riscv64/loongarch64这两个feature用于选择架构。在编辑代码时，你可以将它们中的一个设在default之中，以提示rust-analyzer使用这个版本的代码，这会更方便你的编辑。但是在编译时，建议你不要将他们设在default之中，因为Makefile也会试图指定它，如果出现了冲突就不好了。

board 的含义是“上板”。启用此features时，会根据riscv64和loongarch64选择合适的外存驱动、内存布局、串口输出地址等。当它被启用时，cached_block_dev和ramdisk中的一个应当被启用。

cached_block_dev的含义见上板文档中的“如何避免外存被污染？用内存承接向外存的写入！”

ramdisk的含义见“外存驱动的伪实现：ramdisk”

cached_block_dev和ramdisk是互斥的，且都只应当在board被启用时启用

### 选择用户态代码的feature

用户态代码仅含有`riscv64`和`loongarch64`两个features，含义同上。和上面一样，你可以在编辑代码时将它们中的一个设在default之中，以提示rust-analyzer使用这个版本的代码，但是在编译时应当取消这个default。

### 编辑用户态initproc

用户态初始进程的代码位于`user/src/bin/initproc.rs`，与其平级的其他模块都是一些临时性的组件，你可以选择删除或者编辑它们，换成你自己认为合适的initproc代码。

### make

我们的Makefile有一个需要指定的参数：`TARGET_ARCH`。它可以被指定为`riscv64`或者`loongarch64`。你可以在make时指定它

```bash
make TARGET_ARCH=riscv64
```

也可以直接在项目根目录的Makefile的顶端指定它

```makefile
TARGET_ARCH ?= riscv64
```

我们的Makefile有三个常见用法：

- make
- make log
- make run

它们在TARGET_ARCH的取不同值时含义如下：

| 指令     | TARGET_ARCH=riscv64      | TARGET_ARCH=loongarch64  | 不设TARGET_ARCH |
| -------- | ------------------------ | ------------------------ | --------------- |
| make     | 编译RV内核               | 编译LA内核               | 编译RV和LA内核  |
| make log | 编译RV内核（含`debug!`） | 编译LA内核（含`debug!`） | （非法）        |
| make run | 运行RV内核               | 运行LA内核               | （非法）        |

编译RV内核会在项目根目录下生成`kernel-rv`文件，它是二进制形式的文件，而不是ELF。

编译RV内核会在项目根目录下生成`kernel-la`文件，它是ELF形式的文件，给qemu用的。还会生成`kernel-la.bin`文件，它是二进制形式的文件，给板子用的。

## 关于dotcargo文件夹

每次编译时，我们会将内核和用户各自的`dotcargo`文件夹复制为`.cargo`文件夹，然后在编译结束时删去它，这并非一个错误，而是因为评测机在git clone代码时会忽略以英文句号为首的文件夹，我们所基于的TrustOS设计了这一方案来规避这个问题。
