## 5.27

### iozone 双架构 glibc 修复

iozone 是 glibc 编译的动态链接 ELF，在龙芯和 RISC-V 架构上均出现问题。

**龙芯架构**：`Error relocating ./iozone: __isoc23_sscanf: symbol not found`。根因是 `map_dynamic_link.rs` 将 glibc 的动态链接器 `/lib64/ld-linux-loongarch-lp64d.so.1` 错误映射到了 musl 的 libc.so。musl 不提供 glibc 2.38 的 C23 符号。修复映射目标为正确的 glibc ld-linux 路径。

**RISC-V 架构**：`panic at translate.rs:118 called Option::unwrap() on a None value`。`sys_statx` 中 `translated_str` 在缺页时直接 panic。改为先建立页映射（`copy_from_user`），再读取字符串。

**修改文件**：

- `os/src/fs/map_dynamic_link.rs` — 修复 LoongArch ld-linux 映射，添加 libc.so.6 路径映射
- `os/src/syscall/fs/stat.rs` — `sys_statx` 中 `translated_str` → `copy_from_user`
- `os/src/task/mod.rs` — `exit_current_and_run_next` 中 `clear_child_tid` 处理提前执行
- `os/src/task/task/task.rs` — `exec()` 中提前处理 `clear_child_tid`

### futex 信号中断竞态修复

之前修复了 `futex_wait_bitset` 中 EINTR 返回前清理 Waiter 的路径，但在 Docker/LoongArch 全量运行时仍然出现 `task already in queue` panic。

通过 Claude Code + DeepSeek-v4 分析 `log.ans`，发现 `add_signal`（`signal/mod.rs:240`）在向阻塞态 futex 任务发送信号时直接将其加入就绪队列，但不清理 `FUTEX_QUEUE_BITMAP` 中的 Waiter。在非抢占内核中，发送信号的线程继续执行 `futex_wake`，找到残留 Waiter 后尝试重复入队导致 panic。

修改三处协同修复：

- `wakeup_futex_task` 增加 `task_status == Ready` 检查，若已被信号唤醒则跳过重复入队
- `new_futex_key` 从 1 起始分配，0 稳定表示"已清理"
- EINTR 清理路径增加 `futex_key != 0` 守卫

详细分析见 `Docs/初赛文档/problem.md`。

### 全量测例堆碎片化 OOM 修复

全量运行 11 组测例时，iozone-glibc 在最后 panic：`Heap allocation error, size: 13770752`。单独运行 iozone 正常。

通过 Claude Code 对比单独运行和整体运行，定位到 `FsIndex` 全局 inode 缓存（`fs/kernel_fs_ops/fsidx.rs`）无淘汰机制：`open()` 时插入，`sys_close` 不清理，仅 `sys_unlinkat` 删除。10 组测例累积数百个 inode 条目的 String 路径 + Arc 占据 48MB 堆，阻止 buddy allocator 合并出 iozone 需要的 16MB 连续块。

修改 `sys_close`：关闭 fd 前获取 inode 路径，`fd_table.take()` 释放引用后检查 `Arc::strong_count <= 2`（仅 FsIndex 持有），安全淘汰缓存条目。`/proc` 路径跳过（由 `remove_proc_dir_and_file` 专门清理）。
