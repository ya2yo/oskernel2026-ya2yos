Ya2yOS 在 StarFive VisionFive 2 实板启动指南
===============================================

版本：2026-08-15
适用源码快照：Ya2yOS 当前工作树，使用 TARGET_ARCH=visionfive2 构建。
读者：使用 Windows 和 MobaXterm 操作一块已能启动官方 Linux/OpenSBI/U-Boot 的 VisionFive 2 的开发者。

本文的目标和边界
------------------

本文提供的是“不改写板载 bootloader、从 RAM 临时启动 Ya2yOS”的流程。成功后，串口应看到
Ya2yOS 的早期启动输出；该结果能够验证 U-Boot/OpenSBI 到内核的交接、FDT、VF2 专用高地址
映射和 UART。重复上电会回到 SD 卡上原有 Linux 系统。

当前仓库已经包含：

* VisionFive 2 链接地址和启动页表：物理加载地址 0x40200000，内核高地址
  0xffffffc040200000；
* JH7110 UART0（0x10000000）控制台；
* JH7110 GMAC1（0x16040000）轮询网络驱动和 YT8531 MDIO 探测。

当前仓库尚未包含 JH7110 SD/MMC 块设备驱动。`fs::init()` 仍会尝试访问 QEMU VirtIO block
地址 0x10001000，因此在真正 VF2 上不能把本流程当作“完整启动用户态和 SD 文件系统”的方案。
第一次实板验证应把成功标准限定为：内核已从 UART 打印早期信息，并且没有在进入内核前死机。
完成 JH7110 SD/MMC 驱动的替换或绕过文件系统初始化后，才能继续验证 initproc、文件系统和
完整网络栈。

不要执行以下操作：

* 不要向 SPI flash、eMMC boot 区或 SD 卡的 bootloader 分区写入任何内容；
* 不要在 U-Boot 输入 `saveenv`；本文中所有 `setenv` 只在本次上电有效；
* 不要覆写原有 `/boot/Image`、`u-boot.itb`、`fw_payload.bin` 或现有 DTB；
* 第一次启动不要拔掉串口，也不要只通过 SSH 操作。内核接管后原有 Linux 网络会停止，SSH
  会断开是预期现象。

一、准备条件
------------

硬件：

1. 一块 VisionFive 2（JH7110），已用官方或发行版 SD 卡正常启动 Linux；
2. 一根可用于板载调试串口的 USB 线，或 USB-to-TTL 适配器。使用外置 TTL 时必须是 3.3 V
   电平，TX/RX 交叉并接地；不得使用 RS-232 电平；
3. 一根接到局域网的以太网线。网络不是早期串口启动的前置条件，但 GMAC 验证需要它；
4. Windows 主机已安装 MobaXterm，并知道 Linux 系统的 IP 地址和登录账户。

软件：

1. 一个可构建本仓库的 Linux 环境。可以是 MobaXterm SSH 连接到的开发服务器、WSL，或其他
   Linux 主机；
2. Rust 工具链和本仓库原有的依赖；
3. 打包 U-Boot legacy image 所需的 `mkimage`。Debian/Ubuntu 开发机安装命令为：

   sudo apt-get update
   sudo apt-get install u-boot-tools

MobaXterm 的职责是串口终端、SSH 终端和 SFTP 文件传输。它不是本方案所需的 TFTP 服务器，
所以不需要在 Windows 防火墙上开放 TFTP 端口。

二、连接并确认原系统
----------------------

1. 将 VF2 接通串口和以太网，接上电源。
2. 在 MobaXterm 创建 Serial session：选择正确的 COM 口，参数设为 115200 baud、8 data bits、
   no parity、1 stop bit、flow control 设为 None。若设备管理器显示的是 `USB-SERIAL CH340`
   或类似名称，选择对应 COM 口。
3. 上电后先完整看一次原有 OpenSBI/U-Boot/Linux 启动日志，并记录 Linux 的 IP。
4. 另建 MobaXterm SSH session 登录该 Linux，执行：

   uname -a
   ip -br addr
   lsblk -f
   sudo -v

这一步既确认板子工作正常，也能在出问题时分辨“原系统问题”和“Ya2yOS 问题”。

三、构建 VF2 内核和 U-Boot image
-------------------------------

以下命令在仓库根目录的 Linux 构建机执行：

   make build-arch TARGET_ARCH=visionfive2
   readelf -h os/target/riscv64gc-unknown-none-elf/release/os
   sha256sum kernel-vf2

第一条命令会生成根目录下的 `kernel-vf2`。该文件是从 ELF 去除调试和 ELF 头后的原始二进制，
不是 Linux `Image`，不能直接作为 `booti` 输入。`readelf` 输出中的 Entry point 应为：

   0xffffffc040200000

将原始二进制包装成 U-Boot legacy image。`-a` 和 `-e` 必须等于实际物理加载和入口地址
0x40200000：

   mkimage -A riscv -O linux -T kernel -C none \
       -a 0x40200000 -e 0x40200000 \
       -n 'Ya2yOS VisionFive 2' \
       -d kernel-vf2 ya2yos-vf2.uImage
   mkimage -l ya2yos-vf2.uImage
   sha256sum ya2yos-vf2.uImage

`mkimage -l` 应显示 Architecture 为 RISC-V、Type 为 Kernel Image、Load Address 和 Entry Point
都为 0x40200000。不要把 ELF 文件 `os/.../release/os` 传给 U-Boot；U-Boot 此处需要的是上一步的
`ya2yos-vf2.uImage`。

四、通过 MobaXterm 传送文件到 VF2
----------------------------------

推荐先把文件上传到 Linux 用户目录，再由板上 Linux 使用 sudo 放入现有 ext4 启动分区。这样
无需猜测 Windows 磁盘符，也不会覆盖原系统文件。

方式 A：构建机和板子网络可直接互通。在构建机执行（将 user 和 vf2-ip 替换为实际值）：

   scp ya2yos-vf2.uImage user@vf2-ip:/tmp/ya2yos-vf2.uImage
   ssh user@vf2-ip 'sha256sum /tmp/ya2yos-vf2.uImage'

方式 B：只使用 MobaXterm 图形 SFTP。

1. 用一个 SSH session 连接构建机，在左侧 SFTP 面板把 `ya2yos-vf2.uImage` 下载到 Windows；
2. 用另一个 SSH session 连接 VF2，在其左侧 SFTP 面板上传到 `/tmp/ya2yos-vf2.uImage`；
3. 在 VF2 SSH 终端验证哈希：

   sha256sum /tmp/ya2yos-vf2.uImage

在 VF2 的 Linux SSH 终端执行以下命令。`/boot` 必须是 U-Boot 能以 ext4 读取的分区；先用
`findmnt /boot` 确认，不应假设 `/boot` 是 FAT 或网络挂载：

   findmnt /boot
   sudo install -d -m 0755 /boot/ya2yos
   sudo install -m 0644 /tmp/ya2yos-vf2.uImage /boot/ya2yos/ya2yos-vf2.uImage
   sync
   sha256sum /boot/ya2yos/ya2yos-vf2.uImage

此处只新建 `/boot/ya2yos/ya2yos-vf2.uImage`，没有替换发行版的正常启动文件。记下最后打印的
SHA-256；它必须与构建机的结果相同。

五、在 U-Boot 发现实际 SD 分区
------------------------------

必须通过串口观察并在 U-Boot 执行本节命令。SSH 在重启时会断开。

1. 在 Linux 中执行：

   sudo reboot

2. 串口出现倒计时（常见为 `Hit any key to stop autoboot`）时按任意键，进入 `StarFive #`、
   `U-Boot #` 或类似提示符。
3. 先保存信息并检查 U-Boot 当前正常启动方案：

   version
   printenv bootcmd boot_targets boot_prefixes boot_scripts fdtcontroladdr fdtfile
   mmc list
   part list mmc 0
   part list mmc 1

VisionFive 2 的不同 U-Boot 和镜像可能将 SD 卡编号为 `mmc 0` 或 `mmc 1`，启动分区也可能是
第 1、2 或 3 分区。因此不能把网上某一条固定的 `mmc 1:2` 命令直接套用到所有 SD 卡。

对每个存在的 `<设备>:<分区>`，以只读方式查找本文件。例如先尝试：

   ext4ls mmc 0:1 /ya2yos
   ext4ls mmc 0:2 /ya2yos
   ext4ls mmc 0:3 /ya2yos
   ext4ls mmc 1:1 /ya2yos
   ext4ls mmc 1:2 /ya2yos
   ext4ls mmc 1:3 /ya2yos

哪一条列出 `ya2yos-vf2.uImage`，就把该设备和分区记为 `<bootpart>`。例如得到
`ext4ls mmc 1:2 /ya2yos` 成功，则本指南下文中的 `<bootpart>` 就是 `1:2`。

若所有 `ext4ls` 均报文件系统类型不支持，请不要格式化 SD 卡。先在 Linux 中用 `lsblk -f` 和
`findmnt /boot` 确认实际文件系统；若启动分区是 FAT，使用等价的 `fatls` / `fatload`，并将文件
放入该 FAT 分区。一般 root ext4 分区则可以继续使用 `ext4load`。

六、一次性从 RAM 启动 Ya2yOS
------------------------------

以下示例假设上一步确定 `<bootpart>` 为 `1:2`。请先把它替换成自己的真实值。所有命令仅修改
内存中的 U-Boot 环境，切勿输入 `saveenv`。

   setenv ya2yos_part 1:2
   setenv ya2yos_addr 0x40200000
   ext4load mmc ${ya2yos_part} ${ya2yos_addr} /ya2yos/ya2yos-vf2.uImage
   iminfo ${ya2yos_addr}
   printenv fdtcontroladdr
   fdt addr ${fdtcontroladdr}
   fdt header
   bootm ${ya2yos_addr} - ${fdtcontroladdr}

解释：

* `ext4load` 把 image 放到 0x40200000，和 `visionfive2.ld` 的物理交接地址一致；
* `iminfo` 在跳转前校验 U-Boot image 头和 CRC。它失败时绝不能继续 `bootm`；
* `fdtcontroladdr` 是当前 U-Boot 使用的 VF2 设备树地址。Ya2yOS 在 `a1` 接收该 FDT，并从其中
  读取 RAM 范围、hart 数和 timebase；
* `bootm ... - ${fdtcontroladdr}` 通过 U-Boot 的 RISC-V Linux 启动路径把 hart ID 放在 `a0`、
  FDT 指针放在 `a1`。中间的 `-` 表示没有 initrd。

若 `fdtcontroladdr` 为空或 `fdt header` 失败，不要用 0 作为 FDT 参数。先从 `printenv bootcmd`
中找发行版正常启动时加载 DTB 的路径、设备和地址，然后采用同一个 DTB。例如：

   setenv ya2yos_fdt_addr 0x46000000
   ext4load mmc ${ya2yos_part} ${ya2yos_fdt_addr} /boot/dtbs/<实际内核版本>/<实际 vf2 dtb 文件>
   fdt addr ${ya2yos_fdt_addr}
   fdt header
   bootm ${ya2yos_addr} - ${ya2yos_fdt_addr}

这里的 DTB 路径必须来自板上的实际 `bootcmd` 或 `find /boot -name '*visionfive*2*.dtb'` 结果，
不要照抄占位路径。

七、串口结果判定与故障定位
--------------------------

启动成功的最早标志是 Ya2yOS 在 MobaXterm 串口中打印类似以下内容：

   [kernel] hardware: ram_start=0x40000000, ram_size=..., harts=..., timebase=... Hz
   [kernel] Hello, world!
   mm::init...complete.
   logger::init...complete.
   trap::init...complete.

GMAC 驱动成功创建时，日志还应包含：

   VisionFive2 GMAC1 initialized with PHY 0

在当前存储支持状态下，`fs::init...` 之后的错误、panic 或卡住很可能是预期的 VirtIO block
访问问题，不足以否定“内核已经成功进入 VF2”。务必完整保存串口日志，并记录最后一行。

常见现象和处理：

1. `Bad Magic Number` 或 `Wrong Image Format`：确认传入 `bootm` 的是 `ya2yos-vf2.uImage`，而非
   `kernel-vf2` 或 ELF；重新执行 `iminfo ${ya2yos_addr}`。
2. `ext4load` 找不到文件：重新执行 `part list mmc 0`、`part list mmc 1` 和 `ext4ls`。不要修改
   mmc 编号或分区前先确认当前 SD 卡布局。
3. `bootm` 后立即无串口输出：检查 `iminfo`、确认地址是 0x40200000、确认传入有效 DTB；再在
   U-Boot 执行 `fdt print /memory`，应看到 base 为 0x40000000 的 RAM 节点。
4. 出现 `bootloader did not provide a usable FDT RAM description`：U-Boot 没有传入有效 FDT，或 DTB
   的 `/memory` 节点无有效 `reg`。按第六节的 fallback 显式加载正常系统正在使用的 DTB。
5. 有早期 Ya2yOS 文本但随后死机：记录最后 100 行；这已经证明加载地址、入口、页表和 UART
   基本路径可工作。按当前仓库状态，优先排查仍指向 0x10001000 的 VirtIO block 初始化，而不是
   重新刷写 bootloader。
6. 没有 `VisionFive2 GMAC1 initialized...`：确认网线已接入、PHY 地址为 0、以及串口日志中是否有
   `VisionFive2 GMAC1 initialization failed`。该驱动尚未在实板验证，需保留完整日志用于比对 CRG、
   syscon、MDIO 和 DMA 初始化阶段。

八、恢复原 Linux
----------------

若 Ya2yOS 停住，短按或断电重启 VF2。在没有执行 `saveenv` 或覆盖发行版 boot 文件的前提下，
U-Boot 会恢复原有 `bootcmd` 并重新启动 SD 卡上的 Linux。若停留在 U-Boot，可直接执行：

   run bootcmd

只有确认不再需要临时 image 时，才在正常 Linux 下删除独立目录：

   sudo rm -f /boot/ya2yos/ya2yos-vf2.uImage
   sync

这不是启动所必需的步骤；保留该文件不会改变默认启动。

九、后续验证顺序
----------------

建议严格按以下顺序推进，避免把多个未验证硬件路径混在一起：

1. UART：确认第七节的早期内核输出和 FDT RAM 信息；
2. 存储：补齐 JH7110 SD/MMC 块设备驱动，替换 `BlockDeviceImpl` 的 VirtIO MMIO 实现，然后验证
   `fs::init()` 和 initproc；
3. GMAC：在存储路径稳定后，观察 PHY 发现日志，给接口设置静态 IPv4，依次验证 ARP、ping、
   UDP 和 TCP；
4. 并发和回归：验证多 hart 启动、定时器、文件系统读写以及现有网络测试。

每一次实板测试请保存：Git commit、`sha256sum ya2yos-vf2.uImage`、U-Boot `version`、`printenv`
中 bootcmd/fdtcontroladdr、串口完整日志和网络拓扑。这样才能把软件回归与板级固件或 SD 卡差异区分开。
