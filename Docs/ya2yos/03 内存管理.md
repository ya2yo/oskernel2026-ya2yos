# 第三章 内存管理

## 3.1 地址空间布局

### 3.1.1 物理内存布局

RISC-V64 架构下，物理内存的起始地址为 `0x8000_0000`，默认配置 256MB 物理内存空间。QEMU 模拟的 MMIO 区域分布在物理地址低位：

| 地址范围 | 设备 |
|---------|------|
| `0x0010_0000` | VIRT_TEST |
| `0x0010_1000` | VIRT_RTC |
| `0x1000_0000` | UART0 |
| `0x1000_1000` | VirtIO Block |
| `0x1000_2000` | VirtIO Net |

内核通过 `KERNEL_ADDR_OFFSET = 0xffffffc000000000` 将物理内存直接映射到内核虚拟地址空间的高段（Direct Mapping），实现物理地址与内核虚拟地址的简单转换：`kva = pa + KERNEL_ADDR_OFFSET`。

### 3.1.2 用户虚拟地址空间布局

每个进程拥有独立的 192GB（`0x30_0000_0000`）用户态虚拟地址空间，布局从低地址到高地址依次为：

```
0x0000_0000_0000 ───────────────────────────────
                  │  ELF 各段（代码/数据/BSS）   │
                  ├──────────────────────────────┤
                  │  动态链接器映射段             │
                  │  (DL_INTERP_OFFSET=0x15_0000_0000) │
                  ├──────────────────────────────┤
                  │  Brk 堆区域                  │
                  │  (最大 256MB virtual)         │
                  ├──────────────────────────────┤
                  │  Mmap 映射区域                │
                  │  (最大 256MB)                │
                  ├──────────────────────────────┤
                  │  Guard Page                  │
                  ├──────────────────────────────┤
                  │  线程用户栈 (8MB×N)            │
                  ├──────────────────────────────┤
                  │  TrapContext 页 (N个，每线程1页)   │
0x30_0000_0000 ───────────────────────────────
```

关键常量定义：
- `PAGE_SIZE = 0x1000`（4KB）
- `USER_STACK_SIZE = 8MB`
- `USER_HEAP_SIZE = 256MB`（虚拟预留，实际物理内存通过 Brk 按需映射）
- `MAX_BRK_SIZE = 128MB`（堆实际增长上限）
- `MAX_MMAP_SIZE = 256MB`（mmap 映射总量上限）
- `KERNEL_STACK_SIZE = 16KB`（每个线程的内核栈，4页）
- `KERNEL_HEAP_SIZE = 48MB`（内核堆）

## 3.2 页表机制

### 3.2.1 SV39 三级页表

RISC-V64 架构采用 SV39 分页方案，虚拟地址的 39 位被划分为三级索引和页内偏移：

```
虚拟地址 (39 bits):
┌──────────┬──────────┬──────────┬────────────┐
│  VPN[2]  │  VPN[1]  │  VPN[0]  │   offset   │
│  9 bits  │  9 bits  │  9 bits  │  12 bits   │
└──────────┴──────────┴──────────┴────────────┘
```

`PageTable` 结构体封装了根页表物理地址，通过 `PageTableEntry`（PTE）的 flags 字段控制每页的访问属性：

```rust
bitflags! {
    pub struct PTEFlags: u8 {
        const V = 1 << 0;     // 有效位
        const R = 1 << 1;     // 可读
        const W = 1 << 2;     // 可写
        const X = 1 << 3;     // 可执行
        const U = 1 << 4;     // 用户态可访问
        const G = 1 << 5;     // 全局映射
        const A = 1 << 6;     // 已访问
        const D = 1 << 7;     // 已修改
    }
}
```

### 3.2.2 内核地址空间

内核拥有一个全局的 `KERNEL_SPACE`（`Lazy<Mutex<MemorySetInner>>`），所有 Hart 共享。内核页表将：
- 所有物理内存通过 Direct Mapping 映射到高段虚拟地址（`KERNEL_ADDR_OFFSET + pa`），采用大页（2MB/1GB）以提升 TLB 覆盖率；
- 内核堆（`KERNEL_HEAP_SIZE`）使用独立映射（因为伙伴分配器需要连续虚拟地址）；
- 内核栈（每个线程 16KB）被映射到内核地址空间的顶部区域（`KSTACK_TOP` 附近）。

用户态陷入内核时，`stvec` 在进入陷阱处理前指向内核态的 `__alltraps`，此时页表处于用户页表和内核页表的混合状态（通常用户页表保留了内核空间的恒等映射）。

## 3.3 内存集合（MemorySet）

`MemorySet` 是管理虚拟地址空间的核心抽象。每个 Process 通过 `Arc<RwLock<MemorySet>>` 共享同一个地址空间。

### 3.3.1 结构定义

```rust
pub struct MemorySet {
    pub inner: SyncUnsafeCell<MemorySetInner>,
}

pub struct MemorySetInner {
    page_table: PageTable,     // 页表
    areas: Vec<MapArea>,       // 所有映射区域的向量
}
```

### 3.3.2 映射区域（MapArea）

每个 `MapArea` 代表地址空间中一段连续的虚拟页面范围（`VPNRange`），记录该范围的映射类型、权限和数据帧：

```rust
pub struct MapArea {
    pub vpn_range: VPNRange,                    // 虚拟页号范围
    pub data_frames: BTreeMap<VirtPageNum, FrameTracker>, // VPN → 物理帧映射
    pub area_type: MapAreaType,                 // 区域类型
    pub map_perm: MapPermission,                // 访问权限
    pub mmap_file: Option<(Arc<OSFile>, usize)>, // mmap文件映射（文件和偏移）
    pub mmap_flags: MmapFlags,                  // mmap标志（SHARED/PRIVATE等）
    pub map_type: MapType,                      // 映射类型（线性/按帧）
}
```

`MapAreaType` 定义了区域的用途：

| 类型 | 用途 |
|------|------|
| `Elf` | ELF 代码和数据段（线性映射，从文件读取） |
| `Heap` | Brk 堆区域（按帧分配，COW 支持） |
| `Stack` | 用户栈（主线程或 mmap 栈） |
| `Mmap` | mmap 映射区域（匿名或文件映射） |
| `Trap` | TrapContext 页面 |

## 3.4 物理内存分配

### 3.4.1 CMA 连续内存分配器

物理内存管理采用 **CMA（Contiguous Memory Allocator）** 架构，底层使用伙伴系统（buddy_system）进行页面粒度的分配与回收：

```rust
// 分配连续物理页面
pub fn cma_alloc(num_pages: usize) -> Option<usize>;
// 释放连续物理页面
pub fn cma_dealloc(ppn: usize, num_pages: usize);
```

CMA 初始化时，首先从设备树或内存布局中找到可用物理内存，将 `PHYSICAL_MEMORY_START` 到 `MEMORY_END` 之间的所有空闲物理页面纳入伙伴系统管理。

### 3.4.2 FrameTracker

`FrameTracker` 是物理帧的 RAII 封装，通过引用计数自动管理物理帧的分配与回收：

```rust
pub struct FrameTracker {
    ppn: PhysPageNum,  // 物理页号
}
```

当 `FrameTracker` 被 Drop 时，自动调用 `cma_dealloc` 归还物理帧。在多处共享同一物理帧（如 COW）时，通过 `FrameTracker` 的 Clone（内部引用计数）来追踪物理帧的引用数量。

### 3.4.3 内核堆

内核堆使用 `buddy_system_allocator` 提供的 `LockedHeap`，在初始化时将 48MB 的虚拟地址区域注册为堆空间，通过 Rust 的 `alloc` crate 提供 `Box`、`Vec`、`Arc`、`BTreeMap` 等动态内存分配。

```rust
#[global_allocator]
static HEAP_ALLOCATOR: LockedHeap<32> = LockedHeap::empty();

pub fn init_heap() {
    // 在内核虚拟地址空间映射堆区域
    // 将连续页面分配器注册到 HEAP_ALLOCATOR
    HEAP_ALLOCATOR.lock().init(heap_start, heap_size);
}
```

## 3.5 按需分页（Demand Paging）

### 3.5.1 延迟加载机制

ELF 加载时不立即分配物理帧，而是创建 `MapArea` 记录映射信息但延迟到首次访问时再分配物理帧。当用户首次访问某页时，MMU 触发 **LoadPageFault** 或 **FetchInstructionPageFault** 异常，内核在 `trap_handler` 中调用 `lazy_page_fault` 完成实际帧分配和内容填充。

### 3.5.2 堆的按需增长

Brk 堆使用类似的延迟分配策略。当用户调用 `brk()` 扩展堆顶时，内核仅更新 `user_heappoint` 指针和对应 `MapArea` 的 `vpn_range`，不立即分配物理帧。首次访问新扩展的堆页时，`lazy_page_fault` 分配并清零物理帧。

堆增长的约束包括：
- `MAX_BRK_SIZE = 128MB`：堆总量上限；
- `PAGE_SIZE` 对齐：brk 按页粒度增长；
- 堆只能向高地址方向增长，不能收缩到 `user_heapbottom` 以下。

## 3.6 写时复制（COW）

### 3.6.1 原理

`fork` 时，子进程共享父进程的全部物理帧，但将所有可写页的页表项改为**只读**并设置 COW 标记。任一进程对 COW 页的写入会触发 **StorePageFault** 缺页异常，此时内核：

1. 分配一个新的物理帧；
2. 将原物理帧的内容复制到新帧；
3. 更新触发异常的进程的页表，将对应 PTE 指向新帧并恢复写权限；
4. 将原物理帧的引用计数减一。如果引用计数降为 1（最后一个引用），直接恢复该进程的写权限，无需复制。

### 3.6.2 实现细节

`cow_page_fault` 的核心逻辑：

1. 根据 VPN 在 `areas` 中找到对应的 `MapArea`；
2. 检查该 VPN 是否在 `area.data_frames` 中（COW 页一定有数据帧）；
3. 检查引用计数：如果 `Arc::strong_count(&frame_tracker)` 大于 1，说明有其他进程/线程还在共享此帧，需要进行深拷贝；如果等于 1，直接修改 PTE 恢复写权限；
4. 对于深拷贝场景：分配新帧 `cma_alloc(1)` → `memcpy` 复制内容 → 替换 `data_frames` 中的帧 → 更新页表。

### 3.6.3 Brk 堆的 COW

fork 后的 Brk 堆也采用 COW。子进程的堆扩展通过 `MapArea::from_another()` 创建原始堆的浅拷贝，只在子进程实际写入堆页时才触发 COW 分配。这避免了 fork+exec 模式中的无效堆复制。

### 3.6.4 MAP_SHARED 的 fork 预处理

对于 `MAP_SHARED` 的 mmap 区域，fork 前必须预先分配所有数据帧，否则父子进程各自独立分配帧会破坏共享语义。具体做法是：在 `MemorySetInner::from_existed_user()` 中，遍历所有匿名 `MAP_SHARED` 区域的每个 VPN，调用 `map_one` 预先分配零填充帧；对文件映射的 `MAP_SHARED`，调用 `mmap_write_page_fault` 预读文件内容到物理帧。

## 3.7 mmap 系统调用

### 3.7.1 匿名映射

`mmap(NULL, len, prot, MAP_PRIVATE | MAP_ANONYMOUS, -1, 0)` 创建匿名映射：

1. 在地址空间中查找一个未使用的虚拟地址范围（`mmap_bad_address` 和已有的 areas 用于冲突检测）；
2. 创建新的 `MapArea`，类型为 `Mmap`，设置对应的 `MapPermission`（PROT_READ/WRITE/EXEC）；
3. `MAP_PRIVATE`：数据帧延迟分配（lazy allocation），首次写入时触发缺页异常分配物理帧；
4. `MAP_SHARED`：数据帧立即分配并零填充。

### 3.7.2 文件映射

`mmap(addr, len, prot, MAP_SHARED | MAP_FILE, fd, off)` 创建文件映射：

1. 通过 fd 获取 `Arc<OSFile>`；
2. 创建 `MapArea` 记录 `mmap_file = Some((file, offset))`；
3. 数据帧延迟分配：首次访问时通过 `mmap_read_page_fault` 从文件读取对应偏移的数据；
4. `MAP_SHARED` 写回：当共享映射的脏页被回收或 `msync` 时，将修改写回到文件。

### 3.7.3 mprotect 与 mremap

- `mprotect(addr, len, prot)`：修改已有映射区域的访问权限。遍历对应 VPN 范围内的所有 `MapArea`，更新 `map_perm` 字段并刷新页表项；
- `mremap(addr, old_len, new_len, flags)`：调整已有映射区域的大小，支持 `MREMAP_MAYMOVE` 移动映射位置和 `MREMAP_FIXED` 固定地址重映射。

### 3.7.4 地址冲突检测

`mmap_bad_address` 机制维护了一个特殊的 mmap 检查区域，防止 mmap 与已加载的 ELF 段、堆、栈等区域冲突。在地址空间中插入 `MapArea` 时，通过 `VPNRange` 检测是否与已有区域重叠。

## 3.8 共享内存（SHM）

Ya2yOS 实现了 System V 共享内存接口：

| 系统调用 | 功能 |
|---------|------|
| `shmget(key, size, flags)` | 创建或获取共享内存段 |
| `shmat(shmid, addr, flags)` | 将共享内存段附加到进程地址空间 |
| `shmctl(shmid, cmd, buf)` | 共享内存段控制（IPC_RMID 等） |

共享内存的物理帧独立于进程生命周期——即使所有附加的进程退出，共享内存段仍然保留，直到显式调用 `IPC_RMID` 删除。

## 3.9 地址转换与用户态数据访问

内核通过 `translate_va` 函数将用户态虚拟地址转换为物理地址，这在系统调用中读写用户态数据时至关重要：

```rust
pub fn translate_va(&self, va: VirtAddr) -> Option<PhysAddr>;
```

提供了一系列安全的数据传输函数：

- `copy_from_user(memory_set, src_va, buf)`：从用户态拷贝数据到内核
- `copy_to_user(memory_set, dst_va, data)`：从内核拷贝数据到用户态
- `get_data(token, ptr)`：读取任意类型的用户态数据
- `put_data(token, ptr, value)`：写入任意类型的数据到用户态
- `translated_refmut(token, ptr)`：获取用户态地址的可变引用（用于高效操作）
- `strong_translated_refmut(token, ptr)`：获取用户态地址的独占引用

这些函数在处理过程中会自动检查地址合法性，防止内核因用户态传入的非法地址而崩溃。

## 3.10 缺页异常处理

`page_fault_handler` 处理所有类型的缺页异常：

1. **Lazy Page Fault**（延迟分配）：首次访问未分配帧的合法虚拟地址时，分配并初始化物理帧。适用于 ELF 段的延迟加载和堆的按需增长；
2. **COW Page Fault**（写时复制）：在只读的 COW 页上执行写操作时触发，执行物理帧的深度复制；
3. **Mmap File Fault**（文件映射缺页）：首次访问文件映射区域时，从文件读取数据到新分配的物理帧；
4. **Page Modify Fault**（页修改异常）：LoongArch64 架构特有，处理 TLB 中的 Dirty 位与实际页表不一致的情况；
5. **真正的缺页错误**：如果访问的虚拟地址不属于任何 `MapArea`，发送 `SIGSEGV` 信号给进程。

## 3.11 TLB 管理

TLB（Translation Lookaside Buffer）是地址转换的高速缓存。在页面映射发生变更后（mmap/unmap/mprotect/COW 等），必须通过 `sfence.vma` 指令（RISC-V64）或 `tlb_invalidate` 函数刷新对应的 TLB 条目，确保后续地址访问使用最新的页表映射。

```rust
pub fn tlb_invalidate(va: Option<VirtAddr>, asid: Option<usize>);
```

`sfence.vma` 可以在指定的地址空间 ID（ASID）范围内精确刷新单个虚拟地址或全部 TLB 条目，减少全 TLB 刷新带来的性能损失。

## 3.12 未来改进方向

1. **页面回收与 Swap**：当前不支持物理帧的换出（swap），所有已分配的物理帧始终驻留在内存中。引入 swap 机制可以在内存紧张时将不活跃的匿名页换出到磁盘；
2. **透明大页（THP）**：利用 SV39 支持 2MB 大页和 1GB 巨页的特性，在合适的场景下自动合并连续的小页为大页映射，提升 TLB 覆盖率；
3. **KSM（Kernel Same-page Merging）**：识别内容相同的物理帧并合并，减少冗余内存占用，特别适用于多实例虚拟化场景；
4. **NUMA 感知的物理内存分配**：在多核系统上根据 CPU-内存距离进行页面分配优化。
