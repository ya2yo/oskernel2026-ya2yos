# 第六章 IO设备

## 6.1 设备驱动架构

Ya2yOS 的设备驱动层采用 **分层抽象** 设计，将不同类型的设备通过统一的 trait 接口进行管理。驱动层位于 `os/src/drivers/` 目录下，核心由以下 trait 定义：

```rust
// 基础设备驱动 trait
pub trait BaseDriver: Send + Sync {
    fn device_name(&self) -> &str;
    fn device_type(&self) -> DeviceType;
    fn irq_num(&self) -> Option<usize> { None }
}

// 块设备驱动 trait
pub trait BlockDriver: BaseDriver {
    fn num_blocks(&self) -> usize;
    fn block_size(&self) -> usize;
    fn read_block(&mut self, block_id: usize, buf: &mut [u8]) -> DevResult;
    fn write_block(&mut self, block_id: usize, buf: &[u8]) -> DevResult;
    fn flush(&mut self) -> DevResult;
}
```

支持的设备类型枚举：

```rust
pub enum DeviceType {
    Block,    // 块存储设备（磁盘）
    Char,     // 字符设备（串口）
    Net,      // 网络设备（网卡）
    Display,  // 显示设备（GPU）
}
```

因本人能力有限，IO 设备相比TatlinOS暂未进行大规模修改，以下简要说明 IO 设备的设计。

## 6.2 VirtIO 框架

### 6.2.1 VirtIO 简介

VirtIO 是一种半虚拟化的 IO 设备标准，广泛用于 QEMU/KVM 等虚拟机管理器。与完全模拟物理硬件（如 IDE 磁盘、e1000 网卡）相比，VirtIO 通过共享内存队列（virtqueue）在 Guest 和 Host 之间高效传递 IO 请求，显著减少了虚拟化开销。

Ya2yOS 使用 `virtio-drivers` crate 提供的 VirtIO 设备驱动框架，支持 **MMIO**（Memory-Mapped I/O）传输方式（RISC-V64）和 **PCI** 传输方式（LoongArch64）。

### 6.2.2 VirtIO 传输层

- **MMIO 传输（RISC-V64）**：QEMU 将 VirtIO 设备的 MMIO 寄存器映射到物理地址空间（如 `0x10001000`、`0x10002000`）。内核通过读写这些 MMIO 地址与设备通信。`MmioTransport` 封装了 MMIO 寄存器访问；

- **PCI 传输（LoongArch64）**：在 LoongArch64 平台上，VirtIO 设备通过 PCI 总线暴露。内核通过遍历 PCI 配置空间探测设备，然后使用 `PciTransport` 进行通信。

### 6.2.3 HAL 适配

内核需要为 `virtio-drivers` 提供 HAL（Hardware Abstraction Layer）实现。`VirtIoHalCMAImpl` 负责：

- **DMA 内存分配**：通过 CMA 分配器分配物理上连续的内存用于 virtqueue 缓冲区
- **物理地址转换**：`pa = va - KERNEL_ADDR_OFFSET`
- **MMIO 访问**：封装物理地址的读写操作

### 6.2.4 Virtqueue 通信机制

VirtIO 设备使用 virtqueue（虚拟队列）在 Guest 和 Host 之间传递数据。每个 virtqueue 包含三个部分：

- **Descriptor Table**：描述符数组，每个描述符指向一个 Guest 物理地址缓冲区，包含长度和标志（读/写、链式描述符等）；
- **Available Ring**：Guest 驱动向设备提交可用描述符的环形缓冲区；
- **Used Ring**：设备处理完成后向 Guest 报告已用描述符的环形缓冲区。

以块设备读取为例：
1. 内核分配一个物理缓冲区，创建描述符指向该缓冲区（标记为设备可写）；
2. 将描述符索引写入 Available Ring，更新 Available Index；
3. 通知设备（kick）：写 MMIO Queue Notify 寄存器；
4. 设备处理请求，从磁盘读取数据到缓冲区；
5. 设备将描述符索引写入 Used Ring，发送中断通知 Guest；
6. 内核从 Used Ring 取出已完成的请求，读取缓冲区中的数据。

## 6.3 块设备

### 6.3.1 VirtIO 块设备

```rust
// RISC-V64
pub type BlockDeviceImpl = VirtIoBlkDev<VirtIoHalCMAImpl>;
// LoongArch64
pub type BlockDeviceImpl = VirtIoBlkDev2<VirtIoHalCMAImpl>;
```

`BlockDeviceImpl` 是 VirtIO 块设备的驱动封装，实现了 `BlockDriver` trait。初始化时访问地址 `0x10001000 + KERNEL_ADDR_OFFSET`（RISC-V64）的 MMIO 区域，与 QEMU 中的 VirtIO 块设备建立通信。

### 6.3.2 Disk 抽象

```rust
pub struct Disk {
    block_id: usize,      // 当前块号
    offset: usize,        // 块内偏移
    dev: BlockDeviceImpl, // 底层块设备
}
```

`Disk` 在 `BlockDeviceImpl` 之上提供了一个带**位置光标**的读写抽象，屏蔽了块级操作的复杂性：

- `Disk::read_one(buf)`：在当前位置读取数据（可能跨块边界），自动处理不完整的块读取（先读整块再提取所需部分）；
- `Disk::write_one(buf)`：在当前位置写入数据，同样处理跨块和不完整块写入；
- `Disk::set_position(pos)`：设置光标位置（按字节寻址，内部转换为块号+偏移）。

块大小固定为 512 字节（`BLOCK_SIZE`）。

### 6.3.3 与文件系统的集成

`Disk` 结构被传递给 lwext4 的 `BlockDevice` 接口实现，使得 ext4 文件系统能够在 VirtIO 块设备上运行：

```rust
// lwext4_rust 中的块设备适配
impl blockdev::BlockDevice for DiskAdapter {
    fn read(&self, buf: &mut [u8]) -> Result<i32, SysErrNo>;
    fn write(&self, buf: &[u8]) -> Result<i32, SysErrNo>;
    fn seek(&self, pos: usize);
    fn size(&self) -> usize;
}
```

## 6.4 网络设备

### 6.4.1 VirtIO 网络设备

```rust
// RISC-V64: MMIO 传输，128 个队列槽位
pub type NetDeviceImpl = VirtIoNetDev<VirtIoHalCMAImpl, MmioTransport, QUEUE_SIZE>;
// LoongArch64: PCI 传输
pub type NetDeviceImpl = VirtIoNetDev<VirtIoHalCMAImpl, PciTransport, QUEUE_SIZE>;
```

VirtIO 网络设备使用**两个 virtqueue**：
- **Receive Queue（RX）**：Host → Guest，接收数据包
- **Transmit Queue（TX）**：Guest → Host，发送数据包

队列大小 `QUEUE_SIZE = 128`，即每个队列最多容纳 128 个待处理的数据包。

### 6.4.2 网络设备发现

在 RISC-V64 上，`NetDeviceImpl::try_new_device()` 探测 MMIO 地址 `0x10002000`：

1. 读取 MMIO 头部的 Magic Value 验证是否为合法的 VirtIO 设备；
2. 读取 Device ID 确认是网络设备类型；
3. 协商特性（feature negotiation），如 `VIRTIO_NET_F_MAC`、`VIRTIO_NET_F_STATUS` 等；
4. 初始化 RX 和 TX virtqueue；
5. 读取 MAC 地址。

如果探测失败（地址不可读或不是合法设备），返回 `None`，网络子系统将以无物理网卡模式运行（仅 loopback 可用）。

### 6.4.3 设备容器

```rust
pub struct DeviceContainer<T> {
    devices: Vec<T>,
}
```

`DeviceContainer` 管理多个同类型设备实例，提供了 `from_one()`、`take_one()` 等方法。网络初始化时从中取出一个设备配置为 eth0。

## 6.5 字符设备

### 6.5.1 串口控制台

UART 串口作为内核的控制台输入输出设备，映射在物理地址 `0x10000000`（NS16550A 兼容）。

控制台模块（`console.rs`）实现了：

- `putchar(c)`：通过 UART 发送一个字符。写入 UART 的 THR（发送保持寄存器）并通过 LSR（线路状态寄存器）轮询等待发送完成；
- `getchar()`：从 UART 读取一个字符。轮询 LSR 等待数据就绪，然后从 RHR（接收保持寄存器）读取。

在 QEMU 环境下，UART 输入输出被重定向到宿主机的标准输入/标准输出，提供交互式的控制台体验。

### 6.5.2 标准输入输出文件

`Stdin` 和 `Stdout` 是实现了 `File` trait 的特殊文件，提供进程级别的标准输入输出：

- `Stdin::read()`：从 UART 读取数据（阻塞等待输入），支持行缓冲；
- `Stdout::write()`：向 UART 写入数据，直接输出到宿主终端。

它们分别对应文件描述符 0（stdin）和 1（stdout），在进程创建时由内核自动打开。

## 6.6 PCI 总线（LoongArch64）

在 LoongArch64 平台上，VirtIO 设备通过 PCI 总线枚举。`pci.rs` 实现了基础的 PCI 配置空间访问：

1. 遍历 PCI 总线、设备、功能号；
2. 读取配置空间的 Device ID 和 Vendor ID；
3. 匹配 VirtIO 网络设备（Device ID = 0x1041 + transport）；
4. 配置 BAR（Base Address Register）空间并创建 `PciTransport`。

## 6.7 设备中断处理

### 6.7.1 中断处理架构

Ya2yOS 的中断处理分为两层：

- **架构相关层**（`arch/irq/`）：提供 `handler_table`，注册外部中断处理函数。当外部中断发生时，trap handler 根据中断号查表调用对应的处理函数。
- **设备驱动层**：VirtIO 设备在初始化时向 `handler_table` 注册自己的中断处理函数。

### 6.7.2 当前中断处理策略

当前版本的 Ya2yOS 对外部中断处理较为基础：

- **VirtIO 块设备**：使用同步（轮询）模式，读写请求直接阻塞等待完成，不依赖中断；
- **VirtIO 网络设备**：数据包收发通过 `poll_interfaces()` 在时钟中断路径中轮询驱动，不依赖 VirtIO 网络中断；
- **UART**：同样使用轮询方式。

这种设计简化了中断处理的复杂性，但在高 IO 负载下可能引入额外的轮询开销。

## 6.8 DeviceFS

`DeviceFS` 模块实现了设备文件系统，在 `/dev` 目录下创建设备节点。当前支持以下设备文件：

- `/dev/null`：数据黑洞，写入的数据被丢弃，读取始终返回 EOF
- `/dev/zero`：读取时返回无限零字节
- `/dev/random` / `/dev/urandom`：随机数设备（简单实现）
- `/dev/loop*`：回环设备（loop device），用于将文件映射为块设备

## 6.9 Loop Device

Loop Device（回环设备）允许将一个普通文件作为块设备来访问。这对于挂载磁盘镜像文件极其有用：

```rust
pub struct LoopDev {
    file: Arc<OSFile>,   // 关联的后端文件
    // ...
}
```

Loop Device 通过 `ioctl` 系统调用进行管理：
- `LOOP_SET_FD`：将 loop 设备关联到一个文件
- `LOOP_CLR_FD`：解除关联
- `LOOP_GET_STATUS` / `LOOP_SET_STATUS`：获取/设置 loop 设备状态

这一机制使得 Ya2yOS 可以在现有 ext4 文件系统之上挂载额外的磁盘镜像（如 ext4 镜像文件）。

## 6.10 未来改进方向

1. **异步 IO（AIO）**：实现 Linux 的异步 IO 接口（`io_uring` 已有 stub），支持非阻塞的磁盘 IO 操作；
2. **中断驱动的网络**：利用 VirtIO 网络设备的 MSI-X 中断，替代当前的轮询模式，降低延迟和 CPU 占用；
3. **DMA 引擎抽象**：为 DMA 操作提供统一的内核接口，优化大批量数据传输；
4. **更多设备支持**：GPU（virtio-gpu）、输入设备（virtio-input）、熵设备（virtio-rng）等；
5. **设备电源管理**：实现设备的挂起/恢复（suspend/resume）机制。
