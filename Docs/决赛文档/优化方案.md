# BuildStorm 优化方案

> 适用源码快照：`467f56b1` 加当前未提交的 P22 Linux-aligned EXT4 重构工作区（2026-08-03）。本文只保留当前实现、
> 有效结论、下一步动作和验收边界；历史实验与故障取证见末尾问题记录。

## 0. 路线选择

不再把 `EXT4_OP_LOCK` 的微调当作主线。Linux 没有覆盖全部 ext4 API 的 mount-wide operation lock；它通过 VFS inode、
directory、page cache、block allocator 和 JBD2 transaction 的资源级协议并发运行。当前基于 lwext4 的 pathname wrapper
没有这些对象和协议，继续把全局 gate 拆得更细只能得到更多难以证明正确的例外，不会变成 Linux EXT4。

因此后续实现选择**项目原生 EXT4，Linux 源码作为语义、on-disk format 和并发模型的依据，而不是复制 Linux C 代码**。
直接搬运 Linux `fs/ext4` 不可行：Linux 7.0 的 `EXT4_FS` 依赖 `BUFFER_HEAD`、`JBD2` 和 `FS_IOMAP`，ext4 inode 还绑定
Linux VFS 的 `inode/file/address_space_operations`、folio/page cache、bio、RCU 和 workqueue；Ya2yOS 不具备这些内部 ABI。
“完善”必须以明确的支持矩阵、LTP 语义回归、`e2fsck -fn` 和崩溃恢复为验收，而不是以锁是否被删掉定义。

P21.3 reader/writer admission 只保留为 lwext4 过渡层的正确性和性能兜底，不再扩大到写路径；新功能和主要工程时间优先
投入 P22 的 native inode、extent、directory、allocator 和 transaction 路径。

## 1. 结论

当前 BuildStorm 的首要内核瓶颈仍是挂载级 `EXT4_OP_LOCK` 的排他段：多 hart 能并发运行任务，但 namespace、
allocator、journal、descriptor rebind 与真实写回仍会形成 FIFO 写者栅栏和锁 convoy。调度器耗时和文件页缓存容量在
最新样本中都不是主导项。

内核已经完成撤退全局 gate 所需的两项基础工作：位置无关块 I/O（P21.1）和并发 bcache 基础设施与 telemetry
（P21.2/P21.2a）。P21.3 已将已审计的纯读 API 改为 FIFO shared admission，保留所有可能写盘或改变 C descriptor
的路径为 exclusive；这不是移植 Linux ext4 的完整锁模型，inode identity、目录、allocator 和 journal 仍缺少其各自
的并发协议，因此 `lwext4-smp` 默认启用不等于“EXT4 已并行化”。

P21.2b.0 已用 sanitizer lifecycle oracle 验证当前已覆盖的 bcache intrusive tree/list/refcount 状态机，P21.2b.1 已将
cache-wide dirty flush 改为 bcache 内部的 claim/pin、锁外写回、统一 release。P21.2b.2 已实现为默认关闭的 dirty-capacity
256/128 blocks 高低水位实验：victim 只能经 bcache 内部 API claim/pin，I/O 在 index lock 外，成功写回后才丢弃 clean
buffer，失败保留 dirty。首次 P21.2b dirty victim 实验曾因 LRU RB tree `LoadPageFault` 回退，因此不得恢复由外部策略
直接 `RB_REMOVE`/`RB_INSERT` 的路径，更不能据此将 gate 改成 `RwLock`。

## 2. 当前实现

| 子系统 | 已实现 | 当前边界 |
| --- | --- | --- |
| SMP 与调度 | RISC-V/LoongArch64 SMP；默认 CFS 使用 per-hart run queue，支持 remote enqueue 与 idle hart IPI；perf 可统计 dispatch/wakeup。 | 最新 BuildStorm 中 dispatch 累计远低于 EXT4 wait；暂不调整调度策略或并发度。 |
| 文件页缓存 | 普通文件最大 32 MiB 准入；全局 192K 页（768 MiB）；最多四页顺序预读；clean-page CLOCK 仅回收无外部 `FilePage`/frame 引用的页；dirty/in-use 候选进入 deferred 队列，满载失败保留 direct bypass。 | 生产容量不是当前调参项；2,048 页的 `file-cache-capacity-test` 只用于满载回归。脏页写回与 mmap/truncate 可见性必须优先于命中率。 |
| VFS/EXT4 热路径 | FsIndex、负 dentry、regular-file stat cache、目录局部 epoch、文件页缓存；write quota 移出 gate；write open/data 分段；创建事务复用 stat；稀疏写有界缓冲；rename 成功后迁移 dense path cache。 | 这些均是 lwext4 过渡优化；P22 将以 `(device, inode, generation)` identity、独立 open-file `f_pos` 和 native extent/directory lookup 替换 pathname identity。 |
| EXT4 gate | `EXT4_OP_LOCK` 是 task-aware FIFO reader/writer gate，禁止插队；队首连续 shared waiter 可批量准入，writer 排队后新的 reader 不插队；支持 waiter 取消和任务退出回收。`read-data`、find、read-dir、readlink、get/listxattr、link-count、statfs/ls 可 shared；真实写入、namespace、sync、close、seek、descriptor open/rebind、fstat/recovery 和 metadata setter 为 exclusive。 | 仅作为 lwext4 过渡层。P22 native read path 落地后，读取不再经过该 gate；写路径只能在对应 inode、directory、allocator 和 transaction 锁完整实现后逐段迁移，禁止继续把它当 Linux 锁模型的替代品。 |
| P21.1 块设备 | `KernelDevOp` 使用 `device_size/read_at/write_at/flush`；`Disk` 无共享 cursor，以设备 submission mutex 覆盖一次完整请求及非对齐 RMW；C byte-I/O 使用每次调用 scratch。 | 设备提交仍可串行，但锁域已收缩到单次请求。当前日志中 device contention 为 0，没有证据支持优先拆设备锁。 |
| P21.2 bcache | LBA/LRU/dirty/refcount 由短时 `index_lock` 保护；miss 二次 lookup；`BC_LOADING/BC_IO_ERROR` 同 LBA single-flight；`BC_WRITEBACK/BC_EVICTING` 配合 refcount pin；I/O 和等待在 index lock 外；Rust 提供 task-aware wait/wake。 | 纯读请求已能在 shared admission 下并发进入 bcache；writer 仍独占 mount-wide gate，waiter 仍是 mount-wide wake-all；clean-only shake 遇到全 dirty cache 会越过 16-block soft target。 |
| P21.2a 观测 | perf 内核在 mount 后统一启用并清零 bcache、C block I/O 和 Rust `Disk` 请求计数；报告累计与 interval 的 hit/miss、load/wait、shake/overflow、writeback、resident 和请求时延。 | relaxed interval 快照允许一个在途同步请求造成字段暂差 1；守恒以完整累计快照为准。普通 release 不承担 Rust perf 计数开销。 |
| P21.2b.0 生命周期 oracle | 新增 host C oracle 与 `ext4_bcache_validate()`；覆盖顺序/随机 acquire-release、dirty/flush、clean eviction、读写错误、同/异 LBA 并发 load、writeback callback 与 shake 竞争及负向 corruption control，并逐步检查 refcount、LBA/LRU RB tree、dirty list 和 `ref_blocks`。 | oracle 只验证已覆盖的 bcache 生命周期约束，不代替 RISC-V/LoongArch64 内核压力、fsck 或完整 BuildStorm。 |
| P21.2b.1 dirty ownership | `ext4_bcache_claim_dirty()` 在 `index_lock` 内从 dirty list 选取并建立 refcount pin；`ext4_bcache_release_dirty()` 统一恢复 LRU/dirty membership。cache flush 在锁外写回，写失败保留 dirty 且单次调用不递归重试。 | 只修复 writeback 对象生命周期；尚未启用 256/128 blocks 容量控制，也未撤退 `EXT4_OP_LOCK`。 |
| P21.2b.2 dirty capacity（默认关闭） | `bcache-dirty-capacity-experiment` feature 使用独立 CMake 目录和静态库名，避免错误复用另一配置。resident 达 256 时，依次 claim dirty、锁外写回、成功后仅丢弃 clean block，回收至 128；失败 release 回 dirty list 并向本次 get 返回错误。新增 reclaim run/block/stall telemetry 和 error-injection lifecycle oracle。 | 目前外层 gate 仍使生产 C API 串行；日志仅证明已观察到的高水位和一批回收。`capacity_overflows` 仍按历史 `bc->cnt=16` 统计，不能用于判定 256 水位是否失守。 |

## 3. 有效证据

### 3.1 当前稳定基线

P21.2a 的 `log.ans` 有 `BUILDSTORM_TOOLCHAIN/MINIBUILD ok`，约 573 秒时到 Cargo `21/446`，没有 panic、
`ERROR`、`TFAIL` 或 `TBROK`；但没有 `BUILDSTORM_COMPILE ... ok=true`、测试组 `END` 或 `shutdown!`，
只能用于方向判断，不能报告端到端加速或回退比例。

末个完整累计快照满足：

- `get_ops=661695 = cache_hits 412142 + cache_misses 249553`；
- `loader_ops=249553 = successes 249553 + errors 0`；
- `writeback_ops=18515 = successes 18515 + errors 0`；
- `initial 16 + allocations 266818 - drops 266818 = resident 16`；
- `allocation_races=0`、loader/writeback wait 为 0、device contention 为 0。

同时出现 `shake_full_dirty=401664`、`capacity_overflows=181972`、`max_resident_blocks=1243`。这说明 16-block
bcache soft target 在 dirty-only 压力下不收敛；它不证明设备锁或 waiter 分桶是当前瓶颈，因为全局 gate 尚未撤退。

历史长样本中 `read/find/fstat/write` 的 gate wait 明显高于 hold，scheduler dispatch 仅占很小部分；文件页缓存也未
触及 192K 页上限。因此当前优先级是 EXT4 串行边界和 dirty bcache 生命周期，而不是扩大页缓存、预读窗口或调整 CFS。

### 3.2 P21.2b.0/P21.2b.1 阶段验证

新的 RISC-V 8 HART `tmp_12.ans` 有测试组 `START` 与 `BUILDSTORM_TOOLCHAIN/MINIBUILD ok`，在约
`t=175236ms` 的末次累计快照后仍未出现 panic、`ERROR`、`TFAIL`、`TBROK` 或 SIGSEGV。它没有
`BUILDSTORM_COMPILE ... ok=true`、测试组 `END` 或 `shutdown!`，因此只能证明已观察区间阶段稳定，不能报告完整
BuildStorm 通过或性能提升。

末次累计 bcache 快照满足：

- `538658 = 332749 cache_hits + 205909 cache_misses`；
- `205909 loader_ops = 205909 successes + 0 errors`；
- `13362 writeback_ops = 13362 successes + 0 errors`；
- `16 initial + 218541 allocations - 218541 drops = 16 resident`。

C block callback 的 read/write 请求分别为 `231256/17769`，总计 `249025`，submit 与 complete 全部相等且 error
为 0；device contention 为 0。相邻两个 interval 的 loader 和 read submit/complete 先后出现 `-1/+1` 的互补差异，
是 relaxed 分字段快照跨过一个在途请求；末次累计快照闭合，不作为错误计数。

容量压力仍未解决：`shake_full_dirty=353857`、`capacity_overflows=161383`、`max_resident_blocks=1243`。gate 同时
累计 `fast_acquires=35588`、`queued=6025`、`handoffs=6021`、`queue_depth=4`、`max_queue_depth=8`，handoff wait
累计 `81379237us`。这说明 lifecycle 修复未引入已观察到的正确性错误，但 16-block clean soft target 和 mount-wide
gate 仍分别造成容量失控与串行争用。

### 3.3 已回退实验

`tmp_11.ans` 在 P21.2b dirty victim 实验中触发 RISC-V `LoadPageFault`，`sepc=0xffffffc080369392` 定位到
`ext4_buf_lru_RB_REMOVE_COLOR`。实验代码仅凭 `refctr==0` 和一次 LRU 遍历就直接摘除、写回并重插 intrusive
RB tree 节点，没有证明 index ownership，故已完整回退到 P21.2a clean-only shake。该日志是正确性失败，不是性能样本。

### 3.4 P21.2b.2 两分钟 RISC-V 阶段验证

维护者已在 Docker 中以 RISC-V musl 工具链成功编译实验配置；当前 `log.ans` 是该配置约两分钟的 8 HART 运行结果。
日志有 `BUILDSTORM_TOOLCHAIN/MINIBUILD ok`，未出现 panic、SIGSEGV、`ERROR`、`TFAIL` 或 `TBROK`，但没有
`BUILDSTORM_COMPILE ... ok=true`、测试组 `END` 或 `shutdown!`，故只能证明阶段稳定和容量路径被执行，不能报告完整
BuildStorm 通过、速度提升或回退比例。

约 `t=114851ms` 的累计快照满足：

- `get_ops 367548 = cache_hits 200149 + cache_misses 167399`；
- `loader_ops 167399 = loader_successes 167399 + loader_errors 0`；
- `writeback_ops 4917 = writeback_successes 4917 + writeback_errors 0`；
- `initial 16 + allocations 172079 - drops 171901 = resident 194`；
- C block request `186059 read + 6889 write = 192948 completed`，read/write/device error 都为 0。

新 telemetry 为 `dirty_capacity_reclaim_runs=1`、`dirty_capacity_reclaimed_blocks=128`、
`dirty_capacity_reclaim_stalls=0`，并且 `max_resident_blocks=256`。这表明实验 feature 已实际链接，达到 high 后完成了一次
回收批次；回收后的 workload 又增长到 resident 194，属于 128/256 hysteresis。`capacity_overflows=132836` 仍表示超过
旧 16-block soft target 的历史计数，预期会很大，不表示 256 水位突破。

### 3.5 P21.3 shared admission 的 `tmp_13.ans`

新的 RISC-V 8 HART `tmp_13.ans` 有 `BUILDSTORM_TOOLCHAIN/MINIBUILD ok`，在 `t=283386ms` 后继续到 Cargo
`Building 11/446`；未出现 panic、SIGSEGV、`ERROR`、`TFAIL` 或 `TBROK`，但没有 compile success、测试组 `END` 或
`shutdown!`。因此它只证明已观察区间的阶段稳定，不报告完整 BuildStorm 通过或加速。

该样本确认 shared admission 真正工作：`shared_acquires=39042`、`shared_handoffs=2224`、
`max_active_readers=7`。同时累计 gate handoff wait 仍为 `567915801us`，而读、find、metadata 和 write 的锁等待仍显著，
说明 writer 栅栏和长写事务仍是当前重点。`fstat` 的 sparse flush 计数为 6，且 fstat/recovery 可触发 `file_close()`；
因此它不能作为 shared 路径，后续代码已维持 exclusive，避免把实际写回错误归类成“读并发”。

## 4. 优化顺序

| 优先级 | 工作 | 完成条件 |
| --- | --- | --- |
| P0 | 固定当前基线 | 同一 commit、镜像、QEMU `-smp`、Cargo jobs 和冷启动配置至少完成一次 BuildStorm；记录完整结束标记和宿主 wall-clock。 |
| P21.2b.0（已完成） | bcache 生命周期 oracle | host ASan/UBSan oracle 已覆盖 acquire/release、load、flush、clean eviction、dirty-list 转换、读写错误、同/异 LBA 并发、writeback/shake 竞争、10 万步随机 trace 与负向破坏检查。 |
| P21.2b.1（已完成） | 单一 claim/release API | cache-wide flush 已通过 bcache 内部 API 完成 pin、锁外 writeback 和成功/失败 release；生产 `ext4_block_flush_buf()` 调用点均持有 refcount pin，策略层不再直接取 dirty list 裸指针。 |
| P21.2b.2（已实现，默认关闭） | dirty 容量实验 | 256/128 blocks 高低水位、claim/pin、锁外 writeback、clean-only discard、I/O error retention、host lifecycle oracle 和 reclaim telemetry 已完成。继续验证 `resident <= high + in_flight_loaders`、错误恢复、8 HART 压力和 `e2fsck -fn`，再决定是否默认启用。 |
| P21.3（冻结） | lwext4 shared admission | 保留当前已审计的纯读 shared admission，并只修复正确性和回归；不再扩大到 fstat、write 或 namespace。`tmp_13.ans` 的 `max_active_readers=7` 仅证明过渡层生效。 |
| P22.0 | 范围与镜像兼容矩阵 | 固定支持的 ext4 feature 位、挂载选项、读写/恢复语义和测试镜像；将 unsupported feature 显式拒绝，不再由 lwext4 静默降级。验收：只读挂载、错误 feature 拒绝、`e2fsck -fn` 基线。 |
| P22.1 | Native read path | 实现 superblock/group descriptor/inode 读取、extent 映射、directory htree lookup、symlink 和 inode cache；VFS inode identity 用 `(device, ino, generation)`，open file 独立保存 `f_pos`。验收：只读 BuildStorm/LTP、并发读压测、与 Linux `debugfs`/`e2fsck -fn` 对照。 |
| P22.2 | Native metadata 与 namespace | 实现 inode 写回、目录 create/unlink/link/rename、truncate、xattr，以及 Linux 风格 parent/source/target 锁序。验收：相关 LTP、并发 rename/create、断言 free inode/block 计数守恒。 |
| P22.3 | Allocator、transaction 与 recovery | 实现 block-group allocator、extent 写时分配、transaction handle、ordered writeback、orphan/recovery；先形成项目原生的可恢复日志边界，再决定是否实现 JBD2 on-disk 兼容。验收：fault injection、掉电恢复、`e2fsck -fn`、全量文件系统 LTP。 |

P22.0 是当前工程的下一步；P21.2b.2 的 `e2fsck -fn`、8 HART 持续运行和两次完整 A/B 仍是 lwext4 过渡层的退出条件。
暂不实施：继续扩大页缓存或预读、恢复正 dentry fast path、拆 `Disk::dev` mutex、按 LBA waiter 分桶、提高 BuildStorm
并发度，或仅通过删除 `EXT4_OP_LOCK` 宣称 Linux 对齐。新代码优先进入 native EXT4 read path；只有该路径完整覆盖一个
Linux-visible 功能域并通过对应语义/磁盘检查，才从 lwext4 迁移该功能域。

## 5. 正确性约束

- lwext4 仍在使用时，所有 lwext4 public API 仍须持有 `EXT4_OP_LOCK`；已审计的纯读 API 使用 shared，其余 API 使用
  exclusive。P21.2 的内部锁只提供 bcache 基础设施，不能替代目录、allocator 或 journal 的写侧协议。native EXT4 与
  lwext4 不能在同一挂载上交错写入；迁移必须按只读功能域、metadata/namespace 功能域、transaction/recovery 功能域
  明确切换所有权。
- 固定现有锁序；不得持有 cache index spinlock 等待设备 I/O、task mutex、journal commit 或内存分配。
- 不牺牲 quota reserve/rollback、ENOSPC 小块回退、sparse overlay、`st_blocks`、mtime/ctime、rename/truncate/
  unlink/write 的 cache 失效和 mmap EOF/SIGBUS 语义。
- bcache 容量策略不得在运行时销毁重建 cache，也不得由外部策略直接操作 intrusive tree/list。
- `BC_WRITEBACK` 只表示 I/O 状态，不能替代对象生命周期引用；生产路径离开 index/list 保护域调用
  `ext4_block_flush_buf()` 前必须持有 refcount pin，并在 callback 与状态清理完成后统一 release。
- P21.2b.2 reclaim 在成功写回后只能释放 claim pin 并丢弃最终为 clean 的对象；I/O 失败必须恢复 dirty membership，
  不得在同一次 release 中递归重试。未来移除外层 gate 时，容量上界按 `high + in_flight_loaders` 验收，而非误读旧
  16-block `capacity_overflows`。
- 未出现完整结束标记时，只能报告方向性计数；跨任务累计 wait/hold 不能相加为 guest wall-clock。
- 任一阶段出现 stale read、错误 LBA、目录项丢失/重复、free count 漂移、journal abort、panic、死锁或 fsck 差异，
  立即关闭新路径并回退到上一个已验证阶段。

## 6. 验收

静态与双架构构建：

```bash
cargo fmt --manifest-path os/Cargo.toml --all -- --check
git diff --check
make TARGET_ARCH=riscv64
make TARGET_ARCH=loongarch64
make perf TARGET_ARCH=riscv64
make perf TARGET_ARCH=loongarch64
```

行为与并发回归至少覆盖：同/异 LBA、I/O error、64+ gate waiter 和 owner 退出；read/write/stat/rename/truncate/
unlink-open-close/fsync；mmap 尾页、越界页、并发 truncate；容量 feature；RISC-V 8 HART；涉及共享 C 代码时补
LoongArch64 冒烟和 `e2fsck -fn`。

性能结论必须使用同一环境至少两次完整运行，并同时出现：

```text
BUILDSTORM_COMPILE mode=multi ok=true elapsed_s=<...>
#### OS COMP TEST GROUP END buildstorm ####
shutdown!
```

常用日志提取：

```bash
rg -a -n "BUILDSTORM|shutdown!|panic|TFAIL|TBROK|ERROR|SIGSEGV|QEMU: Terminated" log.ans
rg -a -n "^\[perf\] (t=|interval_ext4|ext4_gate|ext4_bcache|ext4_block|file_cache|scheduler_duration)" log.ans
strings log.ans | tail -240
```
