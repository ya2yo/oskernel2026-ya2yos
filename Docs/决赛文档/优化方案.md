## 2. 不变约束

- 保持 `MAX_SPARSE_WRITE_BUFFER_SIZE = 512 KiB`、`MAX_SPARSE_WRITE_BUFFER_RUNS = 32`、
  `MAX_TOTAL_SPARSE_WRITE_BUFFER_BYTES = 8 MiB`；本轮不修改这些常量或 sparse 发布边界。
- `EXT4_OP_LOCK` 继续保护所有 lwext4 block cache 及 path/file C API。禁止改为 rwlock，禁止多 hart
  并发进入 lwext4。
- 保持锁序 `write_state -> io_state -> EXT4_OP_LOCK`；本轮新增的约束是 `MNT_TABLE` 不能与
  `EXT4_OP_LOCK` 同时持有。
- 保持 quota reserve 的粒度、最终小 chunk 的 `ENOSPC` 回退、`quota_reserved` 更新、写失败回滚、
  `defer_close_flush()`、`st_blocks`/mtime/ctime 失效和 sparse overlay 语义。

## 4. P1：将 write quota 移出 `EXT4_OP_LOCK`（已实施）

这是本轮唯一的代码改动，涉及 `os/src/fs/ext4_lw/inode.rs`、`os/src/utils/perf/fs.rs` 和
`os/src/utils/perf/report.rs`。

### 4.1 先拆分 write 锁统计

在 `os/src/utils/perf/fs.rs` 中把现有 `Ext4LockClass::Write` 拆为 `WriteOpen` 与 `WriteData`：

1. 为两类各增加一个 `Ext4LockStats`，并保留现有 `EXT4_WRITE_LOCK_STATS` 作为两段的总计。
2. 增加 `Ext4OpLock::lock_for_write_open()`、`lock_for_write_data()`；两者都记入 write 总计，分别记入
   open/data 子计。
3. 在 `os/src/utils/perf/report.rs` 输出 `ext4_write_open_lock` 与 `ext4_write_data_lock`。

这样可以区分“为得到 descriptor/size 的必要 gate 时间”和“实际 `file_write_at()` 的必要 gate 时间”，而不是
在改动后把减少的 quota 时间误读成 data 加速。

### 4.2 重排 `Ext4Inode::write_at()`

在 `os/src/fs/ext4_lw/inode.rs` 的 `write_at()` 中保持 `write_state`、`io_state` 覆盖整个操作，但按以下顺序
重构：

```text
write_state -> io_state
  -> WriteOpen gate: live path、ensure_open(O_RDWR)、known_size/file_size、delayed pin
  -> 释放 EXT4_OP_LOCK
  -> MNT_TABLE.reserve_write() 与 quota_reserved 更新
  -> WriteData gate: sparse 判定、file_write_at()、失败时 defer_close_flush()
  -> 释放 EXT4_OP_LOCK
  -> 写失败时 MNT_TABLE.rollback_reservation()；成功时更新 size/cache 状态
```

具体要求如下：

1. `WriteOpen` 段内复制稳定的 `path`，并以已有 `known_size()` 为准；仅在它为空时调用
   `file.file_size()`。`write_state` 已与 rename/truncate/write 互斥，因而 quota 阶段使用该 path 和 size
   不会与同 inode 的路径或大小变更并发。
2. quota 阶段原有的 `target` 对齐、`previous_reserved.max(current_size)`、首次 `ENOSPC` 后按 `end`
   再试、以及所有 `quota_reserved` 写入必须逐字保留；仅改变其不再位于 global gate 内。
3. `WriteData` 段保留 `disable_write_back_cache()`、`file_write_at()` 与失败时的
   `defer_close_flush()`。从 `file.last_write_path()` 取得 fstat 失效原因后再释放该 gate；不得让任何
   `Ext4File` 方法跨到 quota 或 rollback 段。
4. 失败回滚在 `WriteData` guard 释放后执行。成功与失败都不得持有 `MNT_TABLE` 时获取
   `EXT4_OP_LOCK`，也不得持有 `EXT4_OP_LOCK` 时获取 `MNT_TABLE`。

### 4.3 同一补丁解除既有反向嵌套

上述顺序要求同时修改 `inode.rs` 中两处既有嵌套，避免 quota 外移后引入
`MNT_TABLE -> EXT4_OP_LOCK` 与旧 `EXT4_OP_LOCK -> MNT_TABLE` 的循环等待：

1. `Ext4Inode::unlink()`：在 namespace gate 内只完成 `file_remove()`、epoch 与 stat-cache 更新；成功后
   退出该 scope，再调用 `MNT_TABLE.remove_file(path)`。
2. `impl Drop for Ext4Inode`：在 close gate 内完成 delayed `file_remove()` 和 `file_close()`，将待删除路径
   保存到局部值；guard 释放后才调用 `MNT_TABLE.remove_file()`。

这两处的 quota 删除必须只在 lwext4 删除成功时发生，错误返回、延迟删除和 inode identity/directory epoch
的现有语义保持不变。

## 8. P4/P5：dentry 取证与目录 stat cache（已实施）

`tmp_17.ans` 在 `t=539.592s`、Cargo `Building 29/446` 的末尾快照显示：`path_index_hit=31,517`，
`dentry_positive_insert=2,013`，但 `dentry_positive_hit=0`；负 dentry 则有 `3,937` 次命中，
`dentry_clear_calls=0`、容量淘汰为零。根因不是 dentry 被清空或 parent key 失配：普通成功查找已立即发布到
`FsIndex`，下一次 open 先命中 path index，因而不会到 dentry 层。P4.0 已在 lookup/插入/失效和 parent miss 路径
补齐计数，结论是不恢复正 dentry fast path；负 dentry 继续保留。

同一快照的 `ext4_fstat_lock` 为 `4,919` 次、`wait_us=219,294,389`、`hold_us=59,343,405`。目录 pathname lookup
已经持有同一次 `ext4_stat_get()` 的结果，但旧实现只允许首次 fstat 消费一次。P5 将目录 Kstat 保留到
`EXT4_DIRECTORY_STAT_EPOCH` 改变为止；create、link、symlink、unlink、rename、目录的 mode/owner/timestamp 更新，
以及 `getdents` 触发的 atime 更新都会推进该 epoch。fstat 在 epoch load 处线性化，已完成的目录元数据修改必然
丢弃旧值并回退 lwext4；普通文件和 sparse/direct write 的 stat 失效策略不变。

维护者提供的 `tmp_18.ans` 末尾为 `t=566.931s`、Cargo `Building 32/446`，有 `19,457` 次 stat syscall、
`3,653` 次实际 `ext4_fstat`、`ext4_fstat_lock=3,656`、`wait_us=175,237,416`、`hold_us=52,576,106`。但它仍输出旧的
`lookup_directory_stat` 标签；当前 `bdd7e30b` 的 perf 内核应输出 `directory_epoch_cached` 和
`ext4_fstat_directory_stat`。因此该文件未装载 P5 内核，只能保留为旧实现的工作量与读锁基线，不能据其中的
`2,251` 次一次性 lookup-stat 返回宣称目录 epoch cache 生效。它有 `BUILDSTORM_TOOLCHAIN/MINIBUILD ok`，未见
`panic/TFAIL/TBROK/ERROR`，仍未出现 `BUILDSTORM_COMPILE`、END 或 `shutdown!`。

## 9. P9：有界地扩大大文件读缓存（已实施）

`tmp_18` 的主锁等待仍在 `ext4_read_data_lock`（`wait_us=500,516,550`）和 `ext4_find_lock`
（`wait_us=290,144,085`）。其中普通 read 有 `11,252` 次、`74,614,810 B` 因文件总大小超过当前 8 MiB 准入阈值
绕过页缓存。该数据尚未证明这些页会被第二次访问；原全局 `FILE_PAGE_CACHE` 也没有容量边界，因此不能无界地提高
单文件阈值。

P9 将 regular-file read 的准入从 8 MiB 提至 32 MiB，同时为全局页缓存设置 `96 * 1024` 页的固定上限（4 KiB 页时
约 384 MiB）。旧样本的 `mmap_miss=21,167`、`read_page_miss=24,919`、`readahead_pages=22,070` 合计低于约 68K 页，
故保留约 28K 页余量供原先被 8 MiB 阈值排除的编译输入使用。冷页在分配/发布前 CAS 预留一个槽位；并发重复发布、
页帧分配失败及 write/rename/truncate 失效都相应归还槽位。容量已满时仍把本次从 inode 读到的页返回给
`mmap/read`，仅不发布到共享 cache，不能返回 `ENOMEM` 或旧数据。

perf 新增：

```text
[perf] file_cache_capacity resident_pages=<...> max_pages=98304 capacity_bypass_pages=<...>
```

下次必须先执行 `make perf TARGET_ARCH=riscv64`，再确认运行镜像包含
`directory_epoch_cached`、`ext4_fstat_directory_stat` 和 `file_cache_capacity`。在相同 Cargo 检查点比较
`ext4_read_data_lock`/`ext4_find_lock` 的 wait/hold、`read_bypass_file_*`、页缓存命中/缺页、上述 resident/capacity
统计以及 `panic/TFAIL/TBROK` 与最终 BuildStorm 标记。只有两次同配置完整运行都通过，才可报告端到端结论；不得改变
lwext4 单一串行 gate、写入/rename/truncate 的 cache 失效，也不得把 timeout 样本当作端到端结果。

P9 已通过 `cargo fmt --manifest-path os/Cargo.toml --all -- --check`、`git diff --check`、
`make special_make TARGET_ARCH=riscv64`、`make special_make TARGET_ARCH=loongarch64`、
`make perf TARGET_ARCH=riscv64` 和 `make perf TARGET_ARCH=loongarch64`；最后再次重建 RISC-V perf 内核。未自行启动新的
长 QEMU，运行期效果待维护者提供装载新内核的样本。

两个样本中 lwext4 gate 仍有显著 read-data/find 排队，而原统计无法区分具体 backing-read 调用者。P10 因此新增：

```text
[perf] inode_read_source mmap_cache_fill_ops=... mmap_cache_fill_bytes=... \
       page_cached_cold_run_ops=... page_cached_cold_run_bytes=... \
       direct_bypass_ops=... direct_bypass_bytes=... other_ops=... other_bytes=...
```

只在真实 `Inode::read_at()` 成功返回后记录一次 `Relaxed` ops/bytes：`mmap` 缺页/预读填充归入
`mmap_cache_fill`，页缓存 regular-read 的单页加载和多页冷区间归入 `page_cached_cold_run`，
`try_page_cached_read()` 拒绝后的 `read(2)` 直读归入 `direct_bypass`，`splice` 页缓存加载归入 `other`。
page-cache hit、EOF 前的 size 检查和 `read_all()` 均不记入；因此该行描述 VFS `read_at` caller，而不是 page lookup
或设备 I/O。P10 不改变 `EXT4_OP_LOCK`、预读长度、缓存准入/容量、write/rename/truncate 失效和目录 epoch 语义。

末尾 `ext4 reads=32,954 / 296,203,960 B`，P10 已记录的 mmap fill、page-cached cold run 和 direct bypass 合计为
`28,858 / 281,906,659 B`，尚差 `4,096 / 14,297,301 B`。其中 mmap 为 `19,486 / 183,063,432 B`（约 59.1% ops），
regular-read cold run 为 `9,331 / 98,809,115 B`（约 28.3% ops），direct bypass 仅 `41 / 34,112 B`。同一快照
`ext4_read_data_lock=32,072`，恰为 reads 减去 `882` 次 delayed byte-cache hit，说明剩余来源确实仍在数据 gate 前后，
而不是报告采样误差。

全局调用点审计发现 P10 漏掉了 exec probe、ELF metadata prefix，以及 `push_elf_segment_from_file()` 的未对齐
`PT_LOAD` 段。最后一个路径把已映射的零页按目标页逐次 `inode.read_at()`，是上述 4K 级小读的主要候选；其保持存在是为了
处理不能表示成普通 file-backed VMA 的前后零填充语义。

P11 将该路径改为最大 `64 KiB` 的临时缓冲：每块仅调用一次 `read_at()`，再按页内偏移复制到已有映射页。缓冲按
`try_reserve_exact` 分配，分配失败与零/短读异常保持原来的错误返回；段首/尾未被拷贝的字节仍来自原映射页的零初始化。
这使单段不会因文件大小进行无界分配；每段最多以 `ceil(file_size / 64 KiB)` 次底层读完成，实际总次数仍取决于段数和短读。
P10 的 `other` 也接入所有四个 exec/ELF `read_at` 位置，`tmp_03` 已确认四个来源桶覆盖所有
`ext4 reads`；不修改 `EXT4_OP_LOCK`、页缓存、ELF 段权限、COW 或 auxv 语义。

已通过 `cargo fmt --manifest-path os/Cargo.toml --all -- --check`、`git diff --check`、RISC-V/LoongArch64
`make perf` 与默认 `make TARGET_ARCH=riscv64`（release 覆盖两种架构）；最后重建 RISC-V perf 内核。构建仅有已有
Cargo config、vendored `smoltcp` 和 release `ipi_sent` warning；为保留维护者 `disk.img` 链接，本轮不运行 `make run`。

`tmp_03.ans` 已装载包含 P11 标签的 RISC-V perf 内核；有 `BUILDSTORM_TOOLCHAIN ok` 和
`BUILDSTORM_MINIBUILD ok`，未见 `panic`、`TFAIL`、`TBROK` 或 `ERROR`。最后快照为 `t=599250ms`、Cargo
`Building 26/446`，没有 `BUILDSTORM_COMPILE`、END 或 `shutdown!`，因此仍不能报告完整 BuildStorm 或端到端加速。

末尾 `ext4 reads=29060 / 287043303 B`，四类来源为：mmap fill `18869 / 173813719 B`、page-cached cold run
`9335 / 98840795 B`、direct bypass `44 / 36608 B`、other `812 / 14352181 B`。ops 和 bytes 均精确相加到
`ext4 reads`，证明 P11 已覆盖此前遗漏的 exec probe、ELF metadata 和未对齐段读取；`other` 不再是零，但其余量不能
单独解释为重复 I/O 或性能损失。相同快照的 `byte_cache_read_hits=645 / 6657614 B` 仍属于独立的 byte-cache 口径。

本轮结论是“来源归因守恒成立”，不是“端到端变快”：Cargo 工作量和累计锁统计不能与 `tmp_02` 直接作 wall-clock
A/B。暂不扩大 32 MiB 文件准入、96K 页容量或四页预读上限，也不改变 EXT4 单一 gate 及写入失效语义。

## 13. P12：细分 mmap backing-read 来源（已实施，待新样本）

P11 已证明剩余主要 backing-read 来自 mmap fill（约 65% ops、60% bytes）和 page-cached cold run（约 32% ops、34%
bytes）。`tmp_04.ans` 末尾仍为同一 P11 内核：`mmap_cache_fill=19861/187563419 B`、
`page_cached_cold_run=8660/92375936 B`、`direct_bypass=42/34944 B`、`other=791/14311446 B`，页缓存为
`57402/98304` 页且 `capacity_bypass_pages=0`；日志仅到 `Building 26/446`，没有完整结束标记。

本轮只增加低开销来源细分：`FilePageCacheSource` 现在区分真实 demand page fault 与
`prefetch_shared_file_pages()` 的 fork/shared-map 预取，并继续只在成功 `inode.read_at()` 后记账，不对 page-cache hit
增加 atomic。报告保留原 `mmap_cache_fill_*` 聚合，同时新增 `mmap_demand_*` 与 `mmap_prefetch_*`，因此旧样本仍可比较。

下一份同一 Cargo 检查点应同时记录 mmap demand/prefetch ops+bytes、page-cached cold run、`ext4_read_data_lock` 的
samples/wait/hold、page fault/readahead、resident pages 和 `capacity_bypass_pages`。若 demand fill 占主导，再沿
`prepare_file_page()`、`mmap_read_page_fault()` 检查重复读取；若预取占比显著，则评估共享映射预取是否覆盖了已驻留页。
在来源比例稳定且有完整结束标记前，不修改预读深度、缓存上限或 EXT4 锁域。

## 14. P13：消除 mmap EOF 检查的重复页缓存加载（已实施，待新样本）

`tmp_05.ans` 末尾为 Cargo `Building 36/446`、`t=588233ms`；mmap demand 为
`21328 ops / 206960356 B`，prefetch 为 `0/0`，`file_cache_source mmap_miss=21329`，resident 为
`64836/98304` 页且 capacity bypass 为零。当前 trap 对文件映射先调用 `mmap_file_page_beyond_eof()`，该函数会
`get_or_load()`；确认页未越过 EOF 后又调用 `handle_page_fault()`，后者再次查询同一页缓存。该重复 lookup 不产生第二次
底层 read，但会在每个 demand fault 上增加页缓存读锁和路径比较。

P13 将 EOF 判断改为 `mmap_file_page_info()` 得到的页偏移与 `inode.size()` 比较，仅完整越过 EOF 的页返回 SIGBUS；
部分尾页仍进入唯一的 `prepare_file_page()` 加载路径，缺页处理失败时仅在冷路径重新检查 EOF 以覆盖并发截断；普通缺页、私有/共享映射和 COW 语义不变。未修改 P9 的
32 MiB 准入、96K 页容量、四页预读或 EXT4 gate。下一份样本需同时检查 `file_cache hit/mmap_hit` 是否下降、
`page_faults` 与 `mmap_miss` 是否保持、read-data lock 及 SIGBUS/尾页回归是否正常。

## 15. P14：`tmp_06` 验证 mmap demand 归因与 EOF 优化边界

`tmp_06.ans` 是装载 P13 perf 内核的十分钟窗口，最后快照为 `t=560923ms`、Cargo `Building 24/446`。日志包含
`BUILDSTORM_MINIBUILD ok`，未见 `panic`、`TFAIL`、`TBROK` 或 `ERROR`，但没有 `BUILDSTORM_COMPILE`、
`#### OS COMP TEST GROUP END buildstorm ####` 或 `shutdown!`，因此仍不是完整 BuildStorm 验收样本。

最后快照为：

```text
ext4 reads=29210 bytes=289132560
mmap_demand=19059 ops / 176501187 bytes
mmap_prefetch=0 ops / 0 bytes
page_cached_cold_run=9310 ops / 98278502 bytes
direct_bypass=43 ops / 35776 bytes
```

四类 `inode_read_source` 的 ops 和 bytes 分别精确相加为 `29210` 和 `289132560`，与 `ext4 reads` 守恒；本窗口的

P12 的分类稳定、P13 的路径可运行以及 P9 的容量上限未触顶，不能将不同 Cargo 交错或中途累计锁统计换算为端到端加速。
