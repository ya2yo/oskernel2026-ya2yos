## 1. 结论摘要

最后一次 `client.ans` 的多 Hart backtrace 不是锁循环死锁，而是一个 Hart 在持有同一
`MemorySet` 写锁时执行退化的 VMA 空间查找，其他 Hart 因地址空间操作、缺页和 rseq 用户
返回路径排队。真正的第一优先级是修复 `find_insert_addr()` 的算法复杂度；更换锁类型只能
减轻排队时的缓存行争用，不能消除写临界区内的 O(N²) 工作量。

建议按以下顺序推进：

1. 先把 VMA 存储和空洞查找从“无序 `Vec` + 递归重扫”改为有序、迭代的查找，并合并可合并的匿名 VMA。
2. 将 rseq 用户返回更新改为 Linux 风格的事件驱动，只在注册、调度切换、迁核或信号等事件后访问用户内存。
3. 在不改变语义的前提下，先为短小标量用户访问做单次锁保护的 fast path。
4. 再建设基于当前 `satp` 的 fault-safe uaccess；必须同时解决 RISC-V `SUM` 和内核态 fault fixup。
5. 最后再考虑 VMA 锁、页表锁、驻留页锁的进一步拆分，以及读锁竞争时的 backoff。

## 2. 最后一次 BT 证据

### 2.1 Hart 状态

现场位于 [client.ans](/home/ya2yo/projects/oskernel2026-ya2yos/client.ans:353)：

| Hart | backtrace 顶层 | 解释 |
| --- | --- | --- |
| CPU2 | `mmap(4 KiB) -> MemorySet::with_vma_mut -> inner.write -> find_insert_addr` | 当前写锁持有者；正在执行 VMA 空间查找。 |
| CPU4/5 | `mmap(64/128 MiB) -> with_vma_mut -> inner.write` | 等待同一 `MemorySet` 写锁。 |
| CPU6 | `handle_page_fault -> inner.write` | 等待同一地址空间写锁。 |
| CPU3 | `handle_page_fault -> prepare_file_page -> get_ref` | 等待同一地址空间读锁。 |
| CPU0/7 | `trap_return -> rseq_prepare_user_return -> copy_to_user -> get_ref` | rseq 用户返回更新等待读锁。 |
| CPU1 | idle loop | 没有参与这次锁队列。 |

CPU2 并没有停在 `RwLock` 原子指令或 remote-TLB ACK 上，而是已经拿到写锁并执行
`find_insert_addr()`；因此现场证明的是“长写临界区造成全核排队”，不是“所有 Hart
同时无法获得锁”。CPU0/7 的 `fetch_add` 读锁栈是排队结果，不是持锁者。

### 2.2 `find_insert_addr()` 的算法退化

当前实现位于 [area_ops.rs](/home/ya2yo/projects/oskernel2026-ya2yos/os/src/mm/memory_set/area_ops.rs:140)：

```rust
for area in self.areas.iter() {
    if candidate_overlaps(area) {
        let new_hint = candidate_start - PAGE_SIZE;
        return self.find_insert_addr(new_hint, size);
    }
}
```

相关事实：

- `push_lazily()` 直接 `self.areas.push(map_area)`，[area_ops.rs](/home/ya2yo/projects/oskernel2026-ya2yos/os/src/mm/memory_set/area_ops.rs:282)，`areas` 没有按地址排序。
- 普通 mmap 在 [mmap_ops.rs](/home/ya2yo/projects/oskernel2026-ya2yos/os/src/mm/memory_set/mmap_ops.rs:198) 每次都从 `MMAP_TOP` 调用它。
- 每次发现冲突都会重新从 `areas[0]` 扫描；连续小 mmap 会让一次调用反复扫描不断增长的前缀。
- `new_hint` 基于候选区间的起点，而不是冲突 VMA 的起点，导致额外页间隙并使后续扫描更长。

在连续 4 KiB 匿名 mmap、VMA 按追加顺序覆盖搜索方向的情况下，第 N 次查找可进行
约 1 + 2 + ... + N 次 VMA 检查，单次接近 O(N²)，累计 workload 可能接近 O(N³)。
这正好解释了 CPU2 停在一个看似简单的 4 KiB mmap，而 CPU4/5 的大 mmap 也无法推进。

### 2.3 为什么当前结论不是死锁

现场没有形成稳定的锁依赖环：

- CPU2 是明确的写锁持有者，并且栈位于 VMA 扫描代码，而非等待另一把锁。
- CPU0/7 只是读锁等待者；CPU3/4/5/6 也是同一 `MemorySet` 的排队者。
- CPU1 idle 表明系统仍有空闲 Hart，不能用“所有 CPU 被自旋锁完全吞掉”解释现场。

因此应把它归类为高争用地址空间写锁和算法退化。后续仍需保持既有锁序检查，但本现场
的第一修复目标不是继续修改 remote-TLB 协议。

## 4. Linux 7.0 对照

### 4.1 VMA 查找

Linux 不使用无序 VMA 数组递归重扫。Linux 7.0 的 `unmapped_area_topdown()` 使用 Maple
Tree iterator 的 `mas_empty_area_rev()`，见：

- `/home/ya2yo/linux/linux-7.0/mm/vma.h:550-559`
- `/home/ya2yo/linux/linux-7.0/mm/mmap.c:3004-3043`

Ya2yOS 不必直接移植 Maple Tree，但必须保持两个性质：VMA 地址有序、空洞查找不会在每个
冲突上从头扫描。短期可采用有序 `Vec` 的反向迭代；VMA 数量继续增长后再引入 `BTreeMap`
或带最大空洞信息的区间结构。

### 4.2 用户内存复制与 `satp`

“直接使用 `stap`”应为“直接使用 `satp`”。当前 Hart 在 syscall/trap 期间通常仍使用当前
进程的用户页表，且每个进程页表包含内核高地址映射，因此直接访问当前进程用户 VA 在架构
上可行。但 `satp` 只选择页表，不能自动提供 fault-safe 的用户复制语义。

Linux RISC-V 的用户访问由两部分组成：

1. 开启/关闭 `sstatus.SUM`，见 Linux [uaccess.h](/home/ya2yo/linux/linux-7.0/arch/riscv/include/asm/uaccess.h:59)。
2. 对允许 fault 的 load/store 建立 exception table，fault 后跳转到 fixup 并返回 `-EFAULT`，见 Linux [extable.c](/home/ya2yo/linux/linux-7.0/arch/riscv/mm/extable.c:82)。

Ya2yOS 当前 [translate.rs](/home/ya2yo/projects/oskernel2026-ya2yos/os/src/mm/translate.rs:217) 通过软件查 VMA、软件查页表，再按物理页复制；而 [trap/mod.rs](/home/ya2yo/projects/oskernel2026-ya2yos/os/src/trap/mod.rs:481) 对 RISC-V 内核态用户地址 fault 直接 panic。因此现在不能把 `copy_to_user/copy_from_user` 直接替换为裸 `ptr::copy`。

建议将 API 分成：

- `copy_*_current_user()`：仅允许目标 `MemorySet` 等于当前 `satp`，使用架构 uaccess fast path。
- 现有软件翻译路径：处理非当前地址空间、架构尚未具备 fault fixup 的场景。

在完整 fault-safe uaccess 完成前，可先实现“缺页/写时复制准备在锁外完成，短小复制在单次
读锁内完成”的保守 fast path；不能在持有 `MemorySet` 读锁时触发可能递归获取写锁的缺页。

### 4.3 rseq 用户返回

当前 [rseq.rs](/home/ya2yo/projects/oskernel2026-ya2yos/os/src/task/rseq.rs:182) 每次 trap return 都：

- 写 `cpu_id_start`；
- 写 `cpu_id`；
- 写 `node_id` 和 `mm_cid`；
- 读取 `rseq_cs`，必要时读取 descriptor、signature 并清零。

Linux 7.0 在调度切换/迁核事件置位 pending 标志；没有事件时用户返回只做一次廉价判断，
见 Linux [rseq.h](/home/ya2yo/linux/linux-7.0/include/linux/rseq.h:48-95) 和 [rseq_entry.h](/home/ya2yo/linux/linux-7.0/include/linux/rseq_entry.h:598-640)。

Ya2yOS 应引入 `sched_switch`、`ids_changed` 或等价的线程状态：注册时强制更新，任务实际
被切出/迁核时标记，信号路径单独触发 critical-section 检查；普通 trap return 不再进入
`MemorySet` 读锁。

## 5. 分阶段实施方案

### P0：修复 VMA 空间查找

这是当前最高优先级，建议单独提交。

1. 保持 `areas` 按 `vpn_range.start()` 升序排列；所有 split/remove/insert 都维护该不变量。
2. 用迭代式 top-down 查找替换递归实现：候选与 VMA 冲突时，直接把候选终点移动到该 VMA 起点。
3. 普通 mmap 增加 downward allocation hint；没有覆盖时走 O(1) 快路径，出现空洞或固定映射后再走完整查找。
4. 对相邻、权限/flags/backing 一致的匿名私有 VMA 做合并；文件映射只有在 inode、offset 连续且属性完全一致时才允许合并。
5. 修复后保持 `MAP_FIXED`、`munmap` 拆分、`MAP_GROWSDOWN`、`brk` 和 `mremap` 的地址排序不变量。

最小实现可以是“有序 Vec + 反向扫描”，长期实现再考虑 BTreeMap/Maple Tree 风格的 gap
索引。不要先引入复杂区间树而保留递归重扫。

### P1：rseq 事件驱动和批量用户访问

1. 在 `TaskControlBlockInner` 增加 rseq pending 状态，调度器在任务实际切出或迁核时置位。
2. 注册和 exec 后强制置位；signal delivery 触发 critical-section 检查。
3. 普通用户返回先判断 pending；未置位时直接跳过所有用户内存访问。
4. pending 路径在同一个用户访问上下文中完成两个相邻 32-bit store，并读取 `rseq_cs`。
5. 保留错误时 SIGSEGV/EFAULT 语义，不为了减少锁次数吞掉坏指针错误。

现有 rseq regression 只覆盖注册、重复注册、清理和注销；引入事件驱动后必须补充“无调度
的 syscall 不触发清理”“实际迁核会更新 ID”“信号会 abort critical section”测试。

### P2：保守的当前地址空间 uaccess fast path

在完整 exception table 之前，先做可控范围的优化：

1. 检查地址合法性和当前 `satp`/`MemorySet` 一致性。
2. 在不持有 `MemorySet` guard 时处理缺页、COW 和文件页准备。
3. 重新获取一次读锁，确认页表项 present、权限正确，并在单次 guard 内完成短小复制。
4. 使用 `SUM` RAII，保存并恢复原状态；不要无条件清除可能由调用者设置的 SUM。
5. 任何页未 present、权限不符、非当前地址空间或架构不支持时回退原软件翻译路径。

该方案仍会让大复制阻塞 VMA writer，因此只适合 rseq、时间结构、socket 地址等短小对象；
不能把它误称为 Linux 式无锁 bulk copy。

### P3：完整 `satp` + fault-safe uaccess

目标是仿照 Linux `raw_copy_to_user/raw_copy_from_user`：

- `access_ok` 只做用户地址边界和溢出检查；
- 架构汇编在 SUM 开启期间直接访问用户 VA；
- 允许的 S-mode load/store fault 进入可恢复 fixup；
- 缺页可调用 Ya2yOS 当前地址空间 fault handler，无法修复则返回 `EFAULT`；
- 当前地址空间 active-hart 与 remote-TLB frame retention 继续保证解除映射期间的帧生命周期。

实现前必须补齐 RISC-V 内核 trap frame 保存、异常表或等价的 per-hart fixup 表、`sepc` 重写、
剩余字节计数和错误返回。LoongArch64 需要使用其对应页表和用户访问权限机制，不能复制 RISC-V
`satp/SUM` 代码。

### P4：锁粒度和等待策略

只有 P0-P3 的工作量下降后，再评估：

- VMA 元数据锁与页表/PTE 锁分离；
- per-VMA 或 per-range resident-frame 元数据锁；
- 对 `spin::RwLock` 竞争增加指数 backoff，降低读者反复 `fetch_add/fetch_sub` 引起的缓存行抖动；
- 需要可阻塞等待时引入调度器可感知的 rwsem/等待队列，但不得在 remote-TLB ACK 关键路径引入新的锁序环。

Linux 的 `mmap_lock + VMA lock/Maple Tree + PTE lock` 是长期参考模型，不是当前现场的最小修复。

## 6. 并发和语义约束

### 6.1 remote-TLB 与 active-hart

首次无效 PTE 到有效 PTE 的安装可以避免全局 shootdown，但仍需执行当前 Hart 的本地 TLB
同步；其他 Hart 若缓存了 non-present translation，必须通过后续 fault retry 或明确的
shootdown 处理。present PTE 的 COW、权限修改、解除映射和可能回收旧帧的路径必须保留：

```text
UPDATE_LOCK -> MemorySet write lock -> 修改页表 -> remote shootdown/ACK -> 释放旧帧
```

任何直接用户 VA 复制都不能绕过 active-hart、帧保留和异常恢复协议。尤其不能在没有 fault
fixup 时假设“预先检查过 PTE，所以裸指针访问永远不会 fault”。

### 6.2 锁边界

- 文件页准备、EXT4 读取和可能阻塞的 cache 操作必须在 `MemorySet` 锁外完成。
- VMA 查找、页表修改和 resident-frame 所有权更新在短的地址空间临界区内完成。
- 不持有父地址空间读锁去获取 `UPDATE_LOCK` 或目标地址空间写锁；跨地址空间操作先制作 frame/metadata 快照。
- `ResourceSlot`、task/PCB、MemorySet 和 remote-TLB 的既有锁序不能因为 uaccess fast path 被破坏。

## 7. 观测与验证计划

初始现场阶段只做日志和源码分析；P0-P3 实现后应使用同一镜像、同一架构和同一
BuildStorm 参数继续记录：

1. `find_insert_addr` 调用次数、VMA 比较次数、最大扫描长度、递归/重试次数和 `areas.len()`。
2. `MemorySet` read/write lock wait/hold ticks，按 `mmap`、缺页、rseq、普通 copy 分类。
3. rseq 用户返回总次数、跳过次数、实际更新次数和 user-copy fault 次数。
4. `UPDATE_LOCK` 获取、shootdown target、ACK 和 active-hart 数量。
5. 宿主 wall-clock 与 BuildStorm 完成标记；不能用单次 timeout 或 Cargo 进度宣称加速。

建议验证顺序：

- RISC-V/LoongArch64 release 构建；
- rseq、mmap/mmap3/mmap18、mremap、COW 和多线程共享地址空间回归；
- RISC-V 8 Hart BuildStorm 同配置重复两次；
- LoongArch64 相同压力路径；
- 检查 `TPASS/TFAIL/TBROK/panic/SIGSEGV` 和最终 `shutdown!`。
