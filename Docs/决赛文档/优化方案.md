# BuildStorm 后续性能优化方案

> 版本：2026-08-09
>
> 适用源码快照：`f9554f6c74e37af7a9c69fc0e2fa948e9d5cec57`
> (`chore(perf):partition report output into module sections with banner headers`)；已包含
> `fc376373 perf(ext4): coalesce sparse write buffer ranges`。
>
> 证据来源：本次仍在输出的 `server.ans`。截至最后一个已分析快照
> `t=1382033ms`，BuildStorm 尚未完成，本文据此制定后续实施与验证顺序，不将中途

## 1. 当前结论

### 1.1 sparse run 合并已生效，但不是下一主攻方向

本轮已提交的 sparse range 合并能够把连续、重叠和 bridge 写合并为一个 run，同时
保持 hole 和 last-write-wins 语义。新旧主 sparse 工作量的 `batch_bytes` 都是
`285332888` 字节，因而可以对 run 形态做归一化比较：

| 指标 | 合并前 | 合并后 | 变化 |
| --- | ---: | ---: | ---: |
| `batches` | 7,634 | 7,593 | -41（-0.54%） |
| `batch_runs` | 236,719 | 235,379 | -1,340（-0.57%） |
| `run_limit_batches` | 7,363 | 7,321 | -42（-0.57%） |
| `payload_limit_batches` | 266 | 268 | +2 |
| 平均 `runs/batch` | 31.0085 | 30.9995 | 几乎不变 |

优化带来了真实但很小的收益：同样的 sparse payload 少产生约 1,340 个底层 run。
但是 run-limit batch 的占比仅从约 96.45% 降至约 96.42%，主压力段仍基本由
32-run 上限驱动。大多数写范围是彼此离散的，或可合并范围占比太低；继续扩展相邻
合并规则的边际收益预计很低。

正式 `BUILDSTORM_BEGIN` 后的首个短窗口显示，1,129 次 sparse buffer 写仅形成
25 个 run，11 个 flush 都由 payload 上限触发而非 run 上限。这验证了合并逻辑在局部
连续写模式下的有效性，但该窗口太短，不能代表此前的大规模离散写负载。

**决策：** 保留并回归验证现有 sparse 合并；在获得新的分布证据前，不提高 run 上限，
不继续扩展 sparse 合并逻辑，也不改变全局 sparse 预算。

### 1.2 当前直接热点是块设备排队和 EXT4 资源锁

最新 interval（`t=1382033ms`）的关键计数如下：

| 路径 | 观测值 | 含义 |
| --- | ---: | --- |
| `block_writes` | 14,847 | 近期写请求数量高 |
| block service | 29.10 s | 设备服务时间显著 |
| block wait | 12.30 s | 存在明确的设备队列等待 |
| resource lock contention | 366 | 共享 EXT4 资源发生竞争 |
| resource lock wait | 16.43 s | 锁等待已超过块设备排队等待 |
| resource lock hold | 72.87 s | 持锁区存在较长的并发累计工作 |
| `syscall_write` | 455 次 / 27.82 s | 写路径是当前可见长尾 |

这些数字是并发任务的累计 duration，不能彼此相加为 wall-clock；但它们足以确定排序：
下一轮应优先拆解 EXT4 锁临界区和 block request 生命周期，而不是继续微调 sparse
run 数量。

### 1.3 当前运行不能给出总加速比

`server.ans` 尚未出现最终 BuildStorm summary 或 `shutdown!`，因此不能报告完成时间、
通过状态或端到端百分比。当前工作树的 `user/src/bin/initproc.rs` 还启用了 nested QEMU
测例，整体工作负载与历史运行不同；即使本轮完整结束，也不能直接与未启用该测例的旧
墙钟时间做 A/B。

日志中当前未观察到 `panic`、`TFAIL`、`TBROK`、`BUILDSTORM_FAIL` 或 `ERROR`。这只说明
已输出区间未发现功能错误，不等同于完整回归通过。

## 2. 优化原则与边界

1. 先缩短共享锁临界区和减少无效 block request，再考虑提高缓存容量或批量阈值。
2. EXT4 的 inode、目录、rename/unlink/truncate、`fstat` 可见性和错误返回必须保持
   Linux 语义；不得以延迟元数据失效或永久缓存换取单次 BuildStorm 速度。
3. 不在持有 namespace、inode、journal 或 resource lock 时执行可避免的 block I/O、
   长时间等待、用户内存复制或大块临时分配。若必须释放锁后执行 I/O，必须通过版本号、
   inode 引用或重新校验保证对象没有失效。
4. block device 的 service 时间代表设备侧工作，软件只能减少请求数量、请求碎片和排队；
   不能把它误判为单纯调大队列深度即可解决。
5. `perf` 计数按阶段、按模块聚合。调试计数不得在热点逐请求打印，正式成绩运行须关闭
   高频串口报告。
6. 不在当前全量测试仍运行时启动构建、QEMU、Cargo 测试或修改 `disk.img`。以下实施与
   验证在维护者确认当前运行结束后进行。

## 3. 实施优先级

### P0：建立可比较基线并补足分解计数

**目的：** 将当前的“resource lock 等待”和“block wait”拆成可以归因到函数和请求形态的
数据，避免在错误层级优化。

1. 固定一组测试条件：源码 commit、`TARGET_ARCH`、Hart 数、QEMU 参数、测试镜像、
   `initproc` 测例开关、冷/热启动条件和 perf 开关。任何一项变化都创建新的基线，
   不与旧基线混算。
2. 在 `os/src/utils/perf/` 增加低开销聚合项，至少区分：

   | 对象 | 必需计数 |
   | --- | --- |
   | block request | 读/写、请求字节、扇区连续性、队列等待、设备服务、完成等待 |
   | EXT4 resource lock | 调用点类别、acquire 次数、contended 次数、wait、hold、最大 hold |
   | 写回 | sparse flush、dense write、metadata write、cache eviction、journal commit |
   | 锁内 I/O | 提交前、提交后等待、解锁后等待的次数与 duration |

3. 时长使用 tick 或已有 `perf` 时间源；只累计计数与分桶，不打印单个 inode、路径或
   block 编号。先确认 instrumentation 对无 perf 的正式运行没有影响。
4. 在日志中标记 BuildStorm 预构建、正式编译、嵌套 QEMU 测例和结束位置，使后续数据
   可按阶段截取。每个阶段只输出一次简要汇总。

**完成条件：** 能回答“哪个 EXT4 操作持有何种锁时让哪类 block request 排队”，并能用
同一阶段、同一工作量的计数比较改动前后，而不依赖总日志长度推断。

### P1：缩短 EXT4 resource lock 的临界区

**前置证据：** P0 显示某一类写回、元数据更新或 cache eviction 同时具有较高 lock hold
和 block wait，且该锁确实覆盖了可阻塞工作。

1. 沿写入、flush、cache eviction、truncate、close 与元数据提交路径审计 resource
   lock 的获取位置和释放位置，分别标注纯内存状态变更、I/O 提交和 I/O 等待。
2. 对可以两阶段执行的路径，在锁内完成一致性状态转移并保留必要的 inode/buffer 引用；
   在锁外执行块 I/O；完成后重新获取锁并以 generation/epoch/状态位校验结果。发生
   rename、unlink、truncate、写失败或并发 flush 时必须能回滚或重试，不能提交过期数据。
3. 若某类锁只是保护同一 inode，优先将全局 resource lock 分解为稳定的 per-inode
   保护，而不是改变全局锁序。若涉及目录或 journal，保持既有锁顺序并在代码注释中说明。
4. 针对高竞争类别增加窄回归：并发 append、重叠 `pwrite`、rename/unlink 与写回并发、
   `fstat` 可见性、ENOSPC/EIO 失败路径。

**验收指标：** 在相同工作负载中，目标类别的 lock wait/hold 和 block wait 均下降，且
block service 时间、错误率和最终文件内容不恶化。只降低 contention 次数但把 I/O 转移为
更长的重试循环，不视为成功。

### P2：减少 block request 碎片和队列堆积

**前置证据：** P0 证明 block wait 主要来自大量小写、相邻请求未合并，或同一调用者在
短时间内串行提交请求；若 service 时间占主导且请求已足够大，则不在内核侧盲目调度队列。

1. 以请求字节和连续性分桶，比较 sparse flush、dense write、metadata/journal write
   的平均与 p95 请求大小；同时记录“可相邻但未合并”的次数。
2. 在不跨越文件 hole、文件大小边界、设备边界、屏障或错误语义的前提下，合并同一提交
   批次中的相邻 block range。合并发生在 block 层或已有写回批次边界，不在 syscall
   层猜测跨文件顺序。
3. 将 I/O 提交和等待分离：可以安全并发的连续请求先提交，再按既有错误传播规则回收；
   不因并发化改变 `fsync`、close、rename 或 metadata 依赖的持久化顺序。
4. 只有当 P0 显示队列深度不足且 service 可并行时，才评估有限的 in-flight request
   上限调整；该实验必须设硬上限，防止内存膨胀和 resource lock 饥饿。

**验收指标：** 每写入 MiB 的 block request 数和 block wait 下降；同一 workload 的
block service 不明显上升；文件校验、异常注入和并发 rename/unlink 回归保持通过。

### P3：复核 sparse 写缓冲，但不扩大现有策略

现有 sparse run 合并是正确的低风险收益项，应先完成单元测试和实际 workload 验证：

1. 记录 flush 前 run 数分布、相邻/重叠合并命中次数、每个 batch 的 resident bytes，
   区分 payload-limit 与 run-limit 触发。
2. 对现有逻辑运行连续写、前向插入、重叠写、bridge 写、hole 保留、`truncate`、
   `fsync`、close 与写错误回滚测试；确认全局 sparse 预算在竞争路径中不漂移。
3. 仅在实际分布显示大量 batch 能因更大 payload 获益、且 P1/P2 后 I/O/锁时间没有反弹时，
   才做单变量的 512 KiB 与 1 MiB per-inode payload 上限实验。

**明确不做：** 不提高 32-run 上限作为默认改动，不把 hole 零填充为 dense buffer，不以
扩大 8 MiB 全局预算掩盖驱逐或锁竞争问题。

### P4：MM 和 remote-TLB 的独立回归方向

当前累积 remote-TLB 仍可观测，但在主 sparse 压力段并非最直接的增长源。该方向保持独立，
不与 I/O/EXT4 改动混在一个提交中：

1. 保持现有 local-only、remote-target、mailbox wait 和 ACK latency 分类。
2. 只在同一 syscall 连续页表更新可被证明语义等价时做 range shootdown 合并。
3. 必须维持 `UPDATE_LOCK -> MemorySet write -> ACK -> release old frame` 的生命周期；
   不能通过提前释放旧 frame 或漏发远端失效来换取性能。

**启用条件：** P1/P2 后 block wait 与 resource lock wait 已下降，但 BuildStorm 的 MM、
remote-TLB 或 mailbox wait 仍占主导。

## 4. 验证矩阵

当前全量测试完成后，按以下顺序验证；每次只改变一个优化项。

| 阶段 | 运行方式 | 目的 | 必须记录 |
| --- | --- | --- | --- |
| 0 | 静态检查、目标单元测试 | 先验证数据结构与错误语义 | 编译结果、单元测试结果 |
| 1 | 小型 EXT4 并发写回回归 | 验证锁外 I/O 与版本校验 | 文件内容、`fstat`、rename/unlink、错误路径 |
| 2 | 同配置 perf BuildStorm | 归因，不作为成绩 | P0 分解计数、阶段 marker、TPASS/TFAIL/TBROK |
| 3 | 同配置无高频 perf BuildStorm | 端到端比较 | guest 时间、宿主 wall-clock、完成标记 |
| 4 | 另一架构回归 | 排除架构相关退化 | RISC-V64 与 LoongArch64 的构建和关键测试结果 |

端到端实验至少保留同配置的冷启动和热启动样本；报告中给出每组原始时间、完成状态、
中位数和测试入口差异。只有测试镜像、`initproc`、Hart 数、QEMU 参数和性能开关完全一致，
才能计算加速百分比。

每轮日志均检查 `TPASS`、`TFAIL`、`TBROK`、`panic`、`ERROR`、`BUILDSTORM_*`、测试组
结束和 `shutdown!`。不以 wrapper 的单行 `FAIL LTP CASE ... : 0` 代替真实测试结论。

## 5. 建议的提交拆分

1. `perf(ext4): classify resource-lock and block request latency`
2. `perf(ext4): shorten writeback resource-lock critical section`
3. `perf(block): coalesce adjacent writeback requests`
4. `test(ext4): cover concurrent writeback visibility and errors`

每个实现提交单独附带对应回归或聚合计数，不将 P1、P2、P3 和 P4 混合提交。性能数字只在
完整、可比较的运行结束后写入开发日志或问题复盘；当前中途日志的结论仅用于确定优先级。
