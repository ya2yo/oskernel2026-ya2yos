# BuildStorm 优化方案

> 适用源码快照：`c72f46d0` 与本轮审计时的 `os/src/fs/ext4_lw` 过渡实现（2026-08-03）。本文只保留当前实现、
> 有效结论、下一步动作和验收边界；历史实验与故障取证见末尾问题记录。

## 0. 路线选择

### 0.1 当前资源锁替代了 `EXT4_OP_LOCK`

`22013868` 起，当前路径已**不再调用**挂载级 `EXT4_OP_LOCK`。C `struct ext4_fs` 将锁对象拆为 namespace、257 路
inode stripe、257 路 block-group stripe、super、journal 与 cache；Rust 以 C 锁地址为 key，把每个对象映射为可阻塞的
FIFO `TaskRwLock`。`VFileCache` 也拆开 data 与 flush/writeback 锁，竞争 task 不再在 C raw rwlock 上忙等。

这修复了 P21.3 中“持锁 task 被抢占，其他 hart 自旋并饿死 owner”的死锁条件，却**不等于磁盘 I/O 已并行**。资源锁放开后，
此前由全局 gate 节流的多份读写会同时抵达下列仍会汇聚的对象：

1. `Disk::dev`：单个 `spin::Mutex<BlockDeviceImpl>` 覆盖一整个同步请求及非对齐 RMW；virtio 块设备没有由此获得多队列
   或异步提交能力。
2. 合法的共享资源：namespace、super、journal、cache，以及同一 inode/group stripe 仍会串行，这是语义要求而不是
   `EXT4_OP_LOCK` 残留。
3. `LWEXT4_RESOURCE_LOCKS`：每次 C lock/unlock 仍需经过一个全局 `BTreeMap` 的 `spin::Mutex` 查找并 clone `Arc`。
   它只保护 Rust bookkeeping、不会跨 I/O 持有，但在高频锁路径上可能放大 SMP 开销；当前日志尚无它的 wait/hold 统计。

因此后续优化不得恢复 mount-wide gate，也不得直接撤掉 `Disk::dev` mutex。前者会掩盖而非消除队列问题，后者会破坏单个
virtio driver 请求与 RMW 的原子性。应先量化每类资源锁和设备队列，再决定是让设备等待可睡眠、合并/批量提交，还是修复
bcache 的脏块回收以减少请求数。

### 0.2 “真正 Linux EXT4”的工程定义

目标不是把 Linux C 文件逐行搬入 Ya2yOS；Linux 7.0 的 `fs/ext4` 依赖其 VFS `inode/file/address_space_operations`、
folio/page cache、bio、workqueue、`BUFFER_HEAD` 和 JBD2 的内部 ABI，直接移植既不可编译也不会自动正确。目标应是：
**实现 Linux 可识别的 ext4 on-disk format、Linux 可见 VFS 语义、JBD2 可恢复写入语义，以及 Linux 风格的资源级并发模型。**
没有 JBD2-compatible journal/recovery 的可写实现只能称为“ext4 格式子集”，不能称为真正的 Linux ext4 写路径。

下表是本地 Linux 7.0 源码给出的最小并发模型；其中“每文件系统锁”只对应特定 rename 拓扑操作，绝不等价于
`EXT4_OP_LOCK`：

| Linux 层次与源码证据 | Linux 的保护对象 | Ya2yOS 必须建立的对应对象 |
| --- | --- | --- |
| `Documentation/filesystems/directory-locking.rst:6-64`；`fs/namei.c:1926-1935,4574-4599` | 目录的 `i_rwsem`：lookup shared，create/remove exclusive。 | 可睡眠的 per-inode `rwsem`；inode 以 `(device, ino, generation)` 身份缓存，而非 pathname wrapper。 |
| `Documentation/filesystems/directory-locking.rst:53-64,137-161`；`fs/namei.c:3760-3820` | 跨目录 rename 才取得 `s_vfs_rename_mutex`，再以父目录优先、non-directory inode 地址序取得锁。 | 专用、可睡眠的 `rename_topology_mutex`，只包围跨目录拓扑判定；实现 parent/source/target 的固定锁序和死锁断言。 |
| `fs/ext4/ext4.h:1111-1123`；`fs/ext4/extents.c:4251-4269` | 每 ext4 inode 的 `i_data_sem`；只读 extent map shared，带 `CREATE` 的映射和 truncate exclusive。 | 每 native inode 的 data-map rwsem、extent status cache 与页/folio（或等价页缓存）锁；映射查询与分配必须分开。 |
| `fs/ext4/ext4.h:1564-1580,3561-3605` | 每 block group 的锁、per-CPU free counter 与 orphan lock；不以整个 mount 串行分配。 | block-group bitmap/descriptor lock、free inode/block 计数、预分配状态与 orphan-list lock；短临界区锁内不做 I/O。 |
| `fs/ext4/super.c:99-123`；`fs/jbd2/transaction.c:1820-1836` | operation 通过可嵌套 `handle_t` 进入 transaction；JBD2 分别保护 journal state/list 并在可恢复边界 commit。 | task-bound transaction handle、credit/reserve、metadata journal、ordered data writeback、commit/checkpoint 和 recovery；错误必须向 syscall 返回。 |

Linux 的 per-group 自旋锁只保护短临界区，且由 Linux 的 preemption/interrupt 规则约束；它不能成为 Ya2yOS 中可抢占 task
跨 C API busy-spin 的依据。Ya2yOS 的资源级锁若可能等待 I/O、内存分配、journal commit 或另一个 task，必须是可睡眠且可
取消/唤醒的锁；自旋锁只允许保护已验证的短元数据临界区。

### 0.3 兼容性边界与不变量

P22 的“完成”以 Linux 生成和检查工具能验证的行为定义，而不是以 benchmark 或删锁定义：

- 固定首个可写支持 profile（block/inode size、`extent`、`64bit`、`dir_index`、`metadata_csum`、`filetype`、
  `large_file`、extra inode size、journal checksum 等）；挂载时校验 incompat/ro_compat 位，不支持的 feature 显式拒绝，
  不得静默降级或写坏镜像。
- 同一镜像须可由 Linux `mke2fs` 创建、由 Ya2yOS 读写、再由 Linux `e2fsck -fn` 和 `debugfs` 检查；支持 journal 的
  可写 profile 必须以 JBD2-compatible journal 和 orphan recovery 通过掉电恢复，不能用“下次全盘扫描修复”代替。
- pathname lookup、open-file `f_pos`、hard link/unlink-open、rename、truncate、xattr、权限/时间戳和 `st_blocks` 的
  Linux-visible 语义由相关 LTP 和针对性并发/故障注入回归验收。
- 只有 native 挂载完成一整个可写 feature profile 的 ownership、锁序、恢复和磁盘检查后，才移除该挂载对 lwext4
  resource lock 的依赖；不允许按单个 C API “白名单绕过”来宣称 Linux 对齐。

### 0.4 证据范围与未验证点

本文 Linux 对照来自本机只读源码树 `/home/ya2yo/linux/linux-7.0`（`Makefile` 标识 `VERSION = 7`、
`PATCHLEVEL = 0`），关键证据已列于表 0.2。`directory-locking.rst` 明确给出 VFS 目录锁与 rename 锁的规则，
`ext4.h`/`extents.c` 明确给出 `i_data_sem` 与 block-group 锁，`super.c` 给出 buffered write、truncate、direct I/O
和 writepages 的锁序，JBD2 `transaction.c` 给出 handle 结束与 error 返回边界。这些是设计输入，不是 Linux
runtime lockdep trace，也不能替代 Ya2yOS 自己的并发验证。

尚未验证的点：首个 feature profile 的精确组合、Ya2yOS 上 JBD2 journal checksum/revoke 的互操作性、掉电注入点、
casefold/encrypt/bigalloc/inline-data/EA inode/fast-commit 等扩展 feature 的支持范围。它们必须先写入 P22.0 的显式矩阵；
未实现前一律 mount-time 拒绝，不能让测试镜像偶然通过后形成“已兼容”的错误结论。

## 1. 结论

当前内核已拆除 `EXT4_OP_LOCK`，但 `tmp_01.ans` 显示 BuildStorm 反而慢的首要原因是：锁拆分将并发 I/O 暴露给单一
`Disk::dev` submission mutex，而不是为 virtio 块设备提供了并行队列。末次 `t=545199ms` 快照中，`289759` 个请求已有
`38117` 次竞争，累计设备等待 `447649221us`，超过累计 service `386861701us`；最后 45.721 秒内单独又有 `3323` 次竞争和
`103106627us` 等待。它们是跨 task 的累计时间，不能相加为 wall-clock，却足以证明设备队列已经成为主要汇聚点。

同一快照还显示 bcache 在脏页压力下放大请求：`shake_full_dirty=397633`、`capacity_overflows=175994`、
`writeback_ops=17568`，而 256/128 dirty-capacity reclaim 仍为默认关闭。文件页缓存只使用 `51895/196608` 页且没有 eviction，
调度 dispatch 累计仅 `1272274us`；两者均不支持“先扩页缓存/先调 CFS”的假设。资源锁自身及其全局登记表没有 telemetry，
故不能从本日志断言 namespace、cache 或登记表是主导锁，只能将其列为待证伪的次级候选。

该样本在 RISC-V 8 HART 上从 `BUILDSTORM_TOOLCHAIN/MINIBUILD ok` 推进到 Cargo `Building 16/446`，未见 panic、
`ERROR`、`TFAIL`、`TBROK` 或 `SIGSEGV`，但没有 compile success、测试组 `END` 或 `shutdown!`。它证明退化方向和
瓶颈转移，不能与历史的不同 commit/缓存阶段作严格速度百分比比较，也不能证明资源锁语义已完整通过。

P21.2b.0 已用 sanitizer lifecycle oracle 验证当前已覆盖的 bcache intrusive tree/list/refcount 状态机，P21.2b.1 已将
cache-wide dirty flush 改为 bcache 内部的 claim/pin、锁外写回、统一 release。P21.2b.2 已实现为默认关闭的 dirty-capacity
256/128 blocks 高低水位实验：victim 只能经 bcache 内部 API claim/pin，I/O 在 index lock 外，成功写回后才丢弃 clean
buffer，失败保留 dirty。首次 P21.2b dirty victim 实验曾因 LRU RB tree `LoadPageFault` 回退，因此不得恢复由外部策略
直接 `RB_REMOVE`/`RB_INSERT` 的路径，更不能据此将 gate 改成 `RwLock`。

## 3. 有效证据

### 3.1 当前稳定基线

P21.2a 的 `log.ans` 有 `BUILDSTORM_TOOLCHAIN/MINIBUILD ok`，约 573 秒时到 Cargo `21/446`，没有 panic、
`ERROR`、`TFAIL` 或 `TBROK`；但没有 `BUILDSTORM_COMPILE ... ok=true`、测试组 `END` 或 `shutdown!`，
只能用于方向判断，不能报告端到端加速或回退比例。

末个完整累计快照满足：

- `get_ops=661695 = cache_hits 412142 + cache_misses 249553`；
- `loader_ops=249553 = successes 249553 + errors 0`；
- `writeback_ops=18515 = successes 18515 + errors 0`；
- `initial 16 + allocations 266818 - drops 266818 = resident 16`；
- `allocation_races=0`、loader/writeback wait 为 0、device contention 为 0。

同时出现 `shake_full_dirty=401664`、`capacity_overflows=181972`、`max_resident_blocks=1243`。这说明 16-block
bcache soft target 在 dirty-only 压力下不收敛；它不证明设备锁或 waiter 分桶是当前瓶颈，因为全局 gate 尚未撤退。

历史长样本中 `read/find/fstat/write` 的 gate wait 明显高于 hold，scheduler dispatch 仅占很小部分；文件页缓存也未
触及 192K 页上限。因此当前优先级是 EXT4 串行边界和 dirty bcache 生命周期，而不是扩大页缓存、预读窗口或调整 CFS。

### 3.2 P21.2b.0/P21.2b.1 阶段验证

新的 RISC-V 8 HART `tmp_12.ans` 有测试组 `START` 与 `BUILDSTORM_TOOLCHAIN/MINIBUILD ok`，在约
`t=175236ms` 的末次累计快照后仍未出现 panic、`ERROR`、`TFAIL`、`TBROK` 或 SIGSEGV。它没有
`BUILDSTORM_COMPILE ... ok=true`、测试组 `END` 或 `shutdown!`，因此只能证明已观察区间阶段稳定，不能报告完整
BuildStorm 通过或性能提升。

末次累计 bcache 快照满足：

- `538658 = 332749 cache_hits + 205909 cache_misses`；
- `205909 loader_ops = 205909 successes + 0 errors`；
- `13362 writeback_ops = 13362 successes + 0 errors`；
- `16 initial + 218541 allocations - 218541 drops = 16 resident`。

C block callback 的 read/write 请求分别为 `231256/17769`，总计 `249025`，submit 与 complete 全部相等且 error
为 0；device contention 为 0。相邻两个 interval 的 loader 和 read submit/complete 先后出现 `-1/+1` 的互补差异，
是 relaxed 分字段快照跨过一个在途请求；末次累计快照闭合，不作为错误计数。

容量压力仍未解决：`shake_full_dirty=353857`、`capacity_overflows=161383`、`max_resident_blocks=1243`。gate 同时
累计 `fast_acquires=35588`、`queued=6025`、`handoffs=6021`、`queue_depth=4`、`max_queue_depth=8`，handoff wait
累计 `81379237us`。这说明 lifecycle 修复未引入已观察到的正确性错误，但 16-block clean soft target 和 mount-wide
gate 仍分别造成容量失控与串行争用。

### 3.3 已回退实验

`tmp_11.ans` 在 P21.2b dirty victim 实验中触发 RISC-V `LoadPageFault`，`sepc=0xffffffc080369392` 定位到
`ext4_buf_lru_RB_REMOVE_COLOR`。实验代码仅凭 `refctr==0` 和一次 LRU 遍历就直接摘除、写回并重插 intrusive
RB tree 节点，没有证明 index ownership，故已完整回退到 P21.2a clean-only shake。该日志是正确性失败，不是性能样本。

### 3.4 P21.2b.2 两分钟 RISC-V 阶段验证

约 `t=114851ms` 的累计快照满足：

- `get_ops 367548 = cache_hits 200149 + cache_misses 167399`；
- `loader_ops 167399 = loader_successes 167399 + loader_errors 0`；

### 3.5 P21.3 shared admission 的 `tmp_13.ans`

新的 RISC-V 8 HART `tmp_13.ans` 有 `BUILDSTORM_TOOLCHAIN/MINIBUILD ok`，在 `t=283386ms` 后继续到 Cargo

该样本确认 shared admission 真正工作：`shared_acquires=39042`、`shared_handoffs=2224`、
`max_active_readers=7`。同时累计 gate handoff wait 仍为 `567915801us`，而读、find、metadata 和 write 的锁等待仍显著，
说明 writer 栅栏和长写事务仍是当前重点。`fstat` 的 sparse flush 计数为 6，且 fstat/recovery 可触发 `file_close()`；
因此它不能作为 shared 路径，后续代码已维持 exclusive，避免把实际写回错误归类成“读并发”。

### 3.6 P21.3 回退：C raw rwlock 与调度死锁

新的 `server.ans` 到 BuildStorm `tg-xtask` 并行预构建后不再推进；`client.ans` 的全 CPU GDB 栈显示 CPU 0/2/3/7
都在 `ext4_fs_rwlock_write_lock()`，分别由 pathname create/mkdir 调用，另四个 hart idle。没有持锁的 C 临界区栈，
排除常规漏 unlock，确认是持锁 task 被抢占后其它 task 的 C busy loop 吞掉所有 runnable CPU。

因此撤回 P21.3 shared admission，恢复 FIFO exclusive `EXT4_OP_LOCK`，并保留 exit cleanup。当前 `ext4_trunc_inode()`
还以 `journal_lock_held` 判断外层 transaction，修复无 on-disk journal 时的 journal self-deadlock。双架构 release 构建
通过；新内核以默认 16 GiB/8 HART 在 360 秒 timeout 前推进到 Cargo `15/446`（旧死锁样本约停在 `2/446`），无已观察到的
panic/TFAIL/TBROK/ERROR，但缺少完整结束标记，不能报告完整运行通过或性能数据。

### 3.7 P21.4 资源锁后的 `tmp_01.ans`：瓶颈转移到设备队列

当前 `tmp_01.ans` 是 RISC-V 8 HART 的资源锁版本。`BUILDSTORM_TOOLCHAIN/MINIBUILD ok` 后，最后可见进度为 Cargo
`Building 16/446`，末次 perf 快照为 `t=545199ms`；没有 `BUILDSTORM_COMPILE ... ok=true`、测试组 `END` 或 `shutdown!`，
也没有已观察到的 panic、`ERROR`、`TFAIL`、`TBROK` 或 `SIGSEGV`。它不是完整 A/B，不以 Cargo 个数推导严格加速率。

末次完整累计快照闭合：`289759 submits = 260645 read + 29114 write = 289759 completed`，且 read/write/device errors
均为 0。关键变化不是 I/O 错误，而是提交队列已经拥塞：

| 指标 | `t=70428ms` | `t=545199ms` | 含义 |
| --- | ---: | ---: | --- |
| `Disk::dev` contention | 0 | 38,117 | 拆除外层 gate 后，多 task 实际同时请求同一设备。 |
| device wait | 56,882us | 447,649,221us | 等待总和超过 service；它是跨 task 累计，不是 447 秒单任务停顿。 |
| device service | 34,523,009us | 386,861,701us | 单设备同步服务本身也是墙钟吞吐上限；最大单请求 service 达 366,895us。 |
| bcache `shake_full_dirty` | 128,067 | 397,633 | clean 目标无法回收时反复扫描，脏块并未形成稳定容量上限。 |
| bcache `capacity_overflows` | 92,384 | 175,994 | 仍按旧 16-block target 计数，证明默认 dirty-capacity experiment 没有运行。 |
| page-cache resident / max | 35,305 / 196,608 | 51,895 / 196,608 | 页缓存没有到容量上限，扩容不能解释或优先修复本轮退化。 |

`tmp_01` 还出现 `bcache` allocation races `422`、single-flight waits `2562`、writeback `17568`，以及
`1,344,560,640` bytes 的块 I/O。它们与“资源锁允许并行到达，16-block clean target 在 dirty workload 下造成额外读取/回写，
最终在单个同步设备上排队”的因果链一致。末个 45.721 秒 interval 单独有 `4982` 次请求、`3323` 次竞争、`103,106,627us`
device wait 与 `86,062,205us` service，也排除了仅由启动阶段累积造成的假象。

资源锁并非已被证明无开销：`resource_lock()` 在每个 C lock/unlock 上获取全局 `LWEXT4_RESOURCE_LOCKS`，且 `TaskRwLock`
内部使用 `BTreeMap` reader owner 与 `VecDeque` waiter。该缺口已由当前 staged 改动补齐：namespace/inode/group/super/journal/
cache-state/cache-flush 与 VFileCache 分别报告 wait/hold、队深和 registry lookup/create。新样本应将这些 interval 与
`Disk::dev` wait/service 对齐；若资源锁 wait 很低，优先处理设备队列和 bcache 脏块回收。

### 3.8 `tmp_09.ans` 的 namespace 争用与当前锁域收缩

`tmp_09.ans` 的分类锁统计中，namespace 累计 wait 为 `1,141,136,319us`，有 `4,515` 次竞争、最大单次
`121,672,904us`；最后一个 `t=514315ms`、168.879 秒 interval 独占 `679,046,748us` wait。该值是跨 task 的累计等待，
不是单个请求停顿，但足以表明 namespace 先于 inode/group 等类别成为下一处应消除的串行边界。

当前 staged 改动只将目标已由 `ext4_file` 确定的 `fread`、`fwrite`、`ftruncate` 与 `SEEK_DATA/SEEK_HOLE` 收缩为 inode
stripe；纯读 `fopen/fopen2` 不再进入 delayed write-back scope。创建、截断和 pathname namespace mutation 保持原锁域。
同时将 cache state 更新与归零后的长 write-back flush 分离为 `cache_lock` 和 `cache_flush_lock`。这些是锁域和观测改进，
尚无同 commit 的完整 BuildStorm/文件系统语义回归，不将它们表述为吞吐提升。

### 3.9 `server.ans/client.ans` 的任务表-堆锁死锁

最新 `server.ans` 在 TOOLCHAIN/MINIBUILD 后最后推进至 Cargo `Building 46/446`，并非 `38/446`。`client.ans` 显示 CPU#6
在 `TID_TO_TASK` guard 存活时因 `Vec::collect()` 扩容等待 `HEAP`，CPU#0 等待任务表锁，CPU#1 在 SIGKILL 线程组退出的
页帧释放中等待 `HEAP`。这与 lwext4 namespace 锁无关，却会停止定时维护和调度收敛，故必须先修复再比较 staged 文件系统优化。

修复恢复逐项无分配的任务遍历：仅在任务表锁内 `Arc::clone` 下一项，释放后才判断 hart、读取 PCB 和投递信号。它避免
`TID_TO_TASK -> HEAP` 的锁顺序，代价是每个任务一次短暂的任务表锁获取。该修复尚待带 musl 交叉工具链的 BuildStorm guest
验证，不能报告 `46/446` 后续已经完成。

ownership；只有 native 可写 profile 通过语义、并发、掉电恢复和磁盘检查，才能停止使用 lwext4。

### 4.1 P22-R：`lwext4_rust` 全 Rust 化实施方案

#### 4.1.1 目标、边界与不可采用的捷径

本方案的目标是最终删除 `crates/lwext4_rust/c/`、CMake/Make/musl 交叉编译依赖、bindgen 生成的 C ABI 和 C-owned
文件系统状态，同时保留 Ya2yOS 已经依赖的 Linux 可见行为。它不是把 21 个 C 源文件机械翻译成同样的数据结构，也不是
只把 `ulibc.c` 翻译为 Rust 后宣布完成。当前生产 C 核心约 19,336 行，包含路径与文件操作、extent、目录索引、inode/group
分配、bcache、journal、xattr、校验和以及并发状态；这些模块必须以同一 native mount ownership 和同一事务模型重建。

本计划适用源码快照为 `46c399fa`（2026-08-04）；现有 C 核心最近仍在修改 journal-full、checkpoint refcount、journal
callback 生命周期和 SMP 资源锁，因此先冻结过渡后端，再以可回退的 native mount 逐步切换。以下行为一律禁止：

- 使用 `c2rust` 作为最终实现。自动转换只能生成临时语义对照稿，不能替代 ownership、错误传播、锁序和事务设计。
- 在同一个**可写挂载**中混用 C inode/journal/bcache 与 Rust inode/journal/bcache。临时兼容只允许整个挂载按 backend
  选择，或对同一镜像先卸载、`e2fsck -fn` 后再由另一个 backend 打开。
- 在 journal 尚未实现前让 native 后端成为 rootfs 默认可写后端；无 recovery 的写路径只能标记为实验 profile。
- 为了通过单个 LTP 测例而静默忽略 ext4 `incompat`/`ro_compat` feature，或把数据损坏转换成“成功”。不支持的 feature 必须
  在 mount 阶段返回明确错误。

完成定义分为两个层次：`P22-R6` 表示首个可写 feature profile 已切换并通过语义、并发、恢复和磁盘检查；`P22-R7` 才表示
  仓库不再包含生产 C 文件系统代码。扩展 feature（fast commit、quota、ACL、casefold、encrypt、bigalloc、inline data、
  EA inode 等）不属于首个 profile，必须逐项增加并单独验收。

#### 4.1.2 最终代码边界

迁移期间继续使用 `lwext4_rust` crate 名称，避免一次性修改内核 Cargo 依赖；native 实现放在独立命名空间，旧实现收进
`legacy`，最后再删除。建议的目标目录如下：

```text
crates/lwext4_rust/src/
  api.rs                 Rust-only backend trait、公开句柄和稳定错误码
  blockdev.rs            KernelDevOp、请求边界检查和设备 flush
  perf.rs                backend-neutral 的 cache/journal/lock 统计
  legacy/
    ffi.rs               私有 bindings 与 C symbol 声明（P22-R1 后只由 legacy 使用）
    blockdev.rs          现有 C ext4_blockdev 适配
    file.rs              现有 Ext4File/C write-back 兼容实现
  native/
    mount.rs             feature profile、mount/unmount 和 superblock 生命周期
    ondisk/              endian 编解码、super/group/inode/dir/journal 结构
    checksum.rs          CRC32C、metadata checksum 和 journal checksum
    block_cache.rs       buffer pool、LRU/dirty/pin/loading/writeback 状态机
    inode.rs             `(device, ino, generation)` identity 与 inode 状态
    dentry.rs            pathname component、负缓存和目录 epoch
    extent.rs            extent tree 查找、修改、truncate 和 sparse hole
    directory.rs         linear/HTree lookup、entry mutation 和 rename topology
    allocator.rs         block/inode bitmap、group descriptor 和 ENOSPC 回退
    file.rs              open-file、f_pos、read/write/truncate 和 page cache
    journal.rs            handle/credit、descriptor/commit/revoke、checkpoint/recovery
    locks.rs              per-inode/group/journal/cache 可睡眠锁与 lock-order assertion
```

现有 `Ext4BlockWrapper`、`Ext4File`、`InodeTypes` 在迁移期作为兼容外观保留，但其内部必须通过 `api.rs` 的 backend
trait 调用；`os/src/fs/ext4_lw/` 不得继续读取 `bindings::ext4_*`。最终可将公开类型改名为 `Ext4Fs`、`OpenFile` 和
`Metadata`，但这属于 P22-R6 之后的 API 清理，不应阻塞核心迁移。

| `src/bindings.rs` | C layout、常量和 FFI 函数 | `api.rs`、`ondisk/*`、`error.rs` | 先移入 `legacy` 私有模块，移除 crate 外引用；P22-R7 删除文件，不手工维护新的 bindgen 输出。 |
| `src/file.rs`、`src/blockdev.rs` | Rust/C 适配、路径缓存、whole-file write-back | `legacy/*` 后逐项迁入 `native/file.rs`、`block_cache.rs` | 保留外观 API，禁止把旧 pathname cache 直接当 native inode cache；native identity 使用 inode generation。 |
| `src/perf.rs`、`os/src/utils/perf/fs.rs` | C/Rust 混合 telemetry | `perf.rs` 与 native cache/journal/lock 事件 | 保留指标含义和 aggregate 口径，替换底层事件源；A/B 必须使用同一指标定义。 |
| `c/lwext4/fs_test/`、`blockdev/linux`、`blockdev/windows` | 宿主测试、文件块设备、mkfs/mbr 工具 | Rust integration tests、fixture tool、`KernelDevOp` | 生产 native 切换后再替换；这些文件不属于当前内核静态库，但“全目录无 C”时也必须清理。 |

#### 4.1.4 阶段计划与退出条件

##### P22-R0：冻结契约与建立双后端基线

**目的**：先把现有 C 后端的行为、磁盘 profile、错误码和性能计数固定下来，避免重写过程中“语义漂移”却无法定位。

**策略**：不改默认生产路径；在宿主侧建立 C legacy 与未来 native 共用的 block-device fixture、镜像生成命令和结果比较器。
把已修复的 sparse、xattr、rename/unlink-open、journal-full、bcache 生命周期和 SMP 锁问题改写为 backend-neutral 测试。

**修改范围**：

- 新增 `crates/lwext4_rust/tests/` 的镜像 fixture、metadata/dirent/extent 解析断言和故障注入入口；测试不能依赖只读的竞赛
  testcase 源码。
- 新增 native profile 矩阵，记录 block/inode size、extent、64bit、dir_index、metadata checksum、filetype、journal
  checksum、xattr 和明确拒绝的 feature bits。
- 将 `src/perf.rs` 的 cache/block/lock 指标定义整理为与 backend 无关的事件名称；当前 C 指标保持兼容。
- 将 Linux `mke2fs`、`debugfs`、`e2fsck -fn` 命令和故障点写入测试脚本/文档，禁止用 QEMU 日志中的单个成功行替代镜像检查。

**退出条件**：同一镜像在至少两个架构使用 legacy 后端完成读写后，C/Rust-independent 检查器得到一致的 metadata、目录项、
extent 和错误码；基线至少有两次完整或明确记录未完成原因的 BuildStorm 运行，保留 `BUILDSTORM_COMPILE`、`shutdown!`、
`e2fsck -fn` 和 perf 原始结果。P22-R0 不宣称任何 Rust 性能或功能收益。

##### P22-R1：隔离 legacy FFI，建立 Rust-only 稳定接口

**目的**：即使 native 尚未可写，也先让 `os` 和未来 native 实现不再依赖 C 的结构体、常量和错误码。

**策略**：`legacy` 是唯一可以使用 `bindings.rs` 的模块；所有外部调用经 `api.rs` 的 Rust 类型。用兼容 adapter 保持现有
`Ext4File`/`Ext4BlockWrapper` 的调用形状，避免一次性修改 `os/src/fs/ext4_lw/` 的全部调用点。

**修改范围**：

- 新增 `api.rs`、`error.rs`、Rust `Metadata`/`DirEntry`/`FileType`/`OpenFlags` 和显式的 `BlockDevice` trait。
- 将 `src/bindings.rs`、当前 C FFI 声明、`src/ulibc.rs` 和现有 C 适配移动到 `src/legacy/`；`bindings` 不再从 crate 根公开。
- 重写 `os/src/fs/ext4_lw/{mod.rs,sb.rs,inode/*}` 对 `bindings::EOK/EIO` 及 C stat/layout 的直接引用，使它们只依赖 Rust
  API；`legacy` adapter 内部负责 errno 转换。
- 为 `Ext4BlockWrapper` 和 `Ext4File` 增加 backend 选择字段或类型参数，但不改变 legacy 的锁、缓存和 writeback 行为。

**退出条件**：`rg` 在 `os/` 和 native 代码中找不到 `bindings::`、`ext4_file`、`ext4_inode_stat` 等 C 类型的直接使用；legacy
后端的 mount、LTP 冒烟、RISC-V/LoongArch64 构建与已有 bcache oracle 保持原结果。这个阶段仍然需要 C 编译器，不能称为
全 Rust。

##### P22-R2：纯 Rust on-disk 只读核心

**目的**：在不承担写回和 journal 风险的情况下，先验证 Rust 对 Linux ext4 镜像的解析能力。

**策略**：所有 on-disk 类型使用显式 little-endian getter/setter；不把磁盘 block 直接转换为 Rust 引用，不使用未对齐的
`repr(C, packed)` 解引用。每个解析器返回受长度约束的 view 或拥有数据，并检查 magic、范围、checksum 和 feature。

**修改范围**：实现 `native/ondisk/`、`checksum.rs`、`mount.rs` 的只读路径，包括 superblock、group descriptor、inode、
目录项、linear/HTree lookup、extent 查找、软链接、xattr read、分区偏移和 sparse hole。`blockdev.rs` 只提供按 offset 的
完整请求，不承载路径或 inode 状态。

**退出条件**：Linux `mke2fs` 生成的多个 profile 可以被 native readonly mount 读取；普通文件、目录、软链接、extent、
稀疏 hole、xattr list/get、权限/时间戳和 `st_blocks` 与 legacy、`debugfs` 结果一致；并发只读压测没有数据竞争或锁序违规。
该阶段不允许 create/write/truncate/rename，也不能覆盖 legacy rootfs。

##### P22-R3：native inode、目录缓存、页缓存和可睡眠锁

**目的**：将当前 Rust 侧容易与 C 状态交错的 pathname wrapper/cache 改为 native inode ownership，为后续写入和并发提供
正确的状态基础。

**策略**：先在 native readonly mount 中启用 `(device, ino, generation)` identity、dentry/name cache、独立 open-file `f_pos`、
per-inode/group/journal/cache 锁和 page/buffer cache；锁等待必须可以阻塞、取消和在 owner exit 后清理。缓存索引锁不得跨设备
I/O、journal commit、内存分配或任务等待。

**修改范围**：新增 `native/inode.rs`、`dentry.rs`、`file.rs`、`block_cache.rs`、`locks.rs`；将 `src/perf.rs` 和
`os/src/utils/perf/fs.rs` 的事件改接 native backend。现有 `VFileCache` 仅作为 legacy 专用实现，不能直接复制为 native 的
inode cache；`os/src/fs/ext4_lw/inode/` 增加 backend-neutral 适配，但默认仍选择 legacy。

**退出条件**：多 task 同/异目录 lookup/open/close、同 inode 并发读、跨目录 rename 的锁序探测通过；任务取消、owner exit、
cache eviction、page fault/EOF 和 mmap 只读场景没有 stale alias、死锁、UAF 或内存泄漏。native 只读 BuildStorm/LTP 冒烟通过，
但写入和 journal 仍明确拒绝。

##### P22-R4：native metadata 与非 journal 写入实验

**目的**：替换 inode、目录、extent 和 bitmap 的写路径，验证 Rust 内存状态与 ext4 磁盘状态的双向一致性。

**策略**：先做一个只用于 scratch image 的实验 profile，所有 mutation 使用显式 transaction-like rollback guard，但不把它
描述为 Linux 可写 ext4。每次写入按 metadata block 记录 before/after，错误路径必须撤销内存计数和缓存状态；禁止无事务地
把该 profile 作为 rootfs。

**修改范围**：实现 `native/allocator.rs`、extent 写时分配/释放、inode mode/owner/time、directory create/mkdir/unlink/
rmdir/link/rename、truncate、xattr set/remove、free count 与 `st_blocks` 更新；`native/block_cache.rs` 增加 dirty/pin/loading/
writeback 状态机和批量请求；`os/src/fs/ext4_lw` 仅增加 feature/profile 选择，不改 legacy 默认。

**退出条件**：单线程和受控并发的 metadata 操作与 legacy 结果一致，Linux 可挂载/读取结果，操作后 `e2fsck -fn` 无差异，
`ENOSPC`、短 I/O、设备错误和回滚测试均通过。任何未经过 journal 的写 profile 只能显式挂载为实验模式；出现 orphan、目录项
丢失、link count/free count 漂移时立即回退到 P22-R3。

##### P22-R5：native JBD2-compatible journal、checkpoint 与 recovery

**目的**：完成从“可写 ext4 子集”到可恢复 ext4 写路径的关键替换，消除 C `ext4_journal.c`、`ext4_trans.c` 和相关 C bcache
生命周期对 native mount 的依赖。

**策略**：以 task-bound transaction handle 表达 credit、nested start/stop、abort 和 owner；明确 descriptor/data/revoke/
commit 的空间分配、checksum、ordered data writeback、checkpoint、orphan list 和 mount recovery 状态机。journal commit、
设备 I/O 和内存回收均不能在不允许睡眠的锁内执行；错误必须返回至 VFS/syscall，不得 assertion spin 或吞掉错误。

**修改范围**：实现 `native/journal.rs` 以及 `native/ondisk/journal.rs`；把 `bcache` 的 dirty buffer pin、checkpoint retain/release、
writeback callback 和 single-flight wait 统一为 Rust ownership；增加 fault injection：journal 满、descriptor 分配失败、
commit 中断、checkpoint 延迟、writeback error、mount recovery 和 owner exit。

**退出条件**：每个 create/rename/truncate/allocate/unlink 阶段的强制掉电镜像都能由 native mount recovery 恢复，并能由 Linux
`e2fsck -fn`/`debugfs` 检查；同一镜像可由 Linux 生成、Ya2yOS native 写入、Linux 重新挂载；journal abort 的错误码、orphan
回收、mtime/ctime 和 dirty page 可见性通过文件系统 LTP。未达到这些条件前，不允许删除 legacy journal。

##### P22-R6：按完整 profile 切换 native backend

**目的**：将首个已验证的 native 可写 profile 接入 Ya2yOS 默认文件系统，但保留可回退的 legacy backend。

**策略**：按 mount/profile 选择 backend，不按单个 API 混用。切换前先关闭同一镜像的 legacy 引用，确认所有 open file、page
cache、journal handle 和 delayed write-back 已完成；失败时只回退整个 mount，不保留部分 native 状态。

**修改范围**：`os/src/fs/ext4_lw/{sb.rs,mod.rs,inode/*}` 使用 `api.rs` 的统一接口；移除 native 路径上的 `EXT4_OP_LOCK`、
`LWEXT4_RESOURCE_LOCKS`、C lock hook 和 C bcache callback；把 `perf` 指标映射到 native cache/journal/lock 事件；补充 mount
option、unsupported feature 和 recovery 失败的用户可见错误。

**退出条件**：RISC-V 与 LoongArch64 构建、文件系统 LTP、8 HART 并发压力、BuildStorm 两次完整 A/B、Linux 回读与恢复、
`e2fsck -fn` 全部通过；日志同时出现 `BUILDSTORM_COMPILE mode=multi ok=true`、测试组 `END` 和 `shutdown!`。性能结果必须与
legacy 在同镜像、同 QEMU 参数、同缓存状态下比较，不能用不同 commit 或未完成日志报告收益。

##### P22-R7：删除 C 构建链和 legacy 源码

**目的**：让“全 Rust 化”在仓库和构建环境上真正闭环，而不只是 native backend 默认启用。

**策略**：在 R6 的退出条件满足后一次性清理 C 入口，先用静态搜索和干净构建确认没有隐藏引用，再删除生产和宿主辅助 C。
删除动作必须保留可恢复提交，不能在未验证的工作区中直接批量清理。

**修改范围**：

- 从 `Cargo.toml` 删除 `links = "lwext4"` 和不再需要的 `build = "build.rs"`；删除 `build.rs` 中的 CMake、Make、archive、
  musl toolchain 和 bindgen 逻辑。
- 删除 `src/legacy/`、`src/bindings.rs`、`src/ulibc.rs` 及所有 C symbol 声明；将 `perf`、错误码和 metadata 类型固定为 Rust。
- 删除 `c/lwext4/src`、`include`、`ulibc.c`、`wrapper.h`、CMake/Make/patch、Linux/Windows blockdev 和 C fs_test；后者虽不
  进入当前静态库，也必须由 Rust host integration test/fixture tool 取代，才能满足目录无 C 的目标。
- 清理 `target`/archive 复用假设，保证无 musl C 交叉编译器时 `cargo build` 仍能完成；更新 README、文档中的 C 依赖和构建命令。

**退出条件**：`rg -n '\\.c|bindgen|lwext4.*\.a|CMAKE|musl-generic|bindings::|extern "C"'` 只命中历史文档或明确的
第三方说明，不命中生产源；干净环境下 RISC-V/LoongArch64 `make` 不需要任何 C 交叉编译器；native 的 host oracle、双架构
LTP/BuildStorm、Linux 回读、journal recovery 和 `e2fsck -fn` 全部保持 R6 结果。

#### 4.1.5 阶段依赖、回退点和并行工作

主依赖链为 `P22-R0 → P22-R1 → P22-R2 → P22-R3 → P22-R4 → P22-R5 → P22-R6 → P22-R7`。其中 P22-R0 的镜像/差分
测试可以与 P22-R1 的 API 隔离并行；P22-R2 的 checksum、on-disk parser 和 P22-R3 的锁模型可以并行开发，但必须在
同一 native mount 合入前完成接口评审。P22-R4 与 P22-R5 不得并行切换到生产写入：前者的 rollback guard 会被后者的
journal ownership 替代。

每阶段只允许回退到上一个已验证阶段：R2 失败回退 legacy readonly，R4/R5 失败保留 native readonly 并关闭实验写 profile，
R6 失败按整个 mount 切回 legacy。不得仅替换一个 C API、一个 cache 层或一个 journal callback 来声称阶段完成。阶段状态、
支持 feature、未验证项和当前默认 backend 必须同时记录在 `优化方案.md` 和开发日志中。

#### 4.1.6 性能与维护性验收

全 Rust 化的第一目标是可验证的维护边界和内存/生命周期安全，不预设语言转换必然加速。每个 R 阶段都必须保留同定义的
`ext4_reads`、cache hit/miss、buffer load/wait、dirty writeback、journal commit/checkpoint、resource lock wait/hold、
设备 request submit/complete 和 wall-clock 指标。native 实现禁止在 4 KiB 热路径反复创建 `String`/`Vec`、为每个 buffer 单独
分配内存或用 mount-wide `Mutex` 代替资源锁。

R6 的 A/B 至少覆盖顺序/随机 4 KiB I/O、open/stat/close、create/unlink/rename、大目录、sparse、xattr、journal-heavy
写入和 BuildStorm；同一配置至少运行两次，并同时检查功能结束标记和 `e2fsck -fn`。若性能下降，先按 telemetry 区分设备
队列、cache 命中、journal flush、锁等待和 Rust allocator，再决定优化，不允许以删除一致性检查、减少 flush 或放宽锁序换取
数字上的吞吐。

维护性验收还包括：新增一个 filesystem operation 时只需修改 `api.rs`、native backend 和对应测试；`os` 不再接触磁盘布局
或 C ABI；所有跨层错误使用 `FsError` 显式传播；每个 on-disk feature 都有支持/拒绝测试；legacy 删除后不保留第二套隐式
缓存或事务实现。只有同时满足这些条件，才能把“换成 Rust”定义为降低维护难度，而不是单纯改变实现语言。

## 5. 正确性约束

- lwext4 仍在使用时，所有 C 资源访问必须经 task-aware resource lock hook；不得恢复 C raw rwlock busy-spin，也不得以
  `EXT4_OP_LOCK` 重新覆盖全部 API 来掩盖下层队列。native EXT4 与 lwext4 不能在同一可写挂载上交错读写；迁移必须以
  挂载/profile 为 ownership 边界，或在 legacy 挂载不写时仅做 native readonly。
- native 锁序以 Linux 目录锁规则为基线：跨目录 rename 的 topology mutex 在所有 inode lock 之前；目录 parent 先于
  child；两个 non-directory inode 按稳定 `(device, ino)` 序；每 inode 的 data-map lock 只覆盖 extent/map-truncate
  关系。不得把 mount-wide mutex 伪装为普通 read/write 的并发方案。
- 不得持有 cache index spinlock 或 block-group short lock 等待设备 I/O、task mutex、journal commit 或内存分配；
  transaction handle、页锁和可睡眠 rwsem 的嵌套必须有 lock-order assertion 和相应的错误退出路径。
- 不牺牲 quota reserve/rollback、ENOSPC 小块回退、sparse overlay、`st_blocks`、mtime/ctime、rename/truncate/
  unlink/write 的 cache 失效和 mmap EOF/SIGBUS 语义。
- bcache 容量策略不得在运行时销毁重建 cache，也不得由外部策略直接操作 intrusive tree/list。
- `BC_WRITEBACK` 只表示 I/O 状态，不能替代对象生命周期引用；生产路径离开 index/list 保护域调用
  `ext4_block_flush_buf()` 前必须持有 refcount pin，并在 callback 与状态清理完成后统一 release。
- P21.2b.2 reclaim 在成功写回后只能释放 claim pin 并丢弃最终为 clean 的对象；I/O 失败必须恢复 dirty membership，
  不得在同一次 release 中递归重试。资源锁版本的容量上界按 `high + in_flight_loaders` 验收，而非误读旧 16-block
  `capacity_overflows`。
- 未出现完整结束标记时，只能报告方向性计数；跨任务累计 wait/hold 不能相加为 guest wall-clock。
- 任一阶段出现 stale read、错误 LBA、目录项丢失/重复、free count 漂移、journal abort、panic、死锁或 fsck 差异，
  立即关闭新路径并回退到上一个已验证阶段。

## 6. 验收

静态与双架构构建：

```bash
cargo fmt --manifest-path os/Cargo.toml --all -- --check
git diff --check
make TARGET_ARCH=riscv64
make TARGET_ARCH=loongarch64
make perf TARGET_ARCH=riscv64
make perf TARGET_ARCH=loongarch64
```

行为与并发回归至少覆盖：同/异 LBA、I/O error、64+ resource/device waiter 和 owner 退出；read/write/stat/rename/truncate/
unlink-open-close/fsync；mmap 尾页、越界页、并发 truncate；容量 feature；RISC-V 8 HART；涉及共享 C 代码时补
LoongArch64 冒烟和 `e2fsck -fn`。

每个 P22 native profile 另须准备三类独立镜像：Linux `mke2fs` 新建的基线镜像、Ya2yOS 完成随机 namespace/data
操作后的回读镜像、在 create/rename/truncate/allocate/journal commit/checkpoint 各阶段强制掉电后的恢复镜像。三类镜像
均须由 Linux `e2fsck -fn` 和 `debugfs` 检查；只读 profile 也必须验证 unsupported feature 的拒绝路径。并发验收须
同时覆盖同目录与异目录操作，cross-directory rename，以及读取 extent 与并发 allocate/truncate，不能只使用单线程 fsck。

性能结论必须使用同一环境至少两次完整运行，并同时出现：

```text
BUILDSTORM_COMPILE mode=multi ok=true elapsed_s=<...>
#### OS COMP TEST GROUP END buildstorm ####
shutdown!
```

常用日志提取：

```bash
rg -a -n "BUILDSTORM|shutdown!|panic|TFAIL|TBROK|ERROR|SIGSEGV|QEMU: Terminated" log.ans
rg -a -n "^\[perf\] (t=|interval_ext4|ext4_bcache|ext4_block|file_cache|scheduler_duration)" log.ans
strings log.ans | tail -240
```
