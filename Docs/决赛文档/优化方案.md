## 1. 当前结论

### 1.1 `tmp_02.ans` 当前基线（2026-08-02）

- 这是 RISC-V `riscv-virtio,qemu`、8 HART 的 BuildStorm 样本。日志只确认
  `BUILDSTORM_TOOLCHAIN ok` 和 `BUILDSTORM_MINIBUILD ok`，末尾 guest 时间为 `t=593195ms`（约 9.9 分钟），
  Cargo 到 `Building 40/446`；没有 `BUILDSTORM_COMPILE`、测试组 END、`shutdown!` 或 `QEMU: Terminated`。
  因此它是未完成的方向性样本，不是端到端成绩。
- 约 `t=95881ms` 的 interval 首次出现 gate 排队：`queued=3064`、`handoffs=3064`；
  `t=169103ms` 已累计 `queued=6568`、`handoff_wait_us=208632388`。末尾累计公平 gate 为
  `queued=36660`、`handoffs=36658`、`cancelled=0`、`queue_depth=2`，守恒闭合；但
  `handoff_wait_us=2115644661`（约 2115.6 秒）、`max_handoff_wait_us=16650130`（约 16.65 秒）、
  `wait_ge_10s=8`，说明 FIFO 交接没有丢唤醒，吞吐却被长事务和高并发等待拖慢。
- 末尾锁分类的等待/持有累计为：`ext4_read_lock=600.824s/56.811s`（33493 次）、
  `ext4_write_lock=936.287s/71.806s`（25282 次）、`ext4_find_lock=246.151s/72.252s`（13161 次）、
  `ext4_fstat_lock=71.766s/28.050s`（1716 次）。读数据锁等待 `584.879s`、写数据锁等待 `438.269s`，
  优先级明显高于 quota（`ext4_write_duration quota=0.015s`）。这些是跨任务累计值，不能与 593.195 秒 guest
  wall-clock 相加。
- 文件页缓存在整个样本中没有触顶：末尾 `resident_pages=63298/196608`、
  `capacity_bypass_pages=0`、`evictions=0`。mmap 来源为 `mmap_cache_fill=21175` 次/约 202.8 MiB，
  page-cached cold run 为 `10590` 次/约 110.6 MiB，只有 58 次 direct bypass；本轮没有为 P19A 提供容量压力证据。
  `load_races=404` 需要保留为一致性观察项，但不能据此调高容量或预读窗口。
- syscall 累计时间也与 gate 争用一致：`read=693.278s`、`write=1008.762s`、`open=304.795s`、
  `stat=426.208s`、`path=285.969s`。`pipe_read_wait=825.329s/162`（最大约 24.8 秒），而
  `scheduler_dispatch=2.168s/466943`，因此调度器不是下一轮主目标；管道等待先做生产者/消费者归因，不能直接当作
  内核锁瓶颈。

### 1.2 `tmp_03.ans` 一小时停滞证据（2026-08-02）

- 这是同一 RISC-V、8 HART 配置的约 55.4 分钟样本。日志仍只有
  `BUILDSTORM_TOOLCHAIN ok` 和 `BUILDSTORM_MINIBUILD ok`，没有 `BUILDSTORM_COMPILE`、测试组 END、
  `shutdown!`；末尾为 `QEMU: Terminated`，没有 panic、TFAIL、TBROK 或 SIGSEGV。因此它证明的是未完成运行中的
  停滞，不是完整成绩或单独的功能失败。
- `t=3021715ms` 的最后一个有实际 syscall/EXT4 进展的窗口中，gate interval 为
  `queued=235/handoffs=229/queue_depth=6`，同时主分类 interval 已很小；到 `t=3075042ms`，syscall 仅从
  `959019` 增至 `959050`，所有 `interval_ext4_lock` 和 `interval_ext4_gate` 的新增计数都为 0，队列仍为 6。
  之后只有 idle scheduler interval，末尾又有一个 waiter 到达 7。
- 累计 gate 为 `queued=46288`、`handoffs=46281`、`cancelled=0`、`queue_depth=7`，满足
  `queued = handoffs + cancelled + queue_depth`。这排除了简单的票据丢失，但不能解释为什么队首长期无法获取；
  公平 handoff 计数的守恒不等于 owner 生命周期已正确闭环。
- 页缓存仅 `resident_pages=85486/196608`，`capacity_bypass_pages=0`，所以本轮不继续调容量、CLOCK 或预读。
  重点转为 gate 的 owner 生命周期和唤醒链：发散的 `exit_current_and_run_next()` 不保证活跃
  `Ext4OpGuard` 执行 `Drop`，旧退出清理只移除排队票据，可能留下 `held=true` 并永久阻塞后续 waiter。
  这是与代码路径一致的待证伪假设，不是由 `tmp_03` 单独证明的唯一根因。

### 1.3 与历史长样本的关系

- 先前的 `riscv.ans` 确实在 `resident_pages=98304/98304` 后出现大量 capacity bypass，这仍是 P19A 的安全性和满载压力
  验收依据；但 `tmp_02.ans` 在同一生产容量下未触顶，不能把两份运行的 crates/min 或 wall-clock 直接比较。
- 下一轮主线从“继续调页缓存容量”切换为“先解释 EXT4 gate 持有时间和等待来源，再做单一长 transaction 优化”。
  不撤销 FIFO gate、不放宽 lwext4 单线程约束，也不恢复正向 dentry fast path；rename re-key 和目录 epoch 仅在新的
  interval 证据重新占主导时推进。

### 1.4 `tmp_08.ans` 正确性失败（2026-08-02）

- 该样本在 Cargo `17/446` 附近出现 `can't find crate for unicode_ident` 和
  `can't find crate for scopeguard`，随后 `lock_api`/`proc-macro2` 编译失败。它没有完整 BuildStorm 结束标记，不能
  作为性能回归或加速证据。
- 失败发生在尝试让 rename 跳过 dense byte-cache 写回之后：缓存虽然不再立即写回，但新路径的 read、mmap backing
  read 和 `stat.st_size/st_blocks` 可见性没有同时闭合，Rustc 可能读到旧路径或不完整 artifact。该路径已补齐，具体
  根因与边界见 [Rustc artifact rename 写回问题复盘](./problem/buildstorm-rustc-artifact-rename-writeback.md)。

### 1.5 `tmp_09.ans` 当前方向性结果（2026-08-02）

- 修复后没有 `E0463`、panic、`TFAIL` 或 `TBROK`，同一阶段在 `t=568432ms` 到达 Cargo `33/446`；对照
  `tmp_07` 的 `t=593868ms`、`33/446` 提前约 25.4 秒（约 4.3%）。两份日志都未出现
  `BUILDSTORM_COMPILE`、测试组 END 或 `shutdown!`，因此这里只记录方向性收益，不报告端到端成绩。
- `write_duration data` 从 `218.317s/11140` 降至 `157.263s/12429`，最大单次从 `28.060s` 降至 `11.793s`；
  gate `handoff_wait_us` 从 `1832.606s` 降至 `1627.724s`，最大等待从 `28.357s` 降至 `15.749s`。这些累计值
  跨任务相加，不能当作 guest wall-clock 的分解。
- 代价和残余风险也必须保留：sparse buffer 峰值由约 `1.04 MiB` 增至约 `2.05 MiB`，`open/stat/path` 累计时间
  偏高，仍有 `wait_ge_10s=12`。`ext4_rename_write_back ops=0` 只表示当前计数器没有覆盖 dense cache migration，
  不表示运行中没有 rename；后续必须增加迁移专用计数器。

### 1.6 `riscv.ans`：`EXT4_OP_LOCK` 是首要瓶颈，但当前不能直接拆锁（2026-08-02）

- 在该 RISC-V 长样本中，Cargo 从 `t=96.102s` 的 `Building 3/446`，到 `142.170s` 的 `7/446`、
  `284.329s` 的 `19/446`、`484.509s` 的 `36/446`、`665.036s` 的 `46/446`，`951.470s` 时仍为
  `47/446`，最终由外层终止。末尾累计 `ext4_read_lock` 等待/持有为 `920.801s/55.796s`，
  `find=537.213s/108.115s`，`fstat=298.752s/48.965s`，`write=700.074s/151.132s`；公平 gate
  `queued=18773`、`handoffs=18768`、`handoff_wait_us=3151655657`，单次最长 handoff 等待约 69 秒。
  这确认挂载级串行化是当前后段吞吐的首要内核瓶颈。
- 这不等于可将 `EXT4_OP_LOCK` 按 read/find/fstat/write 替换成四把锁或一个 `RwLock`。当前每 inode 的
  `io_state`/`write_state` 只保护 Rust `Ext4File` descriptor 与缓存状态；lwext4 同一 mount 仍共享
  `ext4_bcache` 的 LBA/LRU/dirty 索引、`cache_write_back` 计数、超级块/位图与单一事务状态。`ext4_fread()` 和
  `ext4_fwrite()` 本身也将整段块映射、direct block I/O、cache write-back 和 transaction 包在一个 mount lock
  中。外层 gate 是这些 C 状态在当前 wrapper 中唯一明确的 SMP 边界。
- lwext4 确有 `ext4_mount_setup_locks()`，但接口只是每挂载一对无上下文的 `lock()/unlock()` 回调；当前 Rust
  wrapper 未注册它。即使仅把 `EXT4_OP_LOCK` 搬进该回调，`ext4_fread()`/`ext4_fwrite()` 仍会整段取得同一 mount
  mutex，性能不会获得并行读；外层与回调锁并存还会形成嵌套死锁风险。它可用于收敛“所有 C API 必须被锁住”的
  责任，不是拆锁方案。
- 块设备适配也尚不具备并发前提：`Ext4BlockWrapper` 的 `bdif.lock/unlock` 为 `None`，而 `dev_bread()`/
  `dev_bwrite()` 对同一个 `Disk` 裸取 `&mut`，以可变 position 执行 `seek + read/write`。若 C API 并发进入，
  两次 seek 与 I/O 可以交叉到错误 LBA；因此至少须先让单次块 I/O 原子化，不能仅从 VFS 层放锁。
- Linux ext4 的做法不是一把“读锁”。它将同步分层：VFS 的 `inode->i_rwsem` 支持共享读/互斥写，目录操作用父目录
  inode 锁，仅跨目录 rename 取得 `s_vfs_rename_mutex`；ext4 另用每 inode `i_data_sem` 协调 truncate 与 block
  mapping，并以短时 superblock/allocator/journal 锁保护 orphan、block group、writeback barrier 与 fast-commit
  队列。普通 buffered read 走页缓存，写回和 journal commit 可与别的 inode 工作交叠；只有冲突对象或必要元数据
  被串行，而不是整挂载的所有 path/file 调用。
- 因而“真正拆锁”是 lwext4 的 SMP 化项目，不是本轮性能调优：需为 bcache、块设备、inode data、目录 namespace、
  block-group allocator 和 journal transaction 分别定义所有权、锁粒度与全局锁序，并补并发 create/rename/
  unlink/truncate/fsync、断电恢复和文件系统一致性回归。在没有这些基础前，优先级仍是 cache 命中绕过、去除重复 gate
  准入、缩短已经证实的 C 临界区，以及通过计数定位 bcache flush，而非放宽 lwext4 进入条件。

## 3. 不变约束

- EXT4_OP_LOCK 继续串行化所有 lwext4 block cache 与 path/file C API；不改 rwlock，不允许多 hart 并发进入 lwext4。
- lwext4 当前编译的 `CONFIG_BLOCK_DEV_CACHE_SIZE=16`；`ext4_config.h` 中的 8 只是 fallback。日志尚没有
  bcache hit/miss/shake/dirty-flush 直接计数，故 bcache 抖动是高可信结构性放大因素而非已单独证实的根因；不能在
  运行时重建缓存，若后续 A/B 证明它主导，只能通过 CMake 编译期配置安全地扩大。
- `ext4_mount_setup_locks()` 只提供一个 mount-wide callback mutex，迁移到该接口不产生读并发；不得同时持有它和
  外层 `EXT4_OP_LOCK`。未完成 lwext4 bcache、journal、allocator、namespace 和 block-device 的 SMP 改造前，
  禁止把 gate 拆为 read/find/fstat/write 锁或改为 `RwLock`。
- 保持锁序简单：write_state -> io_state -> EXT4_OP_LOCK；不得在持有 MNT_TABLE 时获取 EXT4_OP_LOCK，也不得反向嵌套。
- P9 保持 32 MiB 文件准入、四页预读与 192K 页经验容量；当前优化对象是满载后的安全回收与候选退避，而非继续调
  `MAX_FILE_PAGE_CACHE_PAGES`。任何改动都必须同时证明没有 OOM、旧数据、SIGSEGV/SIGBUS 或脏页丢失。
- 不牺牲文件系统语义：quota reserve/rollback、ENOSPC 小 chunk 回退、sparse overlay、st_blocks、mtime/ctime、
  rename/truncate/unlink/write 的 cache 失效必须保持。
- 未出现完整结束标记前，所有定时样本只可用于方向性取证，不能报告端到端加速。

## 4. P19A/P19B/P19C/P20 与下一轮计划

### P15：目录 epoch 仅补语义回归，不再作为吞吐主线

1. `tmp_04` 已覆盖父目录局部更新分支：`local_updates=884`、`global_fallbacks=0`，且
   `global_epoch_miss=96`。该结果支持 P15.1/P15.2 的失效范围收敛，但由于与 `tmp_13` 不同运行不可做端到端
   A/B，不再为降低 global miss 单独改缓存策略。
2. 补目录 rename 覆盖、rmdir/unlink 后仍被打开的目录 fd、未缓存父目录 fallback、hard link 和并发 stat
   回归；只有证明错误时才调整失效边界，保持 inode identity epoch 与 cache 一致性约束不变。

### P18.1/P18.2：保留实现，补完整及压力验收

1. 公平 gate 继续仅作用于 `EXT4_OP_LOCK`，不改为 rwlock，不放宽 lwext4 block cache/path/file C API 的单线程
   串行要求，锁序仍为 `write_state -> io_state -> EXT4_OP_LOCK`。
2. 对 P18.1 补无竞争 fast path、64+ waiter、队首取消/退出、跨 hart 连续交接和持锁任务被抢占回归；完整运行中
   检查累计 `queued = handoffs + cancelled + queue_depth`，而不以 Relaxed interval 快照的瞬时队深做守恒判断。
3. 对 P18.2 补新建文件/目录、既有目标 `EEXIST`、非 root、S_ISGID、ENOSPC 回滚，以及新建后立即 stat/read/close。
   `regular_no_lookup_stat=0` 只证明普通创建免首次 pathname fstat，不替代这些语义回归。
4. `tmp_03` 的停滞窗口需单独验收 gate owner 生命周期。退出汇合点先按 TID 移除排队票据；若退出任务正是
   `owner_tid`，同时清除逻辑 `held`、清除 owner 诊断状态并唤醒 FIFO 队首。下一轮日志必须检查：
   `owner_tid`、`owner_hold_us`、`owner_exit_releases`，以及累计
   `queued = handoffs + cancelled + queue_depth`。若停滞时 `owner_tid != 0` 且 `owner_hold_us` 持续增长，
   继续沿具体持锁 lwext4 子阶段分段；若 `owner_tid=0` 而 `queue_depth>0`，优先排查队首 waker/ready queue。

### P18.3：受限 rename dense-cache re-key（已实施，待验收）

1. rename 仍持有既有 `write_state -> io_state -> EXT4_OP_LOCK` 锁序。sparse range 在源目录项仍存在时刷盘；
   dense byte-cache 不在每次 rename 前强制写回，而是在 `file_rename()` 成功后调用 `rename_path_cache()` 迁移。
   迁移以 `CACHE_TABLE` 的 source remove/target remove/target insert 为一个受保护操作，并同步重建 FIFO 项。
2. 目标路径已有 cache 时先清理，避免旧目标内容覆盖新 artifact；rename 失败时不调用迁移，保留 source cache 以便
   重试。迁移后 VFS read/read_all、lookup stat 的 size/blocks overlay 和 mmap backing `read_at()` 必须从新路径看到
   dirty bytes；任一路径不可见都按正确性失败处理，而不是只看 Cargo 是否继续推进。
3. 必须补齐单独的 `rename_cache_migration` ops/bytes/success/failure 统计。当前 `ext4_rename_write_back ops=0` 在
   `tmp_09` 中不能用于证明没有 rename，因为该计数器只覆盖旧的显式 write-back/discard 阶段。
4. 定向回归覆盖：rename 成功后 read/exec/stat/mmap、旧 fd 继续写、rename 失败回滚、覆盖目标、hard link、多 alias、
   `fsync/sync`、`unlink-open-close` 和并发 eviction。未完成这些回归前，不扩大到所有 inode，也不宣称 Linux rename
   覆盖语义已经完整实现。

### P19A：文件页缓存满载候选退避（已实施，待长测）

1. 生产容量固定为 `192 * 1024` 页（768 MiB），不再将 `MAX_FILE_PAGE_CACHE_PAGES` 当作性能调参主线；32 MiB
   文件准入和四页预读保持不变。显式 feature `file-cache-capacity-test` 固定为 2,048 页，仅用于放大满载行为。
2. clean-page CLOCK 使用 `referenced` 二次机会，且只在 `!dirty`、`Arc<FilePage>::strong_count == 1`、
   `Arc<FrameTracker>::strong_count == 1` 时从全局索引移除。后两项不能省略：mmap VMA 持有的是 frame 引用。
   淘汰路径不进入 lwext4，也不在 `MemorySet` 写锁内做文件 I/O。
3. 候选改为两条仅保存 `FilePageKey` 的 FIFO 队列。新页与二次机会页保留在 `active`；dirty 或 `in_use` 页移到
   `deferred`，不再反复占用 128 项 CLOCK 扫描预算。`active` 耗尽后设置 256 次容量 miss 冷却；到期只把 16 个
   deferred 项移回 active 复检。失效路径同步删除两条队列的键，锁序固定为 `pages -> eviction_queues`。
4. 旧 2K 样本在 `t=31.289s` 已有 `capacity_bypass_pages=25790`、`eviction_scans=3240417`，约每个 bypass
   125.6 次检查；在 `t=261.966s` 时 25,650,541/25,690,228 次扫描为 `in_use`。本轮同 feature 的 60 秒运行在
   `t=33.816s` 记录 `bypass=35318`、`scans=17232`、`in_use=4064`、`deferred_retry_pages=2016`、
   `cooldown_bypasses=32414`，扫描均摊低于 0.49 次/bypass。该值证明退避生效，不是完整 BuildStorm wall-clock 结论。
5. 旧样本约 `t=161.948s` 后才开始出现 rustc SIGSEGV；本轮 60 秒样本只到 `BUILDSTORM_TOOLCHAIN ok`，没有覆盖该
   阶段。不能因扫描下降就宣称 SIGSEGV 已修复，也不使用 `RUST_MIN_STACK` 规避。下一份长测必须保留 fault 的
   `scause/stval` 或同等内核证据，单独确认其归因。
6. 不优先扩大 per-file 32 MiB 准入或预读窗口。只有 `inode_read_source` 证明大文件单次顺序 walk 仍主导，且
   回收/退避后的 bypass 与 gate 指标均不再主导时，才考虑文件级准入或 readahead 状态机。

### P21：lwext4 SMP 化，按 Linux ext4 并发语义映射（新课题）

#### 目标、范围与红线

1. 目标是让不同 inode 的 cache miss、路径查找和最终写回能够并发，而同 inode、同目录、同 block group、同 transaction
   或同一块缓存 buffer 的冲突操作仍按正确的对象粒度串行。目标不是让同一文件的非原子写、truncate 与 block allocation
   无约束地并发，也不是以损失 POSIX 可见性换 BuildStorm 吞吐。
2. “一比一还原 Linux ext4”在本项目中应定义为**锁职责、并发条件和故障语义的一一映射**，不能直接复制 Linux C
   实现。Linux ext4 依赖其 VFS/dcache、address_space 页缓存、folio/writeback、bio/block-mq、JBD2、RCU、workqueue
   与 reclaim 模型；直接移植会变成接入 Linux 文件系统子系统的独立内核工程，也需要单独完成许可证与接口边界审查。
3. `EXT4_OP_LOCK` 只在 P21 完成各阶段的并发回归后才逐路径撤退。禁止先删 gate、再依靠随机 BuildStorm 观察是否损坏；
   每个阶段均保留 feature-gated 的全局 gate fallback，遇到一致性差异可立即退回串行实现。

#### Linux 到 lwext4 的职责映射

| Linux ext4 对象/锁 | Linux 负责的冲突 | lwext4/Ya2yOS 目标对象 | P21 后的规则 |
| --- | --- | --- | --- |
| `inode->i_rwsem` | 同 inode 的元数据修改，目录读取/修改的共享或排他访问 | `Ext4Inode` 的 inode-number keyed `meta_rwsem`；目录也使用该对象 | 普通目录 lookup 取共享锁；create/unlink/rename 修改父目录取排他锁；不再以 pathname 作为锁 identity。 |
| `EXT4_I(inode)->i_data_sem` | truncate、hole punch、extent/block mapping 与分配 | 每 inode `data_rwsem` | 已映射只读 I/O 取共享；分配、扩展、truncate、SEEK_HOLE/DATA 取排他；同 inode 锁顺序固定在目录锁之后。 |
| VFS `s_vfs_rename_mutex` 与目录锁序 | 跨目录 rename 的拓扑和死锁规避 | 每 mount `rename_mutex` 与目录 inode 锁 | 只在跨目录 rename 取得 mount rename mutex；父目录按 ancestor-first，非目录 inode 按 inode number 排序。普通 read/find 不取得它。 |
| Linux page cache 的 folio lock、writeback state | 单页填充、dirty/writeback、回收与等待 | `ext4_bcache` 的每 buffer state 与 cache 索引锁 | 采用 `EMPTY/LOADING/CLEAN/DIRTY/WRITEBACK/EVICTING` 状态和 waiter；LBA/LRU/dirty 索引的短锁不得跨设备 I/O，buffer 被 pin 后才可锁外 I/O。 |
| ext4 block-group lock、`s_md_lock`、计数器 | 位图/组描述符分配与全局可用块统计 | 每 block group lock、superblock 统计原子/分片计数 | 位图与 group descriptor 只锁目标组；跨组分配按 group id 排序；free-block/inode 计数不以全 mount mutex 保护。 |
| JBD2 journal state lock、per-handle transaction | 并发元数据修改、credits、commit 与恢复 | `lwext4_journal` 的 running transaction、per-operation handle、commit worker | 删除 `mp->fs.curr_trans` 的单操作独占语义；每个修改操作取得 handle 并加入 running transaction，commit 与新 handle 按状态机协调。 |
| `sb_start_write`/freeze 与短时 superblock locks | mount/remount/freeze、orphan、fast-commit 和错误状态 | mount lifecycle rwsem、orphan/commit/error 细粒度锁 | 挂载、卸载、fsck/recovery、sync/freeze 才排他阻断；普通 read/write 不获取 mount-wide I/O mutex。 |
| bio/block-mq 的位置无关请求 | 多请求提交和完成顺序 | `Disk::read_at/write_at` 或 request queue | 删除共享 cursor；每次 I/O 携带 LBA/长度，完成前 buffer pin；底层驱动暂不支持多队列时可只在设备提交层串行，不能重新扩大到整个文件系统调用。 |

#### 目标架构和锁序

1. 将 lwext4 public API 从“按 path 查找全局 `s_mp[]` 后隐式整 mount 加锁”演进为显式 `ext4_op_ctx`：它持有
   mount、操作类型、已解析 inode/目录、journal handle 和 bcache buffer pin。保留原 API 作为串行兼容 wrapper；新增
   `*_ctx` 路径仅在 `lwext4-smp` feature 下使用。新的同步接口必须携带 `void *ctx`、对象 key 和共享/排他模式，
   不能继续使用只有 `void (*lock)(void)` 的 `ext4_mount_setup_locks()`。
2. Rust 层建立以 inode number 为键的 `Ext4InodeState` 表与独立 `Ext4OpenFile`。前者保存 `meta_rwsem`、
   `data_rwsem`、generation 和 cache invalidation epoch；后者保存一个 POSIX file description 的 `f_pos` 锁。
   现有 `Ext4Inode::io_state`/`write_state` 在迁移期只作为 compatibility wrapper，不能再承担不同 open file 的
   `f_pos` 或 lwext4 inode data 同步。
3. 固定可阻塞锁序为：`mount_freeze(read)` -> `rename_mutex`（仅跨目录 rename） -> directory `meta_rwsem` ->
   non-directory `meta_rwsem`（inode number 顺序） -> `journal_handle` -> `data_rwsem` -> buffer pin。任何 spinlock/
   cache-index lock 只保护内存链表或状态翻转，必须在等待 I/O、等待 journal commit 或等待 task mutex 前释放。
   锁序以 Linux `fs/ext4/super.c` 的写入/截断/写回约束为基线，但须为 Ya2yOS 的 task blocking 重新做 lockdep 风格
   断言和运行时顺序检查。
4. 读路径的最终形态为：dentry/inode cache 命中后取得 inode shared lock，查询 mapping 并 pin buffer；未命中时只有
   该 LBA 的 loader 执行 position-independent I/O，其他任务等待该 buffer，随后并行消费。写路径先用 journal handle
   预留 credits，再取得目标 inode/group/buffer 锁，提交数据和元数据；同步/commit 只等待关联 transaction，不阻塞
   不相干 inode 的读写。

#### 分阶段实施与每阶段退出条件

1. **P21.0：覆盖清单和串行 oracle。** 为每个 lwext4 exported API、`ext4_fs_*` helper、bcache mutation、bitmap/
   inode ref 和 journal 状态写入标注资源所有者；建立固定小 ext4 镜像、操作 trace 与单线程 oracle。新增可开关
   `lwext4-smp`，默认关闭，且每个 trace 可在旧 gate 与新路径下比较 inode、目录项、文件字节、`stat`、free block/inode
   计数和 fsck 结果。未完成清单与 oracle 不进入 P21.1。
2. **P21.1：位置无关块设备。** 把 `KernelDevOp` 的 `seek/read/write` 换为原子 `read_at/write_at` 或 request submit；
   删除 `Disk { block_id, offset }` 作为共享 I/O 状态。过渡实现可用单一 block-device submission mutex 保证
   `LBA + transfer` 原子，但锁范围仅覆盖设备请求，不覆盖 bcache 或 inode。完成 8 HART 随机 LBA read/write、同 LBA
   重叠写、错误注入和连续 10 万次请求校验后，才允许多个 C 调用同时进入只读 bcache 代码。
3. **P21.2：并发 bcache。** 重写 `ext4_bcache`，把 LBA lookup、LRU、dirty queue、refcount 和 eviction 分离；miss
   采用单飞行 `LOADING` waiter，dirty buffer 在 `WRITEBACK` 前 pin，eviction 先声明所有权再锁外写盘。严禁在
   `ext4_block_cache_shake()` 持 index lock 时调用 `ext4_blocks_set_direct()`。完成同 LBA coalescing、不同 LBA 并发、
   dirty/flush/evict 竞争、I/O 失败重试和内存泄漏回归后，才启用不同 inode 的并发只读。
4. **P21.3：inode identity、open file 与只读并发。** 从 path cache 得到稳定 inode number/generation 后，以
   `Ext4InodeState` 取得 shared `meta_rwsem`/`data_rwsem`；打开文件将 `f_pos` 状态移到独立 open-file 对象。先只放开
   read/read_all/fstat/read_dir 的不同 inode 并发，仍让修改操作走 gate fallback。验收包括 dup/close 后共享 file offset、
   hard link/rename 后旧 fd、并发 stat/readdir 与 cache invalidation。
5. **P21.4：目录 namespace。** 引入目录 shared/exclusive 锁和跨目录 `rename_mutex`，实现 ancestor-first 与 inode
   number 排序；create/unlink/link/rename 的 dentry cache 发布必须在 on-disk transaction 成功后可见。验收为双向
   rename、rename 覆盖、循环目录拒绝、unlink-open-close、hard link、多任务路径遍历及死锁超时测试。
6. **P21.5：block-group allocator 与 extent/indirect mapping。** 位图、group descriptor、superblock free count 和
   inode allocation 分离到 group locks；block mapping 只在需要分配/截断时升级 inode `data_rwsem`。验收为多 inode
   append、ENOSPC 竞争、sparse write、truncate/hole punch、SEEK_DATA/SEEK_HOLE 及崩溃后 `e2fsck -fn`。
7. **P21.6：JBD2 语义对齐。** 以 Linux JBD2 的“running transaction + per-operation handle + credits + commit wait”
   取代当前 `mp->fs.curr_trans` 单指针。实现 handle 引用、reserved credits、commit barrier、ordered metadata/data
   writeback、abort 和 recovery；commit worker 可先由一个内核任务实现，之后再优化批处理。未通过 kill-at-every-write-
   boundary 的重挂载/recovery 与 `e2fsck -fn`，不得放开任何 metadata 并发写。
8. **P21.7：逐路径撤退 gate 与性能验收。** 顺序为不同 inode read/fstat -> directory lookup -> independent writeback ->
   create/unlink -> rename/truncate；每放开一类都保留 feature fallback，并比对正确性 oracle。只有完整 BuildStorm 两次均
   `BUILDSTORM_COMPILE ... ok=true`、测试组 END、`shutdown!`，同时 gate wait 下降且没有 I/O 错位、文件损坏、panic、
   TFAIL/TBROK 或 fsck 报错，才默认启用该类并发。

#### 量化指标和风险闸门

1. 新增按对象而非仅总量聚合的 telemetry：bcache hit/miss/loader wait/evict/dirty flush，block request queue/wait/
   completion，inode/data/dir/group/journal lock wait/hold，transaction handle/credits/commit wait，以及每类 fallback
   次数。保留 `EXT4_OP_LOCK` 统计，直到其只覆盖 lifecycle fallback。
2. 每阶段至少运行：单线程 oracle 对照、8 HART 随机化并发 trace、targeted syscall 语义回归、掉电/重挂载恢复、
   `e2fsck -fn`、RISC-V 与 LoongArch64 构建；P21.6 之后还需相同 workload 的两次完整 BuildStorm。任何一次出现
   stale read、错误 LBA、重复/丢失目录项、free count 漂移、journal abort、死锁或 fsck 错误，立即关闭该 feature 并
   回到上一个阶段，不以吞吐数据抵消正确性失败。
3. P21 的首个可交付物不是“完全并行写入”，而是 P21.1--P21.3 后不同 inode 的安全并发只读。它能直接缓解 Cargo
   的 read/find/fstat 排队，并为随后写入和 journal 并发提供可验证的底座；在 P21.6 完成前，不对 BuildStorm 写路径
   报告“Linux 级并发”。

### P19C：`tmp_02` 指向的 gate 长事务归因与单变量优化

1. **已完成一次低风险重复准入优化。** `write_at_impl()` 在 `write_state`/`io_state` 下已能确认同一
   `Ext4File` 的 O_RDWR 描述符和 `known_size`；新增 `is_open_for_write()`，在此条件下跳过只会执行
   `ensure_open()` no-op 的 `EXT4_OP_LOCK.lock_for_write_open()`，首次打开或必须探测大小时仍保留原 gate。
   该改动只减少 FIFO ticket，不放宽 lwext4 的单线程边界；下一轮需用同一镜像、冷启动和 workload 对比
   `write_open_lock` 样本/等待、`write_data_lock` 等待及 gate handoff。
2. **读/写 data 优先。** 先用 P19B 的 interval delta 将 `ext4_read_data_lock` 的 `584.879s` 等待、
   `48.489s` 持有与 `ext4_write_data_lock` 的 `438.269s` 等待、`55.830s` 持有对齐到实际 read/write bytes、
   page-cache miss、sparse/direct 分支和底层 C 调用。若等待占比仍高，优化重复进入 gate、批量化同一 inode 的连续操作或
   减少回源；若持有占比高，只改一个已证实的 C 层子阶段，并保留 `write_state -> io_state -> EXT4_OP_LOCK` 锁序。
3. **find/fstat 次之。** `ext4_find_lock` 等待/持有为 `246.151s/72.252s`，`ext4_fstat_lock` 为
   `71.766s/28.050s`。`fsidx_hit=57589`、`path_index_hit=36216`、`dentry_miss=4775`，说明不能凭直觉恢复正 dentry
   快路径；先定位剩余 miss 是否重复 pathname lookup 或被 gate 排队放大。目录 epoch 仅有 `global_epoch_miss=98`，除非新
   语义回归发现错误，不再为降低该计数单独改失效范围。
4. **管道等待只做归因。** `pipe_read_wait=825.329s/162`、最大约 24.8 秒，明显高于 scheduler dispatch 的
   `2.168s`；增加 producer/consumer、poll/wakeup 和 recheck 的窗口关联，确认它是 BuildStorm 子进程同步还是内核
   丢唤醒。未证明是锁等待前，不修改 pipe 唤醒或调度策略。
5. **rename 先做语义与 telemetry 收尾。** `tmp_09` 的 `ext4_rename_write_back` 计数为 0，不能据此判断
   rename 成本；先接入 migration 计数，再用同一 workload 比较 dirty bytes、迁移成功率和目标覆盖行为。页缓存容量、
   预读窗口和公平 gate 本身不作为本轮调参变量。

### P20：固定环境的端到端归因与验收

1. 使用同一 commit、同一 `kernel-rv`/根文件系统、同一 QEMU 参数和相同冷启动状态，连续至少两次完整
   BuildStorm；记录外部 wall-clock 与 `BUILDSTORM_COMPILE mode=multi ok=true elapsed_s=...`。只有出现测试组 END
   和 `shutdown!` 才比较总耗时。
2. 同时记录 Cargo 的活跃 crate/build-script 名称和固定检查点 `1/446`、`10/446`、`20/446`、`30/446`、
   `40/446`、`52/446`、`64/446`、`85/446`、`97/446`、`120/446`、`150/446`、`446/446` 的 guest `t=`；
   将 crates/min 仅用作同一 DAG 阶段内的辅助观测。重型 `cmake`/C 编译与 Rust crate 不能按一个 crate 计为等价工作。
3. 将 P19A/P19B/P19C 的容量、回收、inode read source、gate wait/hold、pipe wait 和子阶段 delta 对齐：
   若 `capacity_bypass=0` 而 gate 仍忙，继续优化对应 lwext4 子阶段；若 gate 已不忙而 Cargo 仍停在重型 build script，
   则内核不应背负该段 wall-clock，应另行取证编译器 CPU/外部 I/O。

## 5. 验收边界

构建与静态检查：

    cargo fmt --manifest-path os/Cargo.toml --all -- --check
    git diff --check
    make perf TARGET_ARCH=riscv64
    make perf TARGET_ARCH=loongarch64
    make TARGET_ARCH=riscv64
    make TARGET_ARCH=loongarch64

运行期验收必须看测试自身结束，而不是外层 timeout：

    BUILDSTORM_COMPILE mode=multi ok=true elapsed_s=<...>
    #### OS COMP TEST GROUP END buildstorm ####
    shutdown!

P19A/P19B/P19C/P20 的性能结论还必须同时满足：同一 commit/镜像/QEMU 参数和冷启动状态至少完成两次；保留
`tmp_02` 对应的 `t≈95881ms`、`127447ms`、`169103ms`、`259005ms`、`315205ms`、`421834ms`、
`498261ms`、`531571ms`、`593195ms` 附近的 Cargo 活跃 crate、页缓存容量、
`eviction_scans/deferred_retry_pages/cooldown_bypasses`、inode read source、EXT4 gate、pipe wait 和 interval delta；
公平 gate 还必须保留 `owner_tid/owner_hold_us/owner_exit_releases`，并核对退出回收后队列是否继续交接；
使用 `/usr/bin/time` 记录宿主 wall-clock。仅看到 `Building N/446`、外层 timeout，或不同 DAG 阶段的 crates/min，
都不能声明端到端加速或回归比例。

如果下一轮改动触及写入、rename、truncate、unlink、mmap 或 stat 语义，还需补定向回归：

- mmap16、lseek11 的 SEEK_DATA/SEEK_HOLE；
- fstat/statx 的 st_blocks、mtime/ctime；
- write-read、rename、truncate、unlink-open-write-close、fsync/sync；
- 文件映射部分尾页、完整越界页和并发 truncate 的 SIGBUS。
- 文件页缓存容量旁路定向 case：小容量 `file-cache-capacity-test`、动态 ELF exec、mmap fault、MAP_SHARED fork
  预取页传递，以及触顶后的 read/mmap 不返回旧数据、不 SIGSEGV；同时检查 `in_use` 饱和后扫描数不再按
  `128 * capacity_bypass_pages` 增长。

公平锁改动还必须验证：无竞争 fast path、64 个以上 waiter、队首任务取消/退出、跨 hart 连续交接，以及
持锁任务被抢占时没有 lost wakeup 或永久 reservation。
