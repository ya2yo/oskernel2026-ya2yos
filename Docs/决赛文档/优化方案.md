# BuildStorm `server.ans` 性能分析与后续优化方案

> 版本：2026-08-08（基于单次完整日志的分析稿）
> 适用源码快照：当前 `nightly` 工作区，HEAD `c2a83968`，构建日志显示内核启用 `scheduler-cfs` 与 `perf`。
> 测试配置：RISC-V 64、8 个 Hart、QEMU、BuildStorm `mode=multi`、glibc 镜像。
> 目标读者：负责 Ya2yOS 文件系统、内存管理、SMP 调度和 BuildStorm 回归的维护者。
> 实现边界：本文只根据 `server.ans` 和当前源码制定后续方向，没有在本轮修改内核；下文的优化项均为待验证计划，不把本次样本宣称为可比较的性能基线。

## 1. 结论摘要

这次运行功能上完成了 BuildStorm，但性能计时不可采信。日志出现了完整的
`BUILDSTORM_TOOLCHAIN ok`、`BUILDSTORM_MINIBUILD ok`、
`BUILDSTORM_COMPILE mode=multi ok=true`、测试组结束和 `shutdown!`，编译产物为
1,683,456 字节；然而正式标记报告 `elapsed_s=0.00`。评测脚本按该字段直接给出
180/180，因此这个分数反映的是计时接口缺失，而不是内核已经达到该性能。

后续工作按以下顺序推进：

1. **P0：恢复可信的计时和可复用的构建基线。** 实现动态 `/proc/uptime`，让预构建
   产物在计时阶段真正复用，并把高频 `[perf]` 串口报告与正式成绩运行隔离。
2. **P1：降低 MM 页表更新和 remote-TLB 的固定成本。** 最终有 743,109 次 MM
   syscall、3,497,313 次缺页和 911,051 次 shootdown；应先区分“只做本地失效”和
   “需要远端 ACK”的操作，再做范围批处理。
3. **P2：处理 EXT4 稀疏写回和元数据长尾。** 稀疏缓冲 600.7 MB 中 596.2 MB
   因缓存驱逐写回，写数据累计 433.1 s，create/unlink 各有约 2 s 最大值。
4. **P3：降低文件页缓存和块缓存的抖动。** 文件页缓存长期顶到 192K 页并发生
   589,827 次驱逐；块缓存命中率已经约 99.44%，重点应是请求合并和驱逐成本，不能
   直接把所有缓存上限继续调大。
5. **P4：最后才评估调度和 pipe 唤醒。** pipe 的读等待是并发任务的累计阻塞时间，
   而真实拷贝仅约 0.68 s；必须先证明是无效唤醒或负载不均，再改调度策略。

### 2.2 时间只能给出区间，不能给出单点基线

日志的最后一个内核时间快照是 `t=3155976ms`，第一次进入计时命令后的快照是

这个区间与日志中的两个 Cargo 阶段相符：

| 阶段 | 日志耗时 | 是否计入官方 `elapsed_s` |
| --- | ---: | --- |

| `arceos-helloworld` release 构建 | 20m20s（`cargo build ... done (1240.77s)`） | 是 |

和一批 `dep-graph.bin: memory map must have a non-zero length` 警告。说明计时阶段没有
复用预构建结果，约 16m36s 的重复编译会直接吞掉正式时间。根因尚未由这一份日志单独
证明，候选包括增量 dep-graph 实际为零长度、EXT4 关闭/rename 后元数据未持久化，或
`cargo xtask` 使用了不同的 target/profile；必须在下一轮通过 `stat`、`cargo -vv`
和同一镜像复核，不能仅凭警告选择一个内核模块背锅。

### 2.3 `perf` 样本不是成绩样本

本文件 8,688 行中约 8,190 行是 `[perf]`，共有 45 个 `[perf] t=...` 快照。每个快照
还会输出大量文件系统、锁、调度和 syscall 统计；这些内容经 QEMU 串口打印，会改变
任务调度、文件写入和缓存状态。`perf.rs` 的计数器是全局 relaxed 累计值，报告由某个
Hart 触发并非精确的阶段边界。故应保留两种运行：

- **分析运行**：启用 `perf`，只在明确阶段标记或较长间隔报告，保存 `/tmp` 日志，用于
  找路径和长尾；
- **成绩运行**：关闭高频报告和诊断输出，只保留正式 `BUILDSTORM_*` 标记，用同一冷/热
  镜像重复至少两次，比较 guest `elapsed_s` 与宿主 `/usr/bin/time`。

不能把启用 45 次完整遥测的 `server.ans` 与关闭 `perf` 的另一轮直接计算加速百分比。

## 3. 最终累计指标

最终快照位于 [server.ans:8507-8648](../../server.ans:8507)。以下时间都是内核
tick 换算后的累计 `total_us`；并发任务的累计值可以超过端到端 wall-clock，只能用于
排序和形成假设，不能相加后当作总耗时。

### 3.1 syscall、MM 与进程路径

| 路径 | 次数 | 累计时间 | 最大单次 | 解释 |
| --- | ---: | ---: | ---: | --- |
| 全部 syscall | 4,573,860 | - | - | 工作负载规模 |
| `lseek` | 1,907,593 | 9.73 s | 17.84 ms | 次数最高但实现自身仅 1.28 s，不是近期热点 |
| `mm` | 743,109 | 1,196.07 s | 2.24 s | 需要优先拆成 mmap、缺页、权限和回收子类 |
| `read`（active） | 650,641 | 423.27 s | 1.70 s | active 不含完整阻塞等待 |
| `write`（active） | 303,449 | 641.77 s | 16.87 s | 主要对应编译产物和管道输出 |
| `path` | 157,063 | 151.39 s | 1.97 s | 路径解析、目录和 inode 元数据混合 |
| `open` | 64,828 | 106.37 s | 1.88 s | 打开阶段长尾明显 |
| `stat` | 126,857 | 102.38 s | 1.94 s | 与 fstat/目录 epoch 失效相关 |
| `futex` | 597,829 | 53.34 s | 0.37 s | 当前不是主要累计时间 |
| `clone` / `execve` | 3,203 / 539 | 44.57 s / 30.53 s | 0.33 s / 2.07 s | 进程生命周期可在 MM 优化后再细分 |

`mm` 的累计时间和 3,497,313 次缺页说明地址空间变更、文件页安装和 TLB 协议是第一
个内核热点。`clone` 的 `address_space` 子阶段为 28.41 s，`exec` 的 `commit` 子阶段
为 18.66 s；它们是可验证的次级目标，但远小于整个 BuildStorm 的文件 I/O 窗口。

### 3.2 EXT4、块设备和写回

| 指标 | 最终值 | 观察 |
| --- | ---: | --- |
| EXT4 读取 | 623,785 次 / 5.864 GB | 文件读取量大，需结合块请求而非只看 syscall 次数 |
| bcache | 7,995,375 次查询，7,950,785 命中，44,590 miss | 命中率约 99.44%，不是“块缓存完全失效” |
| bcache 写回 | 233,775 次且全部成功 | 写回成本和队列值得继续拆解 |
| block device | 1,497,434 请求 / 10.644 GB | 平均约 7.1 KiB/请求，读 594,433、写 903,000 |
| block service / wait | 725.58 s / 70.25 s | service 是累计设备服务时间，wait 是请求排队时间 |
| 资源锁 | 5,194,309 acquires，wait 104.60 s，hold 1,768.16 s | hold 为并发累计，不等于 wall-clock |
| 文件页缓存 | 3,721,583 hit，335,800 miss | 命中率约 91.72%，但已经顶到 192K 页 |

写路径的阶段计数更有指向性：`write_data` 累计 433.09 s，`open` 11.09 s；稀疏
缓冲写入 292,627 次、600.71 MB，产生 11,541 个 flush batch，其中
`sparse_flush_cache_evict_bytes=596,235,116`，约占稀疏 flush 字节的 99.25%。
`payload_limit_batches=1,131`、`run_limit_batches=93`、`global_budget_batches=0`，
说明当前主要是每 inode 512 KiB payload 上限和缓存驱逐，不是 8 MiB 全局预算或内存
分配失败。相关上限与写入决策见 [file.rs:51-68](../../crates/lwext4_rust/src/file.rs:51)
和 [file.rs:1295-1426](../../crates/lwext4_rust/src/file.rs:1295)。

大块直写也很集中：`direct_too_large_bytes=833,662,954`，占 direct bytes 的约
99.6%。这说明当前 4 MiB whole-file cache 对大型产物覆盖有限；应先验证块请求合并
和稀疏写回，不能贸然把所有大文件纳入全文件缓存，否则会把 sparse hole 物化为零块。

### 3.3 EXT4 锁、fstat 和命名空间长尾

最终锁分类如下：

| 锁类别 | acquires | wait | hold | 最大 hold | 结论 |
| --- | ---: | ---: | ---: | ---: | --- |
| `inode` | 824,152 | 0.49 s | 949.89 s | 2.15 s | 争用少但临界区最长，应拆分 I/O 与元数据段 |
| `journal` | 269,912 | 46.88 s | 422.37 s | 2.15 s | 写回和 namespace 事务的主要等待来源 |
| `namespace` | 308,093 | 27.97 s | 170.79 s | 1.95 s | create/unlink 争用明显 |
| `vfile_cache` | 128,345 | 27.25 s | 147.09 s | 2.23 s | 长尾最大，需按缓存操作阶段定位 |
| `group` | 2,679,263 | 2.02 s | 52.88 s | 52 ms | 次数多但平均等待不高 |

`fstat` 路径累计为：fast cache 82,276 次、directory epoch cache 26,695 次、实际
EXT4 fstat 12,118 次；缓存路径约占 90%，所以方向不是简单增加 fstat cache 容量。
实际 miss 中 cold inode 7,689 次，且目录 cold lookup 7,447 次；目录 epoch miss
14,900 次（local 10,202、global 5,380）。create 4,040 次累计 43.53 s，unlink
4,054 次累计 39.77 s，timestamp metadata 10.56 s，均有接近 2 s 的单次最大值。
当前 fstat/namespace 锁边界见 [metadata.rs:89-148](../../os/src/fs/ext4_lw/inode/metadata.rs:89)
和 [namespace.rs:83-124](../../os/src/fs/ext4_lw/inode/namespace.rs:83)。

### 3.4 TLB、调度和 pipe

- remote-TLB `shootdowns=911,051`、`target_harts=357,410`、
  `acknowledgements=357,399`。11 个未累计 ACK 可以由目标 Hart 在等待期间退出地址
  空间而被正常跳过，不能直接视作丢 ACK；但 911K 次本地失效和 mailbox 往返本身已
  足以成为 MM 优化目标。
- 调度选择 142,882 次，remote enqueue 142,882 次，发送 IPI 86,388 次；各 Hart
  选择数从 31,835 到 10,778，约 2.95 倍差异。当前 CFS 使用共享 `BinaryHeap`，这
  可能是工作负载到达时序，也可能是队列锁和唤醒策略造成的不均衡，必须增加队列等待
  与实际运行 tick 后再判断。
- pipe 读等待累计 4,947,409,853 us、最大 498.9 s，但 read copy 仅 683,633 us，
  user copy 406,529 us；write copy 124,265 us。累计等待跨任务重叠，主要表示编译器
  进程在等输出，不证明 pipe copy 慢。只有出现重复唤醒、轮询重试或 runnable 任务被
  错过时，才把 pipe 纳入近期优化。

## 4. 优化假设与实现方向

### P0-A：实现可审计的 `/proc/uptime`

1. 在 proc 文件打开/读取路径增加只读动态 inode，内容使用架构单调 tick 转换为秒和
   centisecond，格式符合 Linux 的 `"uptime idle\n"`，并保证跨页读、重复读和 EOF
   语义正确。
2. `mount -t proc proc /proc` 仍应保持可接受；如果 Ya2yOS 继续使用路径化 proc
   模型，至少让 `/proc/uptime` 走虚拟文件分发，不要在镜像里放一个静态文件冒充。
3. 用一个小用户程序连续读取两次，检查 `T1 >= T0`；再运行正式脚本，要求
   `BUILDSTORM_COMPILE ... elapsed_s` 与 `[perf] t` 端点在 5% 内一致。
4. 对 LoongArch64 使用该架构的单调时间 API，不能复用 RISC-V 时钟频率常数。

### P0-B：恢复 `tg-xtask` 预构建复用

1. 在预构建结束和计时开始前记录同一个 `target/debug` 二进制、`.d` 和 incremental
   dep-graph 的大小、mtime、inode 号；计时阶段用 `cargo -vv` 记录是 `Fresh` 还是
   `Compiling`。
2. 若 dep-graph 确实为零长度，检查 EXT4 `truncate/write/close/rename` 的顺序和
   dirty cache 写回；重点对照 [io.rs:130-239](../../os/src/fs/ext4_lw/inode/io.rs:130)
   的 sparse/dense 分支，验证关闭后 `stat` 能立即看到最终大小。
3. 若文件状态正常但仍重编译，确认 `cargo build -p tg-xtask` 与
   `cargo xtask` 的 `CARGO_TARGET_DIR`、profile、target triple 和 workspace 根
   一致；修复脚本或构建环境，而不是改内核缓存。
4. 复用成功后单独报告“预构建复用率”和正式 compile 时间。重复编译减少后，才有
   资格比较 P1-P3 对 wall-clock 的影响。

### P0-C：把遥测从成绩路径移出

1. `perf` 运行只保留阶段计数和少数目标 duration；将 45 次完整报告改为显式 marker
   触发或至少 5 分钟一次，并确保不会在持有 EXT4/任务锁时 `println!`。
2. 成绩运行关闭 `perf` 特性和 debug 输出；保留 `BUILDSTORM_*`、组 END、`shutdown!`
   和必要错误行。
3. 每个候选改动使用相同镜像、相同 `-smp`、相同 `target` 清理策略，冷启动和热启动
   各重复两次；同时保存宿主 `/usr/bin/time`，但不把宿主时间与 guest tick 相加。

### P1：MM 页表更新和 remote-TLB 批处理

当前 [handle.rs:97-112](../../os/src/mm/memory_set/handle.rs:97) 对会替换 resident
frame 的更新统一进入 `UPDATE_LOCK -> MemorySet write -> shootdown`；
[handle.rs:317-369](../../os/src/mm/memory_set/handle.rs:317) 已对 fresh PTE 做本地
快速路径，这是正确的基础。下一步不是删除 shootdown，而是让其成本可分类、可批量：

1. 在 [remote_tlb.rs:80-111](../../os/src/mm/remote_tlb.rs:80) 增加 local-only、
   remote-target、mailbox wait 和 ACK latency 的 aggregate duration；按调用者区分
   page fault、munmap、mprotect、COW、mremap 和 fork/exec，避免把 911K 次混成一个桶。
2. 对同一 syscall 内连续 VPN 的失效合并成一个 range 或一个 mailbox sequence；在
   `munmap`/权限批量更新完成后发送一次 shootdown，保留旧 frame 到最后一个 ACK，不能
   为了减少 IPI 提前释放。
3. 对没有 active remote Hart 的地址空间跳过远端 mailbox，但保留当前 Hart 本地
   `tlb_invalidate`；对 fresh non-present PTE 继续使用现有 fast path。
4. 检查 `with_mut` 的 broad frame retention 是否仍被普通路径调用；优先替换为已有
   `with_range_mut`/`with_frame_preserving_mut`，缩短写锁和 `Arc` 扫描时间。
5. 验证共享地址空间多线程、COW、`mprotect`、`munmap`、`mremap`、fault retry 和
   远端 Hart 退出期间的帧生命周期。任何 shootdown 优化都必须保持
   `UPDATE_LOCK -> MemorySet write -> ACK -> release old frame` 的锁序。

### P2：稀疏写缓冲和 EXT4 长锁

证据表明每 inode 512 KiB payload 上限比全局 8 MiB 预算更早触发，而且 99.25% 的
flush 字节来自 cache eviction。建议分三步做可证伪实验：

1. 先在 `perf` 中记录每个 flush batch 的 payload 桶（例如 `<=64 KiB`、`64-256 KiB`、
   `256-512 KiB`、`>512 KiB`）和触发前后的连续区间数；不要逐写 `println!`。
2. 让 sparse range 支持双向相邻/重叠合并，减少同一文件的重复 payload；然后只改变
   一个变量，比较 512 KiB 与 1 MiB 上限。若 `cache_evict_bytes` 显著下降且 journal
   最大 hold 不上升，再考虑自适应 per-inode 上限；全局预算仍需硬上限。
3. 将“缓存驱逐”改为可部分写回的 oldest ranges，而不是达到阈值就取走整个 inode
   的 buffer；失败时恢复原 runs 和全局 byte 计数，保持 unlink/rename/fstat 可见性。
   `fstat`、rename、truncate、close 仍必须是明确的可见性屏障。

同时对 EXT4 资源锁做边界审计：

- 将可能触发块 I/O 的操作与纯路径/epoch 更新分段计时；不要在持有 namespace 或
  inode 锁时执行不必要的用户拷贝、页缓存分配或阻塞等待。
- 为 journal、inode、namespace、vfile cache 分别记录 wait/hold 的 p50/p95/p99
  近似桶和最大值；当前最大 hold 约 2.15 s，单个 max 值比平均值更能解释尾延迟。
- create/unlink 的元数据更新必须继续维护 inode identity、目录 epoch、dentry/fsidx
  失效和 Linux 错误语义，不以全局缓存“永不失效”换取一次 BuildStorm 速度。

### P3：文件页缓存、直接读取和块请求

当前文件页缓存配置为 192K 页（约 768 MiB），CLOCK 发生 589,827 次驱逐、1,344,325
次扫描和 738,434 次 second chance；块缓存却有 99.44% 命中。方向如下：

1. 增加 page-cache `lookup/load/evict` 的 duration 和扫描步数分桶，区分锁等待、
   `Arc` in-use、dirty skip、second chance 和真正 evict；已有计数只说明次数，不能
   证明驱逐耗时。
2. 在同一 workload 下比较 192K、256K 和受内存预算约束的容量，观察 miss、bypass、
   evictions、block service 和 wall-clock 的联合变化。若容量增加只增加回收扫描而
   不减少 miss，应优化 CLOCK 队列而非继续扩容。
3. `mmap` 预读上限当前为 4 页；以 `mmap_demand`、`page_cached_cold_run`、direct
   bypass 和 block request size 做 A/B。不能因为 mmap miss 多就无条件扩大预读，避免
   在 192K 容量下把未使用页推入驱逐队列。
4. 对约 2.01 GB direct-bypass 文件读记录请求长度和是否顺序；先确认块设备每次约
   7.1 KiB 的碎片化来自 VFS 分片、lwext4 还是 virtio，再决定是否做有界合并读。
5. bcache 的 260,045 drops 和 261,953 allocations 说明缓存对象 churn 很高；在不
   改变 2,048 block 上限前，先复用请求 buffer、合并相邻 block 请求，并测量资源锁
   `cache_state/cache_flush` 的持有时间。

### P4：目录索引、调度和 pipe

1. **目录索引。** positive dentry hit 只有 597，而 fsidx/path index 和 final-path
   cache 已有大量命中；先将 dentry miss 按“新建、被 invalidation、identity stale、
   父目录 miss”分类，检查 8,019 次 dentry invalidates 是否过度。目录 epoch 的
   local/global miss 也应分开，优先消除不必要的 global fallback。
2. **调度。** 给共享 CFS 队列增加锁等待、堆长度、每 Hart runnable/runtime tick、
   wake-to-dispatch latency；当前选择数 2.95 倍差异不足以证明不均衡。只有确认远端
   enqueue/idle IPI 造成可见等待，才评估批量唤醒或亲和性调整。
3. **pipe。** 读等待约 4,947 s 是并发累计，拷贝不足 1 s。先记录每次 wait 的原因、
   writer 是否仍 runnable、唤醒后到数据到达的延迟；未证明存在丢唤醒前，不改 ring
   buffer 的语义和阻塞协议。

## 5. 验证矩阵与完成条件

每一阶段只改变一个主要变量，并至少重复两次。建议命令和验收项如下：

| 阶段 | 构建/运行 | 必看结果 |
| --- | --- | --- |
| P0 | `make TARGET_ARCH=riscv64`；RISC-V 官方脚本 | `elapsed_s` 非零、单调，且与 `[perf] t` 区间接近 |
| P0 | 同一镜像两次 prebuild + timed build | 第二阶段 `cargo -vv` 主要为 `Fresh`，不再重复编译 `tg-xtask` |
| P1 | RISC-V 8 Hart `make run` + MM/COW/mremap 回归 | 无 panic/SIGSEGV，shootdown ACK、旧帧释放和 active-hart 正确 |
| P2 | BuildStorm 文件创建、写入、rename、unlink 压力 | `ok=true`、无 EIO/目录损坏，cache-evict flush 字节和 max lock hold 下降 |
| P3 | 192K/256K page cache A/B，冷/热各两次 | miss、evict、block service 和 wall-clock 同向改善，不增加坏指针/数据错误 |
| P4 | RISC-V 后再跑 LoongArch64 | 无架构回归；调度/pipe 指标只有在延迟证据成立后才用于优化结论 |

行为结果必须以 `TPASS/TFAIL/TBROK/panic/SIGSEGV` 和最终 `shutdown!` 为准。性能结果
至少同时记录 guest `elapsed_s`、宿主 wall-clock、关键 `[perf] interval` 和镜像/架构；
缺少结束标记、计时为 0 或仅有一次 timeout 的样本只能作为路径线索。

## 6. 暂不作为近期目标的项目

- `lseek` 虽有 1,907,593 次，但 `lseek_duration impl` 仅 1.28 s；除非新的分层计时
  证明 fd 查找或路径恢复隐藏在 syscall 总时间中，否则不先改 lseek 语义。
- `fstat` 已约 90% 命中 fast/directory cache；先修 epoch/invalidation 的必要失效，
  不直接增大缓存或取消 identity 检查。
- pipe read wait 的累计时间不能与 CPU 时间相加，也不能从一次最大等待推断死锁；
  先做 runnable/wakeup 证据。
- 不把启用 `perf` 的串口日志、预构建重复编译、QEMU 启动时间和官方 timed compile
  混成一个百分比；四者必须在报告中分别列出。
