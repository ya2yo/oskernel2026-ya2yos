# BuildStorm 下一轮优化方案

> 状态：规划，尚未实施本文件提出的新行为改动。
>
> 适用快照：2026-07-29 当前工作区、`tmp_09.ans`、
> `Docs/决赛文档/开发日志.md` 的已验证结论。
>
> 目标：在不破坏 Linux 可见文件系统语义、稀疏文件布局、缓存失效和 lwext4 并发安全前提下，
> 为 BuildStorm 选择下一处可证伪、可验证的优化点。

## 1. 结论边界

`tmp_09.ans` 最后的完整 perf 快照为 `t=497346ms`，Cargo 仅可见到 `Building 20/446`。日志没有：

```text
BUILDSTORM_BEGIN
BUILDSTORM_COMPILE mode=multi ok=true elapsed_s=...
#### OS COMP TEST GROUP END buildstorm ####
shutdown!
```

因此该样本只能用于热点归因，不能用于报告完整编译耗时、端到端加速比例或评分达标。性能结论必须来自
同一 source snapshot、镜像、内存、hart 数、缓存起始状态下的完整 `elapsed_s`。

lwext4 的挂载级 block cache 和 path-based C API 尚未证明 SMP-safe，`EXT4_OP_LOCK` 必须继续保持唯一的
后端串行边界。优化目标是减少不必要的后端进入和缩短已证实的锁内工作，而不是将该锁改为 rwlock，或让多 hart
并发调用 lwext4。

## 2. `tmp_09.ans` 的当前信号

末尾统计显示全局 EXT4 gate 在 Cargo 并发阶段已经饱和：

| 指标 | 最后快照 | 含义 |
| --- | ---: | --- |
| EXT4 gate 操作数 | `79036` | 多类文件操作均通过同一后端边界 |
| 累计 wait / hold | `1344.647 / 394.102 s` | 多 hart 任务排队远高于后端有效工作 |
| `read` wait / hold | `495.282 / 60.520 s` | 仍是最大的排队来源 |
| `write` wait / hold | `304.925 / 71.581 s` | 写入慢路径是第二梯队热点 |
| `find` wait / hold | `261.377 / 55.331 s` | 路径式查找仍频繁进入后端 |
| `fstat` wait / hold | `140.840 / 49.783 s` | 主要成本仍是目录真实 metadata 查询 |

下面三项是下一轮最需要澄清的信号。

### 2.1 inode 级 dense write 快路径覆盖不足

```text
ext4_write_cache hit_ops=608 hit_bytes=18120570
fast_hit_ops=79 fast_hit_bytes=439970
```

`fast_hit_*` 是已有 dense write cache 命中、已经处于 quota 预留范围内、且不触碰 lwext4 的子集。它仅占：

- 操作数：`79 / 608 = 13.0%`；
- 字节数：`439970 / 18120570 = 2.4%`。

这证明 inode cache-only write 的方向正确，但其余 cache hit 为什么没有走快路径尚未归因。不能直接把 quota
预留、cache 初始化或 sparse/direct write 搬出 `EXT4_OP_LOCK`。

### 2.2 sparse 缓冲绝大多数因容量回写

```text
sparse_buffer_ops=9874
sparse_buffer_bytes=30452774
sparse_flush_cache_evict_ops=495
sparse_flush_cache_evict_bytes=30227012
```

约 `99.3%` 的 sparse buffer 字节通过 `CacheEvict` 原因落盘。每个此类非空 flush batch 的平均数据量约为
`61065 B`（约 `59.6 KiB`），接近当前 `64 KiB` 上限，payload 上限是强候选。

但现有 `CacheEvict` 仍不能区分以下触发条件：payload 上限、32 个交错 range 槽位上限、分配失败、大写直通，
或与已有 pending range 的顺序屏障。因此不能只凭该计数立即放大 sparse 缓冲。

### 2.3 `dentry_positive_hit=0` 需要解释，而非假定为 bug

```text
fsidx_hit=44631
dentry_positive_hit=0
dentry_negative_hit=3398
dentry_miss=4447
cached_parent_find=5795
root_find=4400
preserve_final_cache_hit=17456
```

`open()` 先查询完整路径 `FsIndex`，只有 full-path miss 后才会进入 cached-parent dentry 查询。因此正 dentry 零命中
至少可能表示：

1. 重复打开已经由 `FsIndex` 直接命中，dentry 没有查询机会；
2. 进入 dentry 查询的 child 名称大多是一次性临时文件；
3. 正项确实因 parent identity、失效、符号链接保护或插入时机而未能复用。

只有第 3 种才应修改 dentry 实现。

## 3. 已验证结论和禁做项

以下结论来自开发日志和对应 BuildStorm problem 复盘，下一轮必须遵守。

| 方向 | 已验证结论 | 本轮决策 |
| --- | --- | --- |
| 全局 lwext4 锁 | 后端不具备 SMP 并发安全保证 | 保留唯一 `EXT4_OP_LOCK`，不改 rwlock |
| `TaskMutex` / `PollSet` | 可睡眠等待、去重、FIFO 单唤醒已实现 | 无新 overflow/唤醒异常证据前不重构 |
| 页缓存 waiter | 同页加载 race 约 `2.4%~2.9%`，且有历史停滞 | 不引入 per-page single-flight/waiter |
| 顺序预读 | 大窗口试验会放大 read lock hold/wait | 保留当前有界预读，不继续扩大深度 |
| `lseek` 类型检查 | `seek_type` 已缓存，`type_check` 已降至 0 | 不再投入此路径 |
| artifact rename | 整挂载 `ext4_cache_flush()` 尖峰已移除 | 不重复修改 rename 路径 |
| sparse/direct `Kstat` | `fstat/statx` 必须报告真实 `st_blocks`、mtime/ctime | 不用 `known_size` 伪造或保留过期 metadata |
| 目录 metadata | ColdInode 已验证全部为目录 | 只保留按 directory epoch 的一次性 lookup stat 复用，不建持久目录 stat cache |
| quota 慢路径 | 首次写、ENOSPC、sparse/direct write 需要原有会计与发布语义 | 不将 quota 预留整体搬出 gate |
| metadata/namespace | 高值主要是实际 lwext4 调用，不是大块纯内存收尾 | 不按聚合桶猜测性缩锁 |

特别地，普通文件 stat cache 不能推广到目录；目录 mtime/ctime 会被子项 create/link/unlink/rename/symlink
以及目录自身 metadata 修改改变。sparse/direct write 后也不能保留旧 regular-file `Kstat`。

## 4. 下一轮执行计划

### P0：建立可重现的完整基线

此阶段不改内核语义。

1. 记录 `git rev-parse HEAD`、`git diff --stat`、`TARGET_ARCH`、QEMU 内存和 hart 数、raw 镜像路径、BuildStorm
   入口、overlay 路径、是否冷启动。
2. 使用 `/tmp` qcow2 overlay，不写入维护者的 `disk.img` 或基础 raw 镜像。
3. 外层运行窗口必须大于脚本内部 `timeout 14400`；外层 timeout 产生的中途日志不能作为性能结果。
4. 同时记录宿主 `/usr/bin/time` 的 wall/user/sys 时间和 guest 的
   `BUILDSTORM_COMPILE ... elapsed_s=...`。

`tmp_09.ans`、历史 `tmp_03.ans` 等文件名曾被复用，故日志文件名不能充当 A/B 身份；必须记录生成它的
kernel source snapshot 和 QEMU 配置。

### P1：先补齐低开销归因，不改变行为

先以固定时长 BuildStorm 诊断窗口获得决策证据。该窗口只用于局部归因，不报告端到端加速。

#### P1.1 dense write 快路径拒绝原因

在 `Ext4Inode::write_at()` 的现有快路径判定附近增加 `Relaxed` 聚合统计：

- fast attempt / success 的操作数和字节数；
- delayed-unlink 拒绝；
- `quota_reserved` 不足；
- `known_size` 未建立；
- dense cache 不存在；
- cache 无法表示本次写入：hole、超上限、策略禁用；
- cache 写入或分配失败。

不逐调用打印，不改变快路径资格或锁序。

判读规则：

- quota 不足主导：审计 reservation 生命周期、释放和 ENOSPC；不能直接移动 quota；
- cache miss/evict 主导：检查 LRU 准入和缓存生命周期，不能盲目扩容；
- sparse/hole 主导：进入 P2 sparse 方案，不能强行按 dense write 处理；
- fast success 已高但总 wait 不降：停止扩展 write fast path，转查其他 gate 入口。

#### P1.2 sparse flush 的触发条件和 batch 形状

在 `buffer_sparse_write_at()` 与 `flush_sparse_write_buffer()` 中分别统计：

- batch 数、range 数、字节数、每 batch 最大 range/bytes；
- `payload_limit`、`range_limit`、分配失败、大写直通、可见性边界各自的 batch 数和字节数；
- 每种原因是否实际进入 `ext4_fwrite`；
- 保留已有的 fstat/close/rename/truncate/cache-evict 原因统计。

所有计数仅在 perf feature 下使用 relaxed atomic。`fstat`、`statx`、close、rename、truncate、unlink、
`SEEK_DATA/SEEK_HOLE`、fsync/sync 的发布边界不得改变。

#### P1.3 dentry 的使用机会和失效原因

不先修改 `DENTRY_CACHE`，仅增加：

- full-path `FsIndex` 直接命中数；
- dentry 查询 eligible 数，以及因 `O_NOFOLLOW`/`O_UNLINK` 等语义 bypass 的次数；
- positive insert、positive lookup hit/miss；
- 精确失效、parent 失效、容量清理数；
- cached-parent 不可用而退回 root find 的原因。

目标是区分“dentry 未被使用但 `FsIndex` 已完成工作”与“正 dentry 的键、生命周期或失效策略错误”。

### P2：按 P1 证据只选择一个行为改动

#### 情形 A：payload 上限主导 sparse 回写

若多数 `CacheEvict` batch 可证实由 `64 KiB` payload 上限触发，则保持 32 个 range 槽位不变，先小步扩大
payload 上限，例如 `64 KiB -> 256 KiB`。

此改动必须同时具备全局 sparse-buffer 内存预算和明确回收策略，不能仅扩大每 inode 上限。回收后仍要保持
hole 布局、写入顺序和 last-write-wins 语义。

#### 情形 B：range 槽位主导 sparse 回写

若 32-run 上限主导，才仅增加 `MAX_SPARSE_WRITE_BUFFER_RUNS`，保持 payload 上限不变。这样只提高交错
`pwrite` 的容纳能力，不扩大单 inode 的字节上界。

#### 情形 C：dense write 快路径资格主导

若快路径主要被 quota/cache lifecycle 拒绝，只在维持 ENOSPC、delayed-unlink、rename、truncate、sparse-hole
语义的前提下调整对应的单一条件。cache miss、缓存初始化、淘汰写回和所有 lwext4 C API 仍必须走全局慢路径。

### P3：只有确认真实 dentry 失效后才修复 dentry

若 P1 证明正 dentry 已插入、存在可复用 child lookup，却因 parent object identity、错误失效或生命周期问题持续
miss，则修复对应键或失效路径，并回归：

- `O_NOFOLLOW`、内部 `O_UNLINK` 的末级符号链接语义；
- create/link/unlink/symlink/rename 后的 dentry 一致性；
- inode-number reuse 时的 `FsIndex` identity epoch 回退；
- 强引用缓存上限及回收行为。

若 P1 证明 full-path `FsIndex` 已覆盖重复打开，或者 dentry 查询本来就是一次性 child 名，则不对 dentry 做
性能修改，转入 P4 的具体 metadata/namespace 调用来源分析。

### P4：metadata/namespace 只按具体操作优化

`tmp_09.ans` 的分阶段统计中，`mode`、`owner`、`create`、`unlink` 都有明显耗时，但它们当前仍包含真实 lwext4
操作。后续只允许在拆分出具体 syscall、调用者、参数模式和底层调用后，选择能安全合并或消除的单一路径。

禁止按 `metadata` 或 `namespace` 聚合总量整体搬移路径缓存、alias、stat cache 或页缓存失效。

## 5. 验收标准

### 性能验收

完整 BuildStorm 仅以如下组合判定：

```text
BUILDSTORM_COMPILE mode=multi ok=true elapsed_s=<...>
#### OS COMP TEST GROUP END buildstorm ####
shutdown!
```

每个候选改动至少比较：

- 同配置完整 guest `elapsed_s` 和宿主 wall-clock；
- `ext4_read/write/find/fstat/metadata/namespace` 的 wait/hold；
- write cache hit/init/evict/direct/fast-hit；
- sparse flush 的 batch/reason/bytes；
- `panic`、`ERROR`、`TFAIL`、`TBROK`、Summary。

未完成的 `Building N/446` 只可用于判断某条局部假设，不能报告整体加速百分比。

### 功能回归

若进入 dense/sparse write 行为改动，最低覆盖：

- `mmap16`：连续写、容量、缓存和 ENOSPC；
- `lseek11`：`SEEK_DATA`/`SEEK_HOLE` 和 sparse extent；
- `fstat/statx`：`st_size`、`st_blocks`、mtime/ctime；
- write -> read、rename publish、truncate、unlink-open-write-close；
- `O_NOFOLLOW`/`O_UNLINK` 和深路径 `open14`。

所有代码改动至少执行：

```bash
make perf TARGET_ARCH=riscv64
make perf TARGET_ARCH=loongarch64
make TARGET_ARCH=riscv64
make TARGET_ARCH=loongarch64
```

RISC-V 是 BuildStorm 的运行主验证架构；LoongArch64 至少完成构建，相关文件系统语义变动再补定向 guest 回归。

## 6. 架构升级的触发条件

只有当 P1-P4 的局部可避免后端进入已经收敛，并取得完整同配置 BuildStorm 结果后仍接近或超过目标时，才将
lwext4 的单一非 SMP-safe gate 视为架构上限，评估后端深度改造或替换。

在获得并发安全证明前，禁止通过 rwlock、多 hart 并发调用 lwext4、无限扩大预读或重新引入 page-loading waiter
来规避该限制。
