# BuildStorm 优化方案

> 本文件只保留当前可执行计划、约束和验收边界。历史取证细节见
> [BuildStorm EXT4 稀疏写缓冲、顺序预读与锁统计收敛](./problem/buildstorm-ext4-sparse-write-readahead.md)、

> [文件页缓存容量旁路 mmap fault 修复](./problem/file-page-cache-capacity-bypass-mmap-fault.md)

## 1. 当前结论

- `riscv.ans` 是 RISC-V final-2026 BuildStorm 正式脚本的 02:37:57 样本。它只有
  `BUILDSTORM_TOOLCHAIN ok` 和 `BUILDSTORM_MINIBUILD ok`，没有 `BUILDSTORM_COMPILE`、测试组 END 或
  `shutdown!`，末尾为 `QEMU: Terminated`。最终 guest perf 为 `t=9477923ms`，Cargo 仅到
  `Building 97/446`，这是严重超时后的外层终止，不是完整评分结果。
- 可见进度证明后段已经进入不可接受的慢速区间：`t=1022915ms` 到 `52/446`，`t=9233695ms` 到
  `97/446`；52 个之后 8210.780 秒只新增 45 个，约 `0.33 crates/min`。按启动至 52 个的粗略观察值
  `3.05 crates/min` 比较，后段吞吐下降约 89%。其中 `cmake`、`aws-lc-sys(build.rs)` 等重型
  build-script/C 编译阶段会放大单个 crate 的耗时，因此 crate 数仍不是等量工作；但 2.6 小时只到 97/446
  已足以判定必须继续优化。
- 这份样本推翻了 `tmp_04` 中“页缓存尚未触顶”的前提。全局文件页缓存第一次触顶出现在
  `t=4771219ms`，`resident_pages=98304/98304`、`capacity_bypass_pages=14`；末尾变为
  `capacity_bypass_pages=83287`。此前 mmap 容量旁路 SIGSEGV 已修复，说明旁路路径功能上可运行；但大量
  cold mmap/read 页无法发布到全局缓存，后续重复访问必须回源到 lwext4，是当前最高优先级的性能证据。
- `EXT4_OP_LOCK` 仍是第二个核心瓶颈。末尾累计 wait/hold 不能与 wall-clock 相加，但分类比例很清楚：
  `ext4_read_lock=11420.438s/1026.372s`、`ext4_write_lock=16130.857s/1009.734s`、
  `ext4_find_lock=3507.436s/1106.775s`、`ext4_fstat_lock=1042.917s/411.440s`、
  `ext4_namespace_lock=1315.448s/745.371s`。公平 gate 的累计守恒正常：
  `queued=227393`、`handoffs=227393`、`cancelled=0`、`queue_depth=0`，但
  `max_handoff_wait_us=408077260` 且 `wait_ge_10s=173`，说明公平交接没有丢唤醒，却仍被长事务/缓存缺失造成的排队放大。
- 因此下一轮不应撤销 FIFO 公平 gate、不应把 lwext4 改成并发进入，也不应只盯 rename 或目录 epoch。优先顺序调整为：
  先验证并降低文件页缓存容量旁路，再补齐 lwext4 子阶段 interval delta；若缓存旁路收敛后 gate 仍长期排队，再对
  具体长 transaction 做局部优化。

## 2. 已固定优化

| 阶段 | 状态 | 保留结论 |
| --- | --- | --- |
| P1 写路径 | 已实施 | write quota 移出 EXT4_OP_LOCK；write open/data 锁拆分；unlink/drop 中 MNT_TABLE 与 EXT4_OP_LOCK 不再反向嵌套。 |
| P4/P5 dentry/stat | 已实施 | 正 dentry 被 FsIndex path 命中绕过，不恢复正向 dentry fast path；负 dentry 保留；目录 stat cache 受 epoch 保护。 |
| P9 文件页缓存 | 已实施，需 P19A 复核容量策略 | regular-file read 准入为 32 MiB，全局页缓存为 96K 页；容量满时直读/直装但不发布，不能返回 ENOMEM 或旧数据。`riscv.ans` 已证明 96K 页会触顶并产生 83K+ bypass，容量不再视为固定结论。 |
| P10/P11 读来源 | 已实施 | inode_read_source 覆盖 mmap fill、page-cached cold run、direct bypass、other；未对齐 ELF 段改为最大 64 KiB 分块读。 |
| P12/P13 mmap | 已实施 | mmap 来源拆分 demand/prefetch；EOF 检查改为页偏移与 inode.size() 判断，避免普通 fault 的重复页缓存查询。 |
| P15/P15.1/P15.2 目录 epoch | 已实施，已有方向性运行期证据 | 目录自身 metadata 和普通文件 namespace 失效使用 inode/父目录局部 epoch；`tmp_04` 已输出 `local_updates=884/global_fallbacks=0`、`global_epoch_miss=96`，但 rename/rmdir 语义回归和同配置完整验收仍待完成。 |
| P16 create 路径 | 已实施 | perf 报告增加 interval delta/create 子阶段；新 inode 的 mode/owner 合并为一次路径事务，root 0/0 owner 省略；普通文件和目录以底层原子 `O_EXCL` 创建，删除重复 exist check。 |
| P17 rename 写回归因 | 已实施 | 写回拆为 sparse flush、dense byte-cache 与 path-cache discard；记录子阶段 total/max、实际提交字节及零字节快路径，不改 rename 顺序或锁边界。 |
| P18.1 EXT4 gate 公平交接 | 已实施，待完整长测/压力回归 | mount-wide gate 使用 FIFO ticket handoff；有队列时禁止 fast-path 插队，支持取消和任务退出清理。`riscv.ans` 的累计守恒闭合，但 `max_handoff_wait_us=408077260`、`wait_ge_10s=173` 表明公平性正确不等于吞吐足够，后续应缩短事务或减少回源。 |
| P18.2 创建事务与结果复用 | 已实施，待完整长测/语义回归 | lwext4 在创建 transaction 内写入最终 mode/uid/gid，成功后直接复用 `child_ref` 初始化 handle 并返回 stat；`tmp_04` 仍为 `regular_no_lookup_stat=0`，新建普通文件不再立即 pathname fstat。 |
| BuildStorm 入口 | 已调整 | RUST_MIN_STACK=33554432 避免 tmp_07 的 rustc 栈不足崩溃；initproc 当前为直接运行 buildstorm::compile::run() 的定向入口。 |

## 3. 不变约束

- EXT4_OP_LOCK 继续串行化所有 lwext4 block cache 与 path/file C API；不改 rwlock，不允许多 hart 并发进入 lwext4。
- 保持锁序简单：write_state -> io_state -> EXT4_OP_LOCK；不得在持有 MNT_TABLE 时获取 EXT4_OP_LOCK，也不得反向嵌套。
- P9 参数不再一律冻结：保持 32 MiB 文件准入和四页预读作为基线；全局容量或淘汰策略可以做受控 A/B，因为
  `riscv.ans` 已证明 96K 页容量触顶。任何改动都必须同时证明没有 OOM、旧数据、SIGSEGV/SIGBUS 或脏页丢失。
- 不牺牲文件系统语义：quota reserve/rollback、ENOSPC 小 chunk 回退、sparse overlay、st_blocks、mtime/ctime、
  rename/truncate/unlink/write 的 cache 失效必须保持。
- 未出现完整结束标记前，所有定时样本只可用于方向性取证，不能报告端到端加速。

## 4. 下一轮 P19A/P19B/P20 与保留验收

### P15：目录 epoch 仅补语义回归，不再作为吞吐主线

1. `tmp_04` 已覆盖父目录局部更新分支：`local_updates=884`、`global_fallbacks=0`，且
   `global_epoch_miss=96`。该结果支持 P15.1/P15.2 的失效范围收敛，但由于与 `tmp_13` 不同运行不可做端到端
   A/B，不再为降低 global miss 单独改缓存策略。
2. 补目录 rename 覆盖、rmdir/unlink 后仍被打开的目录 fd、未缓存父目录 fallback、hard link 和并发 stat
   回归；只有证明错误时才调整失效边界，保持 inode identity epoch 与 cache 一致性约束不变。

### P18.1/P18.2：保留实现，补完整及压力验收

1. 公平 gate 继续仅作用于 `EXT4_OP_LOCK`，不改为 rwlock，不放宽 lwext4 block cache/path/file C API 的单线程
   串行要求，锁序仍为 `write_state -> io_state -> EXT4_OP_LOCK`。
2. 对 P18.1 补无竞争 fast path、64+ waiter、队首取消/退出、跨 hart 连续交接和持锁任务被抢占回归；完整运行中
   检查累计 `queued = handoffs + cancelled + queue_depth`，而不以 Relaxed interval 快照的瞬时队深做守恒判断。
3. 对 P18.2 补新建文件/目录、既有目标 `EEXIST`、非 root、S_ISGID、ENOSPC 回滚，以及新建后立即 stat/read/close。
   `regular_no_lookup_stat=0` 只证明普通创建免首次 pathname fstat，不替代这些语义回归。

### P18.3：受限 rename dense-cache re-key（继续降低优先级）

1. 已知 rename dense write-back 有可观累计成本，但 `riscv.ans` 末尾 rename 样本很少；在 P19B 指明后段
   长持锁主要来源前，不把 re-key 作为解释 52 -> 97 低吞吐的单一修复。
2. 若后续 interval 证明它重新主导，只对可证明单链接的 regular file 启用：成功后在既有
   `CACHE_TABLE/FIFO_TABLE` 锁序下原子 re-key source cache，丢弃覆盖 target cache；失败、hardlink 或所有权不明
   均保持现有写回后 rename。先完成 rename 覆盖、rename 后 read/exec、旧 fd 继写、fsync/sync、
   unlink-open-close 回归。

### P19A：文件页缓存容量旁路复核（下一项优先内核工作）

1. 先做最低风险容量 A/B：只调整 `MAX_FILE_PAGE_CACHE_PAGES`，保持 32 MiB 文件准入和四页预读不变。建议比较
   96K、192K、256K 页三个点（约 384 MiB、768 MiB、1 GiB）。RISC-V 当前 QEMU 内存为 16 GiB，LoongArch64 为
   36 GiB；若 192K 已显著降低 bypass 且无内存压力，不直接跳到更大值。
2. 每个点记录 `resident_pages/capacity_bypass_pages`、`file_cache_source`、`load_attempts/load_races`、
   `inode_read_source`、`ext4_read_data_lock`、`syscall_read/read_active` 和固定 Cargo 检查点
   `52/64/85/97/120/150/446`。目标不是让 resident 越大越好，而是证明 bypass 降低能转化为更少回源、更低 gate
   wait/hold 和更快 wall-clock。
3. 如果单纯增大容量只能短暂推迟触顶，先补引用状态取证，再实现低风险淘汰：只淘汰已证明 clean、非 dirty、
   未被活动 VMA 引用且可从全局索引移除的页。不能仅凭 `Arc` 尚存就推断 mmap 一致性；若无法可靠证明没有映射，
   该页保持不淘汰。dirty、sparse write overlay、rename/truncate/unlink 相关页继续按现有失效/写回边界处理。
   不要在淘汰路径进入 lwext4，不要在 `MemorySet` 写锁内做文件 I/O。
4. 不优先扩大 per-file 32 MiB 准入或预读窗口。只有当 `inode_read_source` 证明大文件单次顺序 walk 仍主导，
   且容量/淘汰已经解决全局 bypass 后，才考虑文件级准入或 readahead 状态机。

### P19B：为 lwext4 子阶段增加 interval delta

1. `report.rs` 已对各 `ext4_*_lock` 输出 interval wait/hold，但 `ext4_write_duration`、rename write-back、
   namespace/create/unlink、metadata、fstat stage 仍只输出累计 total/max。为这些现有 `samples/ticks` 增加与
   `DurationDelta` 同样的低开销 delta，报告 `samples/total_us`；不逐调用打印，不改变锁、缓存或文件系统语义。
2. 以 `t≈4771s`（缓存首次触顶）、`t≈6337s`（85/446）、`t≈8649s`（95/446）、
   `t≈9234s`（97/446）和末尾 `t≈9478s` 的 30--90 秒窗口为主，在同类操作中比较每次持锁和子阶段平均值。
   若某个 C 层阶段在低吞吐窗口占据 gate hold，再细分 `transaction`、path lookup、directory scan、block allocation、
   journal commit 与 block-cache flush；没有该证据时不移动 VFS 代码出锁，也不提高 BuildStorm 并发度。
3. 优先目标是缩短已获得 gate 后的长 transaction 或减少触发 transaction 的回源次数，而非降低 FIFO 公平性。
   `riscv.ans` 的最大 handoff wait `408.077s` 是排队结果，不能通过允许新请求插队来“优化”。

### P20：固定环境的端到端归因与验收

1. 使用同一 commit、同一 `kernel-rv`/根文件系统、同一 QEMU 参数和相同冷启动状态，连续至少两次完整
   BuildStorm；记录外部 wall-clock 与 `BUILDSTORM_COMPILE mode=multi ok=true elapsed_s=...`。只有出现测试组 END
   和 `shutdown!` 才比较总耗时。
2. 同时记录 Cargo 的活跃 crate/build-script 名称和固定检查点 `52/446`、`64/446`、`85/446`、`97/446`、
   `120/446`、`150/446`、`446/446` 的 guest `t=`；将 crates/min 仅用作同一 DAG 阶段内的辅助观测。
   重型 `cmake`/C 编译与 Rust crate 不能按一个 crate 计为等价工作。
3. 将 P19A/P19B 的容量与 interval delta 对齐：若 bypass 降低后 wall-clock 和 gate wait 明显下降，保留缓存策略；
   若 bypass 已收敛而 gate 仍忙，继续优化对应 lwext4 子阶段；若 gate 已不忙而 Cargo 仍停在重型 build script，则内核不应
   背负该段 wall-clock，应另行取证编译器 CPU/外部 I/O。

## 5. 验收边界

构建与静态检查：

    cargo fmt --manifest-path os/Cargo.toml --all -- --check
    git diff --check
    make perf TARGET_ARCH=riscv64
    make perf TARGET_ARCH=loongarch64
    make TARGET_ARCH=riscv64
    make TARGET_ARCH=loongarch64

运行期验收必须看测试自身结束，而不是外层 timeout：

    BUILDSTORM_COMPILE mode=multi ok=true elapsed_s=<...>
    #### OS COMP TEST GROUP END buildstorm ####
    shutdown!

P19A/P19B/P20 的性能结论还必须同时满足：同一 commit/镜像/QEMU 参数和冷启动状态至少完成两次；保留
`t≈1023s`、`t≈4771s`、`t≈6337s`、`t≈8649s`、`t≈9234s`、`t≈9478s` 附近的 Cargo 活跃 crate、
页缓存容量、inode read source、EXT4 gate 和 interval delta；使用 `/usr/bin/time` 记录宿主 wall-clock。
仅看到 `Building N/446`、外层 timeout，或不同 DAG 阶段的 crates/min，都不能声明端到端加速或回归比例。

如果下一轮改动触及写入、rename、truncate、unlink、mmap 或 stat 语义，还需补定向回归：

- mmap16、lseek11 的 SEEK_DATA/SEEK_HOLE；
- fstat/statx 的 st_blocks、mtime/ctime；
- write-read、rename、truncate、unlink-open-write-close、fsync/sync；
- 文件映射部分尾页、完整越界页和并发 truncate 的 SIGBUS。
- 文件页缓存容量旁路定向 case：小容量 `file-cache-capacity-test`、动态 ELF exec、mmap fault、MAP_SHARED fork
  预取页传递，以及触顶后的 read/mmap 不返回旧数据、不 SIGSEGV。

公平锁改动还必须验证：无竞争 fast path、64 个以上 waiter、队首任务取消/退出、跨 hart 连续交接，以及
持锁任务被抢占时没有 lost wakeup 或永久 reservation。
