## 1. 当前结论

### 1.1 `tmp_02.ans` 当前基线（2026-08-02）

- 这是 RISC-V `riscv-virtio,qemu`、8 HART 的 BuildStorm 样本。日志只确认
  `BUILDSTORM_TOOLCHAIN ok` 和 `BUILDSTORM_MINIBUILD ok`，末尾 guest 时间为 `t=593195ms`（约 9.9 分钟），
  Cargo 到 `Building 40/446`；没有 `BUILDSTORM_COMPILE`、测试组 END、`shutdown!` 或 `QEMU: Terminated`。
  因此它是未完成的方向性样本，不是端到端成绩。
- 约 `t=95881ms` 的 interval 首次出现 gate 排队：`queued=3064`、`handoffs=3064`；
  `t=169103ms` 已累计 `queued=6568`、`handoff_wait_us=208632388`。末尾累计公平 gate 为
  `queued=36660`、`handoffs=36658`、`cancelled=0`、`queue_depth=2`，守恒闭合；但
  `handoff_wait_us=2115644661`（约 2115.6 秒）、`max_handoff_wait_us=16650130`（约 16.65 秒）、
  `wait_ge_10s=8`，说明 FIFO 交接没有丢唤醒，吞吐却被长事务和高并发等待拖慢。
- 末尾锁分类的等待/持有累计为：`ext4_read_lock=600.824s/56.811s`（33493 次）、
  `ext4_write_lock=936.287s/71.806s`（25282 次）、`ext4_find_lock=246.151s/72.252s`（13161 次）、
  `ext4_fstat_lock=71.766s/28.050s`（1716 次）。读数据锁等待 `584.879s`、写数据锁等待 `438.269s`，
  优先级明显高于 quota（`ext4_write_duration quota=0.015s`）。这些是跨任务累计值，不能与 593.195 秒 guest
  wall-clock 相加。
- 文件页缓存在整个样本中没有触顶：末尾 `resident_pages=63298/196608`、
  `capacity_bypass_pages=0`、`evictions=0`。mmap 来源为 `mmap_cache_fill=21175` 次/约 202.8 MiB，
  page-cached cold run 为 `10590` 次/约 110.6 MiB，只有 58 次 direct bypass；本轮没有为 P19A 提供容量压力证据。
  `load_races=404` 需要保留为一致性观察项，但不能据此调高容量或预读窗口。
- syscall 累计时间也与 gate 争用一致：`read=693.278s`、`write=1008.762s`、`open=304.795s`、
  `stat=426.208s`、`path=285.969s`。`pipe_read_wait=825.329s/162`（最大约 24.8 秒），而
  `scheduler_dispatch=2.168s/466943`，因此调度器不是下一轮主目标；管道等待先做生产者/消费者归因，不能直接当作
  内核锁瓶颈。

### 1.2 `tmp_03.ans` 一小时停滞证据（2026-08-02）

- 这是同一 RISC-V、8 HART 配置的约 55.4 分钟样本。日志仍只有
  `BUILDSTORM_TOOLCHAIN ok` 和 `BUILDSTORM_MINIBUILD ok`，没有 `BUILDSTORM_COMPILE`、测试组 END、
  `shutdown!`；末尾为 `QEMU: Terminated`，没有 panic、TFAIL、TBROK 或 SIGSEGV。因此它证明的是未完成运行中的
  停滞，不是完整成绩或单独的功能失败。
- `t=3021715ms` 的最后一个有实际 syscall/EXT4 进展的窗口中，gate interval 为
  `queued=235/handoffs=229/queue_depth=6`，同时主分类 interval 已很小；到 `t=3075042ms`，syscall 仅从
  `959019` 增至 `959050`，所有 `interval_ext4_lock` 和 `interval_ext4_gate` 的新增计数都为 0，队列仍为 6。
  之后只有 idle scheduler interval，末尾又有一个 waiter 到达 7。
- 累计 gate 为 `queued=46288`、`handoffs=46281`、`cancelled=0`、`queue_depth=7`，满足
  `queued = handoffs + cancelled + queue_depth`。这排除了简单的票据丢失，但不能解释为什么队首长期无法获取；
  公平 handoff 计数的守恒不等于 owner 生命周期已正确闭环。
- 页缓存仅 `resident_pages=85486/196608`，`capacity_bypass_pages=0`，所以本轮不继续调容量、CLOCK 或预读。
  重点转为 gate 的 owner 生命周期和唤醒链：发散的 `exit_current_and_run_next()` 不保证活跃
  `Ext4OpGuard` 执行 `Drop`，旧退出清理只移除排队票据，可能留下 `held=true` 并永久阻塞后续 waiter。
  这是与代码路径一致的待证伪假设，不是由 `tmp_03` 单独证明的唯一根因。

### 1.3 与历史长样本的关系

- 先前的 `riscv.ans` 确实在 `resident_pages=98304/98304` 后出现大量 capacity bypass，这仍是 P19A 的安全性和满载压力
  验收依据；但 `tmp_02.ans` 在同一生产容量下未触顶，不能把两份运行的 crates/min 或 wall-clock 直接比较。
- 下一轮主线从“继续调页缓存容量”切换为“先解释 EXT4 gate 持有时间和等待来源，再做单一长 transaction 优化”。
  不撤销 FIFO gate、不放宽 lwext4 单线程约束，也不恢复正向 dentry fast path；rename re-key 和目录 epoch 仅在新的
  interval 证据重新占主导时推进。

## 3. 不变约束

- EXT4_OP_LOCK 继续串行化所有 lwext4 block cache 与 path/file C API；不改 rwlock，不允许多 hart 并发进入 lwext4。
- 保持锁序简单：write_state -> io_state -> EXT4_OP_LOCK；不得在持有 MNT_TABLE 时获取 EXT4_OP_LOCK，也不得反向嵌套。
- P9 保持 32 MiB 文件准入、四页预读与 192K 页经验容量；当前优化对象是满载后的安全回收与候选退避，而非继续调
  `MAX_FILE_PAGE_CACHE_PAGES`。任何改动都必须同时证明没有 OOM、旧数据、SIGSEGV/SIGBUS 或脏页丢失。
- 不牺牲文件系统语义：quota reserve/rollback、ENOSPC 小 chunk 回退、sparse overlay、st_blocks、mtime/ctime、
  rename/truncate/unlink/write 的 cache 失效必须保持。
- 未出现完整结束标记前，所有定时样本只可用于方向性取证，不能报告端到端加速。

## 4. P19A/P19B/P19C/P20 与下一轮计划

### P15：目录 epoch 仅补语义回归，不再作为吞吐主线

1. `tmp_04` 已覆盖父目录局部更新分支：`local_updates=884`、`global_fallbacks=0`，且
   `global_epoch_miss=96`。该结果支持 P15.1/P15.2 的失效范围收敛，但由于与 `tmp_13` 不同运行不可做端到端
   A/B，不再为降低 global miss 单独改缓存策略。
2. 补目录 rename 覆盖、rmdir/unlink 后仍被打开的目录 fd、未缓存父目录 fallback、hard link 和并发 stat
   回归；只有证明错误时才调整失效边界，保持 inode identity epoch 与 cache 一致性约束不变。

### P18.1/P18.2：保留实现，补完整及压力验收

1. 公平 gate 继续仅作用于 `EXT4_OP_LOCK`，不改为 rwlock，不放宽 lwext4 block cache/path/file C API 的单线程
   串行要求，锁序仍为 `write_state -> io_state -> EXT4_OP_LOCK`。
2. 对 P18.1 补无竞争 fast path、64+ waiter、队首取消/退出、跨 hart 连续交接和持锁任务被抢占回归；完整运行中
   检查累计 `queued = handoffs + cancelled + queue_depth`，而不以 Relaxed interval 快照的瞬时队深做守恒判断。
3. 对 P18.2 补新建文件/目录、既有目标 `EEXIST`、非 root、S_ISGID、ENOSPC 回滚，以及新建后立即 stat/read/close。
   `regular_no_lookup_stat=0` 只证明普通创建免首次 pathname fstat，不替代这些语义回归。
4. `tmp_03` 的停滞窗口需单独验收 gate owner 生命周期。退出汇合点先按 TID 移除排队票据；若退出任务正是
   `owner_tid`，同时清除逻辑 `held`、清除 owner 诊断状态并唤醒 FIFO 队首。下一轮日志必须检查：
   `owner_tid`、`owner_hold_us`、`owner_exit_releases`，以及累计
   `queued = handoffs + cancelled + queue_depth`。若停滞时 `owner_tid != 0` 且 `owner_hold_us` 持续增长，
   继续沿具体持锁 lwext4 子阶段分段；若 `owner_tid=0` 而 `queue_depth>0`，优先排查队首 waker/ready queue。

### P18.3：受限 rename dense-cache re-key（继续降低优先级）

1. 已知 rename dense write-back 有可观累计成本，但 `riscv.ans` 末尾 rename 样本很少；在 P19B 指明后段
   长持锁主要来源前，不把 re-key 作为解释 52 -> 97 低吞吐的单一修复。
2. 若后续 interval 证明它重新主导，只对可证明单链接的 regular file 启用：成功后在既有
   `CACHE_TABLE/FIFO_TABLE` 锁序下原子 re-key source cache，丢弃覆盖 target cache；失败、hardlink 或所有权不明
   均保持现有写回后 rename。先完成 rename 覆盖、rename 后 read/exec、旧 fd 继写、fsync/sync、
   unlink-open-close 回归。

### P19A：文件页缓存满载候选退避（已实施，待长测）

1. 生产容量固定为 `192 * 1024` 页（768 MiB），不再将 `MAX_FILE_PAGE_CACHE_PAGES` 当作性能调参主线；32 MiB
   文件准入和四页预读保持不变。显式 feature `file-cache-capacity-test` 固定为 2,048 页，仅用于放大满载行为。
2. clean-page CLOCK 使用 `referenced` 二次机会，且只在 `!dirty`、`Arc<FilePage>::strong_count == 1`、
   `Arc<FrameTracker>::strong_count == 1` 时从全局索引移除。后两项不能省略：mmap VMA 持有的是 frame 引用。
   淘汰路径不进入 lwext4，也不在 `MemorySet` 写锁内做文件 I/O。
3. 候选改为两条仅保存 `FilePageKey` 的 FIFO 队列。新页与二次机会页保留在 `active`；dirty 或 `in_use` 页移到
   `deferred`，不再反复占用 128 项 CLOCK 扫描预算。`active` 耗尽后设置 256 次容量 miss 冷却；到期只把 16 个
   deferred 项移回 active 复检。失效路径同步删除两条队列的键，锁序固定为 `pages -> eviction_queues`。
4. 旧 2K 样本在 `t=31.289s` 已有 `capacity_bypass_pages=25790`、`eviction_scans=3240417`，约每个 bypass
   125.6 次检查；在 `t=261.966s` 时 25,650,541/25,690,228 次扫描为 `in_use`。本轮同 feature 的 60 秒运行在
   `t=33.816s` 记录 `bypass=35318`、`scans=17232`、`in_use=4064`、`deferred_retry_pages=2016`、
   `cooldown_bypasses=32414`，扫描均摊低于 0.49 次/bypass。该值证明退避生效，不是完整 BuildStorm wall-clock 结论。
5. 旧样本约 `t=161.948s` 后才开始出现 rustc SIGSEGV；本轮 60 秒样本只到 `BUILDSTORM_TOOLCHAIN ok`，没有覆盖该
   阶段。不能因扫描下降就宣称 SIGSEGV 已修复，也不使用 `RUST_MIN_STACK` 规避。下一份长测必须保留 fault 的
   `scause/stval` 或同等内核证据，单独确认其归因。
6. 不优先扩大 per-file 32 MiB 准入或预读窗口。只有 `inode_read_source` 证明大文件单次顺序 walk 仍主导，且
   回收/退避后的 bypass 与 gate 指标均不再主导时，才考虑文件级准入或 readahead 状态机。

### P19B：为 lwext4 子阶段增加 interval delta

1. 已在 perf 报告中补齐 write open/quota/data、fstat actual/inner、rename write-back 和 namespace
   create/unlink 的 interval delta；每次报告输出窗口 `samples/total_us`，并保留累计 `max_us` 作为长尾参考。
   统计使用 relaxed atomic 快照，不逐调用打印，不改变锁、缓存或文件系统语义。
2. 本轮 120 秒 RISC-V 冒烟已输出 `interval_ext4_phase`：约 `t=102999ms` 的窗口中
   `write_open=60`、`write_data=85`，下一窗口为 `write_open=37`、`write_data=1306`；该输出证明埋点和
   新 fast path 均生效，但由于不是同一冷启动 A/B，不报告端到端加速。固定复现时保留
   `t≈95881ms`、`127447ms`、`169103ms`、`259005ms`、`315205ms`、`421834ms`、
   `498261ms`、`531571ms` 和 `593195ms` 的 30--90 秒窗口。第一轮只比较各类平均 hold/wait 与
   `write_duration(data/open/quota)`、`fstat_inner`、`namespace(create/unlink)`、`rename dense_write_back`；
   不把不同 Cargo DAG 阶段的 crate 数当作等量工作。
3. 若某个 C 层阶段在 gate hold 中占主导，再在该阶段内细分 `transaction`、path lookup、directory scan、block
   allocation、journal commit 和 block-cache flush；没有该证据时不把 VFS 代码移出锁、不放宽 lwext4 串行约束，也不提高
   BuildStorm 并发度。`tmp_02` 的 `write_duration data=494.488s` 而 quota 仅 `0.015s`，下一轮先验证 data 阶段，
   不再优化 quota。

### P19C：`tmp_02` 指向的 gate 长事务归因与单变量优化

1. **已完成一次低风险重复准入优化。** `write_at_impl()` 在 `write_state`/`io_state` 下已能确认同一
   `Ext4File` 的 O_RDWR 描述符和 `known_size`；新增 `is_open_for_write()`，在此条件下跳过只会执行
   `ensure_open()` no-op 的 `EXT4_OP_LOCK.lock_for_write_open()`，首次打开或必须探测大小时仍保留原 gate。
   该改动只减少 FIFO ticket，不放宽 lwext4 的单线程边界；下一轮需用同一镜像、冷启动和 workload 对比
   `write_open_lock` 样本/等待、`write_data_lock` 等待及 gate handoff。
2. **读/写 data 优先。** 先用 P19B 的 interval delta 将 `ext4_read_data_lock` 的 `584.879s` 等待、
   `48.489s` 持有与 `ext4_write_data_lock` 的 `438.269s` 等待、`55.830s` 持有对齐到实际 read/write bytes、
   page-cache miss、sparse/direct 分支和底层 C 调用。若等待占比仍高，优化重复进入 gate、批量化同一 inode 的连续操作或
   减少回源；若持有占比高，只改一个已证实的 C 层子阶段，并保留 `write_state -> io_state -> EXT4_OP_LOCK` 锁序。
3. **find/fstat 次之。** `ext4_find_lock` 等待/持有为 `246.151s/72.252s`，`ext4_fstat_lock` 为
   `71.766s/28.050s`。`fsidx_hit=57589`、`path_index_hit=36216`、`dentry_miss=4775`，说明不能凭直觉恢复正 dentry
   快路径；先定位剩余 miss 是否重复 pathname lookup 或被 gate 排队放大。目录 epoch 仅有 `global_epoch_miss=98`，除非新
   语义回归发现错误，不再为降低该计数单独改失效范围。
4. **管道等待只做归因。** `pipe_read_wait=825.329s/162`、最大约 24.8 秒，明显高于 scheduler dispatch 的
   `2.168s`；增加 producer/consumer、poll/wakeup 和 recheck 的窗口关联，确认它是 BuildStorm 子进程同步还是内核
   丢唤醒。未证明是锁等待前，不修改 pipe 唤醒或调度策略。
5. **低优先级项目暂缓。** `rename` 仅 61 次、dense write-back 约 `14.014s`，create/unlink 分别约 `32.953s/18.971s`；
   P18.3 re-key 只有在新的 interval 证明 rename 重新主导时才实施，并先完成旧 fd、hard link、fsync/sync 和覆盖目标回归。
   页缓存容量、预读窗口和公平 gate 本身不作为本轮调参变量。

### P20：固定环境的端到端归因与验收

1. 使用同一 commit、同一 `kernel-rv`/根文件系统、同一 QEMU 参数和相同冷启动状态，连续至少两次完整
   BuildStorm；记录外部 wall-clock 与 `BUILDSTORM_COMPILE mode=multi ok=true elapsed_s=...`。只有出现测试组 END
   和 `shutdown!` 才比较总耗时。
2. 同时记录 Cargo 的活跃 crate/build-script 名称和固定检查点 `1/446`、`10/446`、`20/446`、`30/446`、
   `40/446`、`52/446`、`64/446`、`85/446`、`97/446`、`120/446`、`150/446`、`446/446` 的 guest `t=`；
   将 crates/min 仅用作同一 DAG 阶段内的辅助观测。重型 `cmake`/C 编译与 Rust crate 不能按一个 crate 计为等价工作。
3. 将 P19A/P19B/P19C 的容量、回收、inode read source、gate wait/hold、pipe wait 和子阶段 delta 对齐：
   若 `capacity_bypass=0` 而 gate 仍忙，继续优化对应 lwext4 子阶段；若 gate 已不忙而 Cargo 仍停在重型 build script，
   则内核不应背负该段 wall-clock，应另行取证编译器 CPU/外部 I/O。

## 5. 验收边界

构建与静态检查：

    cargo fmt --manifest-path os/Cargo.toml --all -- --check
    git diff --check
    make perf TARGET_ARCH=riscv64
    make perf TARGET_ARCH=loongarch64
    make TARGET_ARCH=riscv64
    make TARGET_ARCH=loongarch64

运行期验收必须看测试自身结束，而不是外层 timeout：

    BUILDSTORM_COMPILE mode=multi ok=true elapsed_s=<...>
    #### OS COMP TEST GROUP END buildstorm ####
    shutdown!

P19A/P19B/P19C/P20 的性能结论还必须同时满足：同一 commit/镜像/QEMU 参数和冷启动状态至少完成两次；保留
`tmp_02` 对应的 `t≈95881ms`、`127447ms`、`169103ms`、`259005ms`、`315205ms`、`421834ms`、
`498261ms`、`531571ms`、`593195ms` 附近的 Cargo 活跃 crate、页缓存容量、
`eviction_scans/deferred_retry_pages/cooldown_bypasses`、inode read source、EXT4 gate、pipe wait 和 interval delta；
公平 gate 还必须保留 `owner_tid/owner_hold_us/owner_exit_releases`，并核对退出回收后队列是否继续交接；
使用 `/usr/bin/time` 记录宿主 wall-clock。仅看到 `Building N/446`、外层 timeout，或不同 DAG 阶段的 crates/min，
都不能声明端到端加速或回归比例。

如果下一轮改动触及写入、rename、truncate、unlink、mmap 或 stat 语义，还需补定向回归：

- mmap16、lseek11 的 SEEK_DATA/SEEK_HOLE；
- fstat/statx 的 st_blocks、mtime/ctime；
- write-read、rename、truncate、unlink-open-write-close、fsync/sync；
- 文件映射部分尾页、完整越界页和并发 truncate 的 SIGBUS。
- 文件页缓存容量旁路定向 case：小容量 `file-cache-capacity-test`、动态 ELF exec、mmap fault、MAP_SHARED fork
  预取页传递，以及触顶后的 read/mmap 不返回旧数据、不 SIGSEGV；同时检查 `in_use` 饱和后扫描数不再按
  `128 * capacity_bypass_pages` 增长。

公平锁改动还必须验证：无竞争 fast path、64 个以上 waiter、队首任务取消/退出、跨 hart 连续交接，以及
持锁任务被抢占时没有 lost wakeup 或永久 reservation。
