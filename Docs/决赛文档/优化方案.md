# BuildStorm 当前优化路线图

> 状态：sparse 写缓冲的容量归因、两步有界扩容和 dense write 快路径归因均已完成。当前基线为
> `512 KiB` per-inode sparse payload、32 个 run、8 MiB 全局预算；后续优先验证该基线并解释
> `dentry_positive_hit=0`，不再继续扩大 sparse 阈值。
>
> 2026-07-30：`tmp_15.ans` 与 `log.ans` 的十分钟窗口确认 sparse 工作量一致，`41/446` 与 `38/446`
> 的差异属于锁/调度交错；dentry 仍无正命中。已按 P3 将 create 后的 mode/owner 初始元数据合并到
> ext4 的连续 namespace 操作锁区间，待同配置新样本验证其收益。
>
> 适用证据：2026-07-29 工作区，维护者提供的同入口十分钟窗口 `tmp_09.ans` 至 `tmp_13.ans`，以及
> [sparse 写复盘](./problem/buildstorm-ext4-sparse-write-readahead.md) 和开发日志中的已验证结论。

## 1. 当前基线与证据边界

维护者确认 `tmp_09.ans` 至 `tmp_13.ans` 均为相同的十分钟 BuildStorm 运行窗口。因此末尾
`Building N/446` 可以作为该固定窗口内的 Cargo 编译吞吐指标，用于比较本计划中的局部改动；它不是完整
BuildStorm 的 `elapsed_s`，不能外推为总编译时长、评分或端到端加速比例。

所有样本都只有 `BUILDSTORM_TOOLCHAIN/MINIBUILD ok`，没有：

```text
BUILDSTORM_COMPILE mode=multi ok=true elapsed_s=...
#### OS COMP TEST GROUP END buildstorm ####
shutdown!
```

因此完整性能结论仍须使用同一 source snapshot、镜像、内存、hart 数和缓存起始状态下的完整运行。

### 已接受的 sparse 基线

| 样本 | sparse payload | 末尾 `Building` | sparse batch | 容量回写 batch | 结论 |
| --- | ---: | ---: | ---: | ---: | --- |
| `tmp_10.ans` | `64 KiB` | `14/446` | 439 | 427 | payload limit 为 422 个容量 batch 的主因 |
| `tmp_11.ans` | `256 KiB` | `27/446` | 139 | 125 | 第一阶段有界扩容有效 |
| `tmp_12.ans` | `256 KiB` + 临时诊断 | `17/446` | 120 | 108 | 诊断落在写热路径，不能作为 P2 A/B 结果 |
| `tmp_13.ans` | `512 KiB` | `32/446` | 77 | 63 | 当前接受的固定窗口基线 |

当前实现保持：

- `MAX_SPARSE_WRITE_BUFFER_SIZE = 512 KiB`；
- `MAX_SPARSE_WRITE_BUFFER_RUNS = 32`；
- `MAX_TOTAL_SPARSE_WRITE_BUFFER_BYTES = 8 MiB`。

`tmp_13.ans` 中 `batch_max_bytes=524288`，证明 512 KiB 上限已生效。与 `tmp_11.ans` 相比，完全相同的
`30,492,014 B` sparse logical writes 从 139 个 batch 降至 77 个，容量回写 batch 从 125 降至 63；末尾
进度从 `27/446` 升至 `32/446`。`resident_max_bytes=1,042,257`、`global_budget_* = 0`，故 8 MiB
预算仍只是安全上界，并非当前瓶颈。

payload limit 仍为 50 个 batch、`25,709,614 B`，run limit 为 13 个 batch、`3,257,626 B`。payload 仍占主要
字节，但 run limit 已不再可忽略；在没有重复样本和 sparse 语义回归前，不再连续提高 payload 或 run 上限。

### 已完成的 dense write 归因

`tmp_12.ans` 的一次性 P1.1 统计得到：

```text
attempt_ops=9151 attempt_bytes=37108634
success_ops=58 success_bytes=312056
quota_reservation_ops=519 quota_reservation_bytes=13634667
cache_absent_or_disabled_ops=8573 cache_absent_or_disabled_bytes=23161911
cache_hole_ops=0 cache_limit_ops=0 cache_error_ops=0
```

dense 快路径仅覆盖 `0.63%` 操作和 `0.84%` 字节，主要拒绝原因是 path-keyed cache 缺失或 sparse policy 禁用，
其次是 quota reservation。它不是当前适合扩展的方向。

该诊断版本每个 `write_at()` 额外执行一次 attempt 和一次 outcome 记录；两次记录各更新 ops/bytes 两个全局
`Relaxed` atomic，即每个 write 有四次跨 hart 共享 atomic RMW。`tmp_12` 的 `17/446` 低于 `tmp_11` 的
`27/446`，其直接代码层面的额外成本是原子 cache-line 争用、QEMU 原子执行和附加分支均落在写热路径。
诊断已移除。`tmp_13` 同时移除了诊断并改为 512 KiB，故不能精确分离两项变化各自的贡献；当前只保留整体正向的
512 KiB 配置。

## 2. 已确认的约束与禁做项

| 方向 | 已确认结论 | 当前决策 |
| --- | --- | --- |
| lwext4 全局锁 | 挂载级 block cache 和 path-based C API 未证明 SMP-safe | 保留唯一 `EXT4_OP_LOCK`，不改 rwlock，不让多 hart 并发进入 lwext4 |
| sparse buffer | 512 KiB 已降低容量回写；全局预算未触发 | 保持 512 KiB / 32 runs / 8 MiB，先复验，不再扩容 |
| dense write fast path | 覆盖率低，cache absence/policy 与 quota 主导 | 不扩大 dense cache，不移动 quota reservation，不将 sparse write 当作 dense write |
| 稀疏 metadata | `fstat/statx` 必须反映真实 `st_blocks`、mtime/ctime | 不用 `known_size` 伪造 metadata，不放宽 flush/invalidate 边界 |
| 目录 metadata | directory mtime/ctime 会被子项变化影响 | 只保留一次性 directory lookup-stat 复用，不建持久目录 stat cache |
| 预读与 page waiter | 大预读会放大 read lock hold/wait；single-flight 有停滞历史 | 保留当前有界预读，不扩大窗口，不引入 per-page waiter |
| dentry | `dentry_positive_hit=0` 尚未证明是 bug | 先取证使用机会、插入和失效，不能直接重构 dentry |

所有 sparse 写改动继续保持 hole 布局、write order、last-write-wins、read overlay，以及 `fstat/statx`、close、
rename、truncate、unlink、fsync/sync、`SEEK_DATA/SEEK_HOLE` 的既有发布边界。

## 3. 后续行动

### P0：确认 512 KiB 基线

1. 在相同十分钟入口下至少重复两次，记录末尾 `Building N/446`、`ext4_sparse_buffer`、锁 wait/hold、
   `global_budget_*` 与 `panic/ERROR/TFAIL/TBROK`。
2. 执行 sparse 语义回归：`mmap16`、`lseek11` 的 `SEEK_DATA/SEEK_HOLE`、`fstat/statx`、write-read、
   rename publish、truncate、unlink-open-write-close、fsync/sync。
3. 只有重复样本仍保持正向且语义通过，才固定 512 KiB；若 run limit 或预算成为主要原因，再以新的证据决定下一个
   单变量实验。

### P1：解释 dentry 的实际使用机会

不先修改 `DENTRY_CACHE`。仅收集足以区分下列情况的低干扰证据：

- full-path `FsIndex` 直接命中与 dentry eligible lookup 的数量；
- 语义 bypass，例如 `O_NOFOLLOW`、内部 `O_UNLINK`；
- positive insert、positive lookup hit/miss；
- parent/namespace/容量清理造成的失效，以及 cached-parent 无法使用而回退 root find 的原因。

计数应优先复用现有 VFS 指标或只落在实际 dentry 分支，不能在每次 write/read 增加多组全局 atomic RMW。

### P2：只修复已证实的 dentry 问题

| P1 结果 | 允许的后续动作 |
| --- | --- |
| `FsIndex` 已覆盖重复 open，dentry 没有查询机会 | 不修改 dentry，转 P3 |
| positive entry 未插入 | 只修正对应准入或插入路径 |
| 已插入的 positive entry 被错误或过早失效 | 只修正对应失效路径 |
| child 名称主要一次性 | 不修改 dentry，转 P3 |

任何 dentry 行为改动必须回归 `O_NOFOLLOW`、`O_UNLINK`、create/link/unlink/symlink/rename、inode-number reuse、
容量回收和深路径 `open14`。

### P3：按具体调用来源分析 metadata/namespace

若 dentry 无可验证收益，再按 syscall、调用者、参数模式和底层 lwext4 操作细分 `mode`、`owner`、`create`、
`unlink` 等聚合热点。只有证明存在可合并的重复 lookup、重复 metadata 更新或可安全复用的结果后，才做一个局部改动；
禁止按聚合总量猜测性缩小锁域或扩大缓存。

本轮 `tmp_15.ans`/`log.ans` 的稳定调用链为 `create -> fmode_set -> owner_set`：新 inode 在进入
`FsIndex` 前不会被其他任务访问，因此 ext4 后端已将三步合并为 `create_with_metadata()`，仅减少 Rust
侧子 inode/global gate 的连续交接；底层 C metadata 调用和 Linux 可见顺序保持不变。两份日志早于该实现，
后续需以新样本观察 namespace lock hold/wait 与 mode/owner phase 的变化。

### P4：获得完整 BuildStorm 基线

使用固定 source snapshot、镜像、内存、hart 数与缓存起始状态，运行到：

```text
BUILDSTORM_COMPILE mode=multi ok=true elapsed_s=<...>
#### OS COMP TEST GROUP END buildstorm ####
shutdown!
```

这才是完整吞吐和时限的判据。十分钟 `Building N/446` 仅用于 P0-P3 的局部决策。

## 4. 验收标准

每个行为改动至少执行：

```bash
make perf TARGET_ARCH=riscv64
make perf TARGET_ARCH=loongarch64
make TARGET_ARCH=riscv64
make TARGET_ARCH=loongarch64
git diff --check
```

RISC-V 是 BuildStorm 的运行主验证架构；LoongArch64 至少完成构建，涉及文件系统语义时补定向 guest 回归。
固定十分钟实验需同时报告 crate 进度、sparse batch/reason/bytes、EXT4 锁 wait/hold 和功能标记；完整实验还需报告
guest `elapsed_s` 与宿主 wall-clock。
