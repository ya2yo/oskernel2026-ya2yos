# BuildStorm 优化方案

> 适用源码快照：`467f56b1` 与本轮审计时的 `os/src/fs/ext4_lw` 过渡实现（2026-08-03）。本文只保留当前实现、
> 有效结论、下一步动作和验收边界；历史实验与故障取证见末尾问题记录。

## 0. 路线选择

### 0.1 `EXT4_OP_LOCK` 为什么仍然存在

它是 **lwext4 过渡适配层的安全闸门，不是 Linux ext4 的锁模型，也不是最终设计**。当前
`os/src/fs/ext4_lw/mod.rs` 中的 `Ext4OpLock` 覆盖全部 lwext4 C API；它在 task 上下文把竞争者放入 FIFO
sleep queue，而不是让它们直接自旋。保留它有三个不可省略的原因：

1. **已复现的调度死锁。** P21.3 让多个 task 直接进入 lwext4 C raw rwlock 后，`client.ans` 显示 CPU 0/2/3/7
   同时停在 `ext4_fs_rwlock_write_lock()`，没有持锁 C 栈，其余 hart idle。根因不是普通漏 unlock，而是持锁 task
   被抢占后，竞争者 busy-spin 占满 runnable CPU，owner 得不到再次运行的机会。Rust 边界的 gate 使竞争者可睡眠，
   是该 C 库在当前调度模型中的正确性前提。
2. **lwext4 wrapper 不是稳定 inode 对象模型。** `Ext4InodeInner` 持有按路径工作的可变 `Ext4File` 和 alias；
   rename、hard link、unlink 后还要依赖 pathname 重新绑定和全局 identity epoch。每个 wrapper 的 `io_state` 只能保护
   那一个 descriptor，不能表达目录项、同一 inode 的多 alias、block group、缓存和 journal 之间的所有权与锁序。
3. **C 层的资源协议不能与 VFS 分割。** 即使 Rust bcache 已把 index/LRU/dirty 生命周期拆开，进入 lwext4 后仍会经过
   C 层的 pathname traversal、descriptor rebind、allocator、journal 和 raw lock；仅把外层改成 `RwLock` 或给少数
   “读 API”放行，既无法让底层锁可睡眠，也无法证明与写侧元数据的一致性。

因此在 **任意 lwext4 C API 仍会被调用的挂载** 上，`EXT4_OP_LOCK` 必须保持 task-aware FIFO **exclusive**；包括
`read-data`、find、read-dir、readlink、get/listxattr、link-count、statfs 和 `ls`。这纠正了本文旧版“已审计纯读 API
使用 shared”的过时表述：P21.3 shared admission 已整体回退，不能把历史实验状态误当作当前实现。

删除该锁的条件不是“读路径看上去不写”，而是该操作从 VFS 到块设备 **完全不进入 lwext4**，并且所需的 native inode、
directory、extent、allocator、writeback 与 transaction 锁协议已经实现和验证。过渡期间 native 与 lwext4 不能在同一
可写挂载上交错访问同一份元数据；native read 先只服务于只读挂载，legacy lwext4 挂载继续由 gate 保护。

### 0.2 “真正 Linux EXT4”的工程定义

目标不是把 Linux C 文件逐行搬入 Ya2yOS；Linux 7.0 的 `fs/ext4` 依赖其 VFS `inode/file/address_space_operations`、
folio/page cache、bio、workqueue、`BUFFER_HEAD` 和 JBD2 的内部 ABI，直接移植既不可编译也不会自动正确。目标应是：
**实现 Linux 可识别的 ext4 on-disk format、Linux 可见 VFS 语义、JBD2 可恢复写入语义，以及 Linux 风格的资源级并发模型。**
没有 JBD2-compatible journal/recovery 的可写实现只能称为“ext4 格式子集”，不能称为真正的 Linux ext4 写路径。

下表是本地 Linux 7.0 源码给出的最小并发模型；其中“每文件系统锁”只对应特定 rename 拓扑操作，绝不等价于
`EXT4_OP_LOCK`：

| Linux 层次与源码证据 | Linux 的保护对象 | Ya2yOS 必须建立的对应对象 |
| --- | --- | --- |
| `Documentation/filesystems/directory-locking.rst:6-64`；`fs/namei.c:1926-1935,4574-4599` | 目录的 `i_rwsem`：lookup shared，create/remove exclusive。 | 可睡眠的 per-inode `rwsem`；inode 以 `(device, ino, generation)` 身份缓存，而非 pathname wrapper。 |
| `Documentation/filesystems/directory-locking.rst:53-64,137-161`；`fs/namei.c:3760-3820` | 跨目录 rename 才取得 `s_vfs_rename_mutex`，再以父目录优先、non-directory inode 地址序取得锁。 | 专用、可睡眠的 `rename_topology_mutex`，只包围跨目录拓扑判定；实现 parent/source/target 的固定锁序和死锁断言。 |
| `fs/ext4/ext4.h:1111-1123`；`fs/ext4/extents.c:4251-4269` | 每 ext4 inode 的 `i_data_sem`；只读 extent map shared，带 `CREATE` 的映射和 truncate exclusive。 | 每 native inode 的 data-map rwsem、extent status cache 与页/folio（或等价页缓存）锁；映射查询与分配必须分开。 |
| `fs/ext4/ext4.h:1564-1580,3561-3605` | 每 block group 的锁、per-CPU free counter 与 orphan lock；不以整个 mount 串行分配。 | block-group bitmap/descriptor lock、free inode/block 计数、预分配状态与 orphan-list lock；短临界区锁内不做 I/O。 |
| `fs/ext4/super.c:99-123`；`fs/jbd2/transaction.c:1820-1836` | operation 通过可嵌套 `handle_t` 进入 transaction；JBD2 分别保护 journal state/list 并在可恢复边界 commit。 | task-bound transaction handle、credit/reserve、metadata journal、ordered data writeback、commit/checkpoint 和 recovery；错误必须向 syscall 返回。 |

Linux 的 per-group 自旋锁只保护短临界区，且由 Linux 的 preemption/interrupt 规则约束；它不能成为 Ya2yOS 中可抢占 task
跨 C API busy-spin 的依据。Ya2yOS 的资源级锁若可能等待 I/O、内存分配、journal commit 或另一个 task，必须是可睡眠且可
取消/唤醒的锁；自旋锁只允许保护已验证的短元数据临界区。

### 0.3 兼容性边界与不变量

P22 的“完成”以 Linux 生成和检查工具能验证的行为定义，而不是以 benchmark 或删锁定义：

- 固定首个可写支持 profile（block/inode size、`extent`、`64bit`、`dir_index`、`metadata_csum`、`filetype`、
  `large_file`、extra inode size、journal checksum 等）；挂载时校验 incompat/ro_compat 位，不支持的 feature 显式拒绝，
  不得静默降级或写坏镜像。
- 同一镜像须可由 Linux `mke2fs` 创建、由 Ya2yOS 读写、再由 Linux `e2fsck -fn` 和 `debugfs` 检查；支持 journal 的
  可写 profile 必须以 JBD2-compatible journal 和 orphan recovery 通过掉电恢复，不能用“下次全盘扫描修复”代替。
- pathname lookup、open-file `f_pos`、hard link/unlink-open、rename、truncate、xattr、权限/时间戳和 `st_blocks` 的
  Linux-visible 语义由相关 LTP 和针对性并发/故障注入回归验收。
- 只有 native 挂载完成一整个可写 feature profile 的 ownership、锁序、恢复和磁盘检查后，才移除该挂载的
  `EXT4_OP_LOCK`；不允许按单个 C API “白名单绕过”来宣称 Linux 对齐。

### 0.4 证据范围与未验证点

本文 Linux 对照来自本机只读源码树 `/home/ya2yo/linux/linux-7.0`（`Makefile` 标识 `VERSION = 7`、
`PATCHLEVEL = 0`），关键证据已列于表 0.2。`directory-locking.rst` 明确给出 VFS 目录锁与 rename 锁的规则，
`ext4.h`/`extents.c` 明确给出 `i_data_sem` 与 block-group 锁，`super.c` 给出 buffered write、truncate、direct I/O
和 writepages 的锁序，JBD2 `transaction.c` 给出 handle 结束与 error 返回边界。这些是设计输入，不是 Linux
runtime lockdep trace，也不能替代 Ya2yOS 自己的并发验证。

尚未验证的点：首个 feature profile 的精确组合、Ya2yOS 上 JBD2 journal checksum/revoke 的互操作性、掉电注入点、
casefold/encrypt/bigalloc/inline-data/EA inode/fast-commit 等扩展 feature 的支持范围。它们必须先写入 P22.0 的显式矩阵；
未实现前一律 mount-time 拒绝，不能让测试镜像偶然通过后形成“已兼容”的错误结论。

## 1. 结论

当前 BuildStorm 的首要内核瓶颈仍是挂载级 `EXT4_OP_LOCK` 的排他段：多 hart 能并发运行任务，但 namespace、
allocator、journal、descriptor rebind 与真实写回仍会形成 FIFO 写者栅栏和锁 convoy。调度器耗时和文件页缓存容量在
最新样本中都不是主导项。

内核已经完成撤退全局 gate 所需的两项基础工作：位置无关块 I/O（P21.1）和并发 bcache 基础设施与 telemetry
（P21.2/P21.2a），但这些基础设施不足以让可抢占 task 直接争用 C raw rwlock。P21.3 的 shared admission 已撤回，
所有 lwext4 C API 重新经 FIFO exclusive admission；inode identity、目录、allocator 和 journal 仍缺少其各自的
并发协议，因此 `lwext4-smp` 默认启用不等于“EXT4 已并行化”。

P21.2b.0 已用 sanitizer lifecycle oracle 验证当前已覆盖的 bcache intrusive tree/list/refcount 状态机，P21.2b.1 已将
cache-wide dirty flush 改为 bcache 内部的 claim/pin、锁外写回、统一 release。P21.2b.2 已实现为默认关闭的 dirty-capacity
256/128 blocks 高低水位实验：victim 只能经 bcache 内部 API claim/pin，I/O 在 index lock 外，成功写回后才丢弃 clean
buffer，失败保留 dirty。首次 P21.2b dirty victim 实验曾因 LRU RB tree `LoadPageFault` 回退，因此不得恢复由外部策略
直接 `RB_REMOVE`/`RB_INSERT` 的路径，更不能据此将 gate 改成 `RwLock`。

## 2. 当前实现

| 子系统 | 已实现 | 当前边界 |
| --- | --- | --- |

## 3. 有效证据

### 3.1 当前稳定基线

P21.2a 的 `log.ans` 有 `BUILDSTORM_TOOLCHAIN/MINIBUILD ok`，约 573 秒时到 Cargo `21/446`，没有 panic、
`ERROR`、`TFAIL` 或 `TBROK`；但没有 `BUILDSTORM_COMPILE ... ok=true`、测试组 `END` 或 `shutdown!`，
只能用于方向判断，不能报告端到端加速或回退比例。

末个完整累计快照满足：

- `get_ops=661695 = cache_hits 412142 + cache_misses 249553`；
- `loader_ops=249553 = successes 249553 + errors 0`；
- `writeback_ops=18515 = successes 18515 + errors 0`；
- `initial 16 + allocations 266818 - drops 266818 = resident 16`；
- `allocation_races=0`、loader/writeback wait 为 0、device contention 为 0。

同时出现 `shake_full_dirty=401664`、`capacity_overflows=181972`、`max_resident_blocks=1243`。这说明 16-block
bcache soft target 在 dirty-only 压力下不收敛；它不证明设备锁或 waiter 分桶是当前瓶颈，因为全局 gate 尚未撤退。

历史长样本中 `read/find/fstat/write` 的 gate wait 明显高于 hold，scheduler dispatch 仅占很小部分；文件页缓存也未
触及 192K 页上限。因此当前优先级是 EXT4 串行边界和 dirty bcache 生命周期，而不是扩大页缓存、预读窗口或调整 CFS。

### 3.2 P21.2b.0/P21.2b.1 阶段验证

新的 RISC-V 8 HART `tmp_12.ans` 有测试组 `START` 与 `BUILDSTORM_TOOLCHAIN/MINIBUILD ok`，在约
`t=175236ms` 的末次累计快照后仍未出现 panic、`ERROR`、`TFAIL`、`TBROK` 或 SIGSEGV。它没有
`BUILDSTORM_COMPILE ... ok=true`、测试组 `END` 或 `shutdown!`，因此只能证明已观察区间阶段稳定，不能报告完整
BuildStorm 通过或性能提升。

末次累计 bcache 快照满足：

- `538658 = 332749 cache_hits + 205909 cache_misses`；
- `205909 loader_ops = 205909 successes + 0 errors`；
- `13362 writeback_ops = 13362 successes + 0 errors`；
- `16 initial + 218541 allocations - 218541 drops = 16 resident`。

C block callback 的 read/write 请求分别为 `231256/17769`，总计 `249025`，submit 与 complete 全部相等且 error
为 0；device contention 为 0。相邻两个 interval 的 loader 和 read submit/complete 先后出现 `-1/+1` 的互补差异，
是 relaxed 分字段快照跨过一个在途请求；末次累计快照闭合，不作为错误计数。

容量压力仍未解决：`shake_full_dirty=353857`、`capacity_overflows=161383`、`max_resident_blocks=1243`。gate 同时
累计 `fast_acquires=35588`、`queued=6025`、`handoffs=6021`、`queue_depth=4`、`max_queue_depth=8`，handoff wait
累计 `81379237us`。这说明 lifecycle 修复未引入已观察到的正确性错误，但 16-block clean soft target 和 mount-wide
gate 仍分别造成容量失控与串行争用。

### 3.3 已回退实验

`tmp_11.ans` 在 P21.2b dirty victim 实验中触发 RISC-V `LoadPageFault`，`sepc=0xffffffc080369392` 定位到
`ext4_buf_lru_RB_REMOVE_COLOR`。实验代码仅凭 `refctr==0` 和一次 LRU 遍历就直接摘除、写回并重插 intrusive
RB tree 节点，没有证明 index ownership，故已完整回退到 P21.2a clean-only shake。该日志是正确性失败，不是性能样本。

### 3.4 P21.2b.2 两分钟 RISC-V 阶段验证

维护者已在 Docker 中以 RISC-V musl 工具链成功编译实验配置；当前 `log.ans` 是该配置约两分钟的 8 HART 运行结果。
日志有 `BUILDSTORM_TOOLCHAIN/MINIBUILD ok`，未出现 panic、SIGSEGV、`ERROR`、`TFAIL` 或 `TBROK`，但没有
`BUILDSTORM_COMPILE ... ok=true`、测试组 `END` 或 `shutdown!`，故只能证明阶段稳定和容量路径被执行，不能报告完整
BuildStorm 通过、速度提升或回退比例。

约 `t=114851ms` 的累计快照满足：

- `get_ops 367548 = cache_hits 200149 + cache_misses 167399`；
- `loader_ops 167399 = loader_successes 167399 + loader_errors 0`；
- `writeback_ops 4917 = writeback_successes 4917 + writeback_errors 0`；
- `initial 16 + allocations 172079 - drops 171901 = resident 194`；
- C block request `186059 read + 6889 write = 192948 completed`，read/write/device error 都为 0。

新 telemetry 为 `dirty_capacity_reclaim_runs=1`、`dirty_capacity_reclaimed_blocks=128`、
`dirty_capacity_reclaim_stalls=0`，并且 `max_resident_blocks=256`。这表明实验 feature 已实际链接，达到 high 后完成了一次
回收批次；回收后的 workload 又增长到 resident 194，属于 128/256 hysteresis。`capacity_overflows=132836` 仍表示超过
旧 16-block soft target 的历史计数，预期会很大，不表示 256 水位突破。

### 3.5 P21.3 shared admission 的 `tmp_13.ans`

新的 RISC-V 8 HART `tmp_13.ans` 有 `BUILDSTORM_TOOLCHAIN/MINIBUILD ok`，在 `t=283386ms` 后继续到 Cargo
`Building 11/446`；未出现 panic、SIGSEGV、`ERROR`、`TFAIL` 或 `TBROK`，但没有 compile success、测试组 `END` 或
`shutdown!`。因此它只证明已观察区间的阶段稳定，不报告完整 BuildStorm 通过或加速。

该样本确认 shared admission 真正工作：`shared_acquires=39042`、`shared_handoffs=2224`、
`max_active_readers=7`。同时累计 gate handoff wait 仍为 `567915801us`，而读、find、metadata 和 write 的锁等待仍显著，
说明 writer 栅栏和长写事务仍是当前重点。`fstat` 的 sparse flush 计数为 6，且 fstat/recovery 可触发 `file_close()`；
因此它不能作为 shared 路径，后续代码已维持 exclusive，避免把实际写回错误归类成“读并发”。

### 3.6 P21.3 回退：C raw rwlock 与调度死锁

新的 `server.ans` 到 BuildStorm `tg-xtask` 并行预构建后不再推进；`client.ans` 的全 CPU GDB 栈显示 CPU 0/2/3/7
都在 `ext4_fs_rwlock_write_lock()`，分别由 pathname create/mkdir 调用，另四个 hart idle。没有持锁的 C 临界区栈，
排除常规漏 unlock，确认是持锁 task 被抢占后其它 task 的 C busy loop 吞掉所有 runnable CPU。

因此撤回 P21.3 shared admission，恢复 FIFO exclusive `EXT4_OP_LOCK`，并保留 exit cleanup。当前 `ext4_trunc_inode()`
还以 `journal_lock_held` 判断外层 transaction，修复无 on-disk journal 时的 journal self-deadlock。双架构 release 构建
通过；新内核以默认 16 GiB/8 HART 在 360 秒 timeout 前推进到 Cargo `15/446`（旧死锁样本约停在 `2/446`），无已观察到的
panic/TFAIL/TBROK/ERROR，但缺少完整结束标记，不能报告完整运行通过或性能数据。

## 4. 优化顺序

| 优先级 | 工作 | 完成条件 |
| --- | --- | --- |
| P0 | 固定当前基线 | 同一 commit、镜像、QEMU `-smp`、Cargo jobs 和冷启动配置至少完成一次 BuildStorm；记录完整结束标记和宿主 wall-clock。 |
| P21.2b.0（已完成） | bcache 生命周期 oracle | host ASan/UBSan oracle 已覆盖 acquire/release、load、flush、clean eviction、dirty-list 转换、读写错误、同/异 LBA 并发、writeback/shake 竞争、10 万步随机 trace 与负向破坏检查。 |
| P21.2b.1（已完成） | 单一 claim/release API | cache-wide flush 已通过 bcache 内部 API 完成 pin、锁外 writeback 和成功/失败 release；生产 `ext4_block_flush_buf()` 调用点均持有 refcount pin，策略层不再直接取 dirty list 裸指针。 |
| P21.2b.2（已实现，默认关闭） | dirty 容量实验 | 256/128 blocks 高低水位、claim/pin、锁外 writeback、clean-only discard、I/O error retention、host lifecycle oracle 和 reclaim telemetry 已完成。继续验证 `resident <= high + in_flight_loaders`、错误恢复、8 HART 压力和 `e2fsck -fn`，再决定是否默认启用。 |
| P21.3（已回退） | lwext4 raw rwlock preemption deadlock | 当前保持 FIFO exclusive admission；只有 C 锁获得 task-aware wait/wake 或明确不可抢占边界并完成资源锁序证明后，才可重新评估 shared/read 并发。 |
| P22.0 | Linux ext4 profile 与镜像契约 | 记录首个可写 profile 的 feature bits、mount option、block/inode size、journal layout/checksum、拒绝策略和 Linux 生成命令；输入镜像必须由 Linux 工具创建。验收：mount-time feature negative tests、只读 `debugfs` 对照、`e2fsck -fn` 基线。 |
| P22.1 | Native VFS inode 与可睡眠锁基础 | 建立 `(device, ino, generation)` inode cache、dentry/name cache、独立 open-file `f_pos`、per-inode `rwsem`、data-map rwsem 与只限跨目录 rename 的 topology mutex；先把锁层和 lock-order assertion 放在没有 lwext4 的 native mount 内。验收：多 task lookup/open/close、同目录 create/remove、跨目录 rename 的死锁探测与 owner exit/cancel。 |
| P22.2 | Native read-only ext4 | 实现 superblock/group descriptor/inode 读取、checksum 校验、extent 映射、directory linear/htree lookup、symlink、xattr read 和页缓存；只以 native readonly mount 暴露，legacy lwext4 仍独占自己的挂载。验收：Linux 生成镜像上的只读 BuildStorm/LTP、并发读压测、`debugfs`/`e2fsck -fn` 字节级字段对照。 |
| P22.3 | Native metadata 与 namespace 协议 | 实现 inode/dir entry 写回、create/mkdir/unlink/rmdir/link/rename、truncate、xattr write，严格采用 parent/source/target 锁序；cross-directory rename 才拿 topology mutex。验收：相关 LTP、并发 rename/create/unlink、目录项/`i_nlink`/free inode 计数守恒；不接入 journal 前只允许明确标记的实验性非 journal profile，不宣称 Linux 可写 ext4。 |
| P22.4 | Allocator、JBD2 与恢复 | 实现 block-group allocator、extent 写时分配、task-bound `handle`/credit、JBD2-compatible descriptor/commit/revoke/checksum、ordered data writeback、orphan list、checkpoint 与 mount recovery。验收：fault injection、每个 metadata 更新阶段的掉电恢复、Linux `e2fsck -fn`/`debugfs`、journal abort 的 errno 传播。 |
| P22.5 | 完整切换与移除 gate | 对一个完整可写 profile，将 VFS 到 block I/O 全路径切到 native；确认没有 `Ext4File`/lwext4 C API/`EXT4_OP_LOCK` 可达，再删除该 native mount 的过渡 gate。验收：双架构 LTP/BuildStorm、8 HART 长压、两次完整 A/B、Linux 挂载回读与恢复。 |
| P22.6 | 扩展 profile 与长期兼容 | 在基本 profile 稳定后逐项实现并单独验收 fast commit、quota、ACL、casefold、encrypt、bigalloc、inline data、EA inode 等；每个 feature 必须有 on-disk、恢复、并发和拒绝路径测试。 |

P22.0/P22.1 是当前工程的下一步：先固定磁盘契约和可验证的锁对象，再做 P22.2 native readonly path。P21.2b.2 的
`e2fsck -fn`、8 HART 持续运行和两次完整 A/B 只是 lwext4 过渡层本身的退出条件，不是对 Linux ext4 兼容性的替代证明。
暂不实施：继续扩大页缓存或预读、恢复正 dentry fast path、拆 `Disk::dev` mutex、按 LBA waiter 分桶、提高 BuildStorm
并发度，或仅通过删除 `EXT4_OP_LOCK` 宣称 Linux 对齐。新代码必须从 P22.0 的 feature 矩阵选择一个完整 profile，并按
P22.1→P22.5 建立 ownership；只有 native 可写 profile 通过语义、并发、掉电恢复和磁盘检查，才能停止维护 lwext4 gate。

## 5. 正确性约束

- lwext4 仍在使用时，所有 lwext4 public API（包括当前看来纯读的 API）仍须持有 **exclusive** `EXT4_OP_LOCK`；
  P21.2 的内部锁只提供 bcache 基础设施，不能替代目录、allocator 或 journal 的写侧协议。native EXT4 与 lwext4
  不能在同一可写挂载上交错读写；迁移必须以挂载/profile 为 ownership 边界，或在 legacy 挂载不写时仅做 native readonly。
- native 锁序以 Linux 目录锁规则为基线：跨目录 rename 的 topology mutex 在所有 inode lock 之前；目录 parent 先于
  child；两个 non-directory inode 按稳定 `(device, ino)` 序；每 inode 的 data-map lock 只覆盖 extent/map-truncate
  关系。不得把 mount-wide mutex 伪装为普通 read/write 的并发方案。
- 不得持有 cache index spinlock 或 block-group short lock 等待设备 I/O、task mutex、journal commit 或内存分配；
  transaction handle、页锁和可睡眠 rwsem 的嵌套必须有 lock-order assertion 和相应的错误退出路径。
- 不牺牲 quota reserve/rollback、ENOSPC 小块回退、sparse overlay、`st_blocks`、mtime/ctime、rename/truncate/
  unlink/write 的 cache 失效和 mmap EOF/SIGBUS 语义。
- bcache 容量策略不得在运行时销毁重建 cache，也不得由外部策略直接操作 intrusive tree/list。
- `BC_WRITEBACK` 只表示 I/O 状态，不能替代对象生命周期引用；生产路径离开 index/list 保护域调用
  `ext4_block_flush_buf()` 前必须持有 refcount pin，并在 callback 与状态清理完成后统一 release。
- P21.2b.2 reclaim 在成功写回后只能释放 claim pin 并丢弃最终为 clean 的对象；I/O 失败必须恢复 dirty membership，
  不得在同一次 release 中递归重试。未来移除外层 gate 时，容量上界按 `high + in_flight_loaders` 验收，而非误读旧
  16-block `capacity_overflows`。
- 未出现完整结束标记时，只能报告方向性计数；跨任务累计 wait/hold 不能相加为 guest wall-clock。
- 任一阶段出现 stale read、错误 LBA、目录项丢失/重复、free count 漂移、journal abort、panic、死锁或 fsck 差异，
  立即关闭新路径并回退到上一个已验证阶段。

## 6. 验收

静态与双架构构建：

```bash
cargo fmt --manifest-path os/Cargo.toml --all -- --check
git diff --check
make TARGET_ARCH=riscv64
make TARGET_ARCH=loongarch64
make perf TARGET_ARCH=riscv64
make perf TARGET_ARCH=loongarch64
```

行为与并发回归至少覆盖：同/异 LBA、I/O error、64+ gate waiter 和 owner 退出；read/write/stat/rename/truncate/
unlink-open-close/fsync；mmap 尾页、越界页、并发 truncate；容量 feature；RISC-V 8 HART；涉及共享 C 代码时补
LoongArch64 冒烟和 `e2fsck -fn`。

每个 P22 native profile 另须准备三类独立镜像：Linux `mke2fs` 新建的基线镜像、Ya2yOS 完成随机 namespace/data
操作后的回读镜像、在 create/rename/truncate/allocate/journal commit/checkpoint 各阶段强制掉电后的恢复镜像。三类镜像
均须由 Linux `e2fsck -fn` 和 `debugfs` 检查；只读 profile 也必须验证 unsupported feature 的拒绝路径。并发验收须
同时覆盖同目录与异目录操作，cross-directory rename，以及读取 extent 与并发 allocate/truncate，不能只使用单线程 fsck。

性能结论必须使用同一环境至少两次完整运行，并同时出现：

```text
BUILDSTORM_COMPILE mode=multi ok=true elapsed_s=<...>
#### OS COMP TEST GROUP END buildstorm ####
shutdown!
```

常用日志提取：

```bash
rg -a -n "BUILDSTORM|shutdown!|panic|TFAIL|TBROK|ERROR|SIGSEGV|QEMU: Terminated" log.ans
rg -a -n "^\[perf\] (t=|interval_ext4|ext4_gate|ext4_bcache|ext4_block|file_cache|scheduler_duration)" log.ans
strings log.ans | tail -240
```
