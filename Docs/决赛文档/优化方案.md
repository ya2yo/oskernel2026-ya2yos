# BuildStorm 优化方案

> 适用源码快照：`467f56b1`（2026-08-02）。本文只保留当前实现、有效结论、下一步动作和验收边界；
> 历史实验与故障取证见末尾问题记录。

## 1. 结论

当前 BuildStorm 的首要内核瓶颈仍是挂载级 `EXT4_OP_LOCK`：多 hart 能并发运行任务，但所有 lwext4 path/file
调用最终串行进入同一 gate，形成排队和锁 convoy。调度器耗时和文件页缓存容量在最新样本中都不是主导项。

内核已经完成撤退全局 gate 所需的两项基础工作：位置无关块 I/O（P21.1）和并发 bcache 基础设施与 telemetry
（P21.2/P21.2a）。但 public API 仍未开放并发，inode identity、目录、allocator 和 journal 也仍是串行语义，
因此 `lwext4-smp` 默认启用不等于“EXT4 已并行化”。

下一步不能直接将 gate 改成 `RwLock`。应先证明 bcache intrusive tree/list/refcount 的生命周期，再完成受控的
dirty-capacity 回收；随后只放开不同 inode 的只读路径。首次 P21.2b dirty victim 实验已因 LRU RB tree
`LoadPageFault` 回退，不得恢复未经 oracle 覆盖的 `RB_REMOVE`/`RB_INSERT` 路径。

## 2. 当前实现

| 子系统 | 已实现 | 当前边界 |
| --- | --- | --- |
| SMP 与调度 | RISC-V/LoongArch64 SMP；默认 CFS 使用 per-hart run queue，支持 remote enqueue 与 idle hart IPI；perf 可统计 dispatch/wakeup。 | 最新 BuildStorm 中 dispatch 累计远低于 EXT4 wait；暂不调整调度策略或并发度。 |
| 文件页缓存 | 普通文件最大 32 MiB 准入；全局 192K 页（768 MiB）；最多四页顺序预读；clean-page CLOCK 仅回收无外部 `FilePage`/frame 引用的页；dirty/in-use 候选进入 deferred 队列，满载失败保留 direct bypass。 | 生产容量不是当前调参项；2,048 页的 `file-cache-capacity-test` 只用于满载回归。脏页写回与 mmap/truncate 可见性必须优先于命中率。 |
| VFS/EXT4 热路径 | FsIndex、负 dentry、regular-file stat cache、目录局部 epoch、文件页缓存；write quota 移出 gate；write open/data 分段；创建事务复用 stat；稀疏写有界缓冲；rename 成功后迁移 dense path cache。 | cache identity 仍以 pathname 和 epoch 为主，尚未形成 P21.3 所需的 inode-number keyed 共享状态；rename migration 缺独立计数和完整语义长测。 |
| EXT4 gate | `EXT4_OP_LOCK` 是 task-aware FIFO gate，禁止插队；支持 waiter 取消；任务退出时回收票据，并在退出任务是 owner 时释放 gate、唤醒队首。 | 所有 lwext4 path/file C API 仍串行。当前锁序保持 `write_state -> io_state -> EXT4_OP_LOCK`，不得反向获取。 |
| P21.1 块设备 | `KernelDevOp` 使用 `device_size/read_at/write_at/flush`；`Disk` 无共享 cursor，以设备 submission mutex 覆盖一次完整请求及非对齐 RMW；C byte-I/O 使用每次调用 scratch。 | 设备提交仍可串行，但锁域已收缩到单次请求。当前日志中 device contention 为 0，没有证据支持优先拆设备锁。 |
| P21.2 bcache | LBA/LRU/dirty/refcount 由短时 `index_lock` 保护；miss 二次 lookup；`BC_LOADING/BC_IO_ERROR` 同 LBA single-flight；`BC_WRITEBACK/BC_EVICTING` pin；I/O 和等待在 index lock 外；Rust 提供 task-aware wait/wake。 | 仍由外层 gate 遮蔽真实并发；waiter 是 mount-wide wake-all；clean-only shake 遇到全 dirty cache 会越过 16-block soft target。 |
| P21.2a 观测 | perf 内核在 mount 后统一启用并清零 bcache、C block I/O 和 Rust `Disk` 请求计数；报告累计与 interval 的 hit/miss、load/wait、shake/overflow、writeback、resident 和请求时延。 | relaxed interval 快照允许一个在途同步请求造成字段暂差 1；守恒以完整累计快照为准。普通 release 不承担 Rust perf 计数开销。 |

## 3. 有效证据

### 3.1 当前稳定基线

P21.2a 的 `log.ans` 有 `BUILDSTORM_TOOLCHAIN/MINIBUILD ok`，约 573 秒时到 Cargo `21/446`，没有 panic、
`ERROR`、`TFAIL` 或 `TBROK`；但没有 `BUILDSTORM_COMPILE ... ok=true`、测试组 `END` 或 `shutdown!`，
只能用于方向判断，不能报告端到端加速或回退比例。

末个完整累计快照满足：

- `get_ops=661695 = cache_hits 412142 + cache_misses 249553`；
- `loader_ops=249553 = successes 249553 + errors 0`；
- `writeback_ops=18515 = successes 18515 + errors 0`；
- `initial 16 + allocations 266818 - drops 266818 = resident 16`；
- `allocation_races=0`、loader/writeback wait 为 0、device contention 为 0。

同时出现 `shake_full_dirty=401664`、`capacity_overflows=181972`、`max_resident_blocks=1243`。这说明 16-block
bcache soft target 在 dirty-only 压力下不收敛；它不证明设备锁或 waiter 分桶是当前瓶颈，因为全局 gate 尚未撤退。

历史长样本中 `read/find/fstat/write` 的 gate wait 明显高于 hold，scheduler dispatch 仅占很小部分；文件页缓存也未
触及 192K 页上限。因此当前优先级是 EXT4 串行边界和 dirty bcache 生命周期，而不是扩大页缓存、预读窗口或调整 CFS。

### 3.2 已回退实验

`tmp_11.ans` 在 P21.2b dirty victim 实验中触发 RISC-V `LoadPageFault`，`sepc=0xffffffc080369392` 定位到
`ext4_buf_lru_RB_REMOVE_COLOR`。实验代码仅凭 `refctr==0` 和一次 LRU 遍历就直接摘除、写回并重插 intrusive
RB tree 节点，没有证明 index ownership，故已完整回退到 P21.2a clean-only shake。该日志是正确性失败，不是性能样本。

## 4. 优化顺序

| 优先级 | 工作 | 完成条件 |
| --- | --- | --- |
| P0 | 固定当前基线 | 同一 commit、镜像、QEMU `-smp`、Cargo jobs 和冷启动配置至少完成一次 BuildStorm；记录完整结束标记和宿主 wall-clock。 |
| P21.2b.0 | bcache 生命周期 oracle | 可重复覆盖 acquire/release、load、flush、clean eviction、dirty-list 转换和 I/O error；逐步检查 refcount、LBA/LRU tree membership、dirty-list membership、`ref_blocks`；完成同/异 LBA 与 10 万次随机生命周期。 |
| P21.2b.1 | 单一 claim/release API | victim pin、index ownership 转移、锁外 writeback、成功 drop 和失败恢复全部由 bcache 内部状态机完成；策略层不得直接操作 RB tree/list。 |
| P21.2b.2 | 默认关闭的容量实验 | 先试 256/128 blocks 高低水位；验证 `resident <= high + in_flight_loaders`、错误恢复、8 HART 压力和 `e2fsck -fn`，再决定是否默认启用。 |
| P21.3 | 不同 inode 只读并发 | 建立 inode number/generation keyed `Ext4InodeState` 和独立 open-file `f_pos`；仅开放 `read/read_all/fstat/read_dir` shared admission，修改操作继续 exclusive fallback；必须观测 `max_active_readers > 1` 且 read/find/fstat wait 下降。 |
| P21.4+ | namespace、allocator、journal | 依次引入目录锁与 rename mutex、block-group/extent 锁、per-operation journal handle；每阶段保留串行 fallback，正确性和 fsck 通过后才撤退对应 gate。 |

暂不实施：继续扩大页缓存或预读、恢复正 dentry fast path、拆 `Disk::dev` mutex、按 LBA waiter 分桶、提高
BuildStorm 并发度，以及把 `EXT4_OP_LOCK` 直接替换为操作分类锁或 `RwLock`。只有新 telemetry 证明对应资源已成为
主导瓶颈时，才将其中一项作为单变量实验。

## 5. 正确性约束

- 外层 gate 撤退前，所有 lwext4 public API 仍须持有 `EXT4_OP_LOCK`；P21.2 的内部锁只提供基础设施。
- 固定现有锁序；不得持有 cache index spinlock 等待设备 I/O、task mutex、journal commit 或内存分配。
- 不牺牲 quota reserve/rollback、ENOSPC 小块回退、sparse overlay、`st_blocks`、mtime/ctime、rename/truncate/
  unlink/write 的 cache 失效和 mmap EOF/SIGBUS 语义。
- bcache 容量策略不得在运行时销毁重建 cache，也不得由外部策略直接操作 intrusive tree/list。
- 未出现完整结束标记时，只能报告方向性计数；跨任务累计 wait/hold 不能相加为 guest wall-clock。
- 任一阶段出现 stale read、错误 LBA、目录项丢失/重复、free count 漂移、journal abort、panic、死锁或 fsck 差异，
  立即关闭新路径并回退到上一个已验证阶段。

## 6. 验收

静态与双架构构建：

```bash
cargo fmt --manifest-path os/Cargo.toml --all -- --check
git diff --check
make TARGET_ARCH=riscv64
make TARGET_ARCH=loongarch64
make perf TARGET_ARCH=riscv64
make perf TARGET_ARCH=loongarch64
```

行为与并发回归至少覆盖：同/异 LBA、I/O error、64+ gate waiter 和 owner 退出；read/write/stat/rename/truncate/
unlink-open-close/fsync；mmap 尾页、越界页、并发 truncate；容量 feature；RISC-V 8 HART；涉及共享 C 代码时补
LoongArch64 冒烟和 `e2fsck -fn`。

性能结论必须使用同一环境至少两次完整运行，并同时出现：

```text
BUILDSTORM_COMPILE mode=multi ok=true elapsed_s=<...>
#### OS COMP TEST GROUP END buildstorm ####
shutdown!
```

常用日志提取：

```bash
rg -a -n "BUILDSTORM|shutdown!|panic|TFAIL|TBROK|ERROR|SIGSEGV|QEMU: Terminated" log.ans
rg -a -n "^\[perf\] (t=|interval_ext4|ext4_gate|ext4_bcache|ext4_block|file_cache|scheduler_duration)" log.ans
strings log.ans | tail -240
```
