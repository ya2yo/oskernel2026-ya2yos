# BuildStorm 优化方案

> 本文件只保留当前可执行计划、约束和验收边界。历史取证细节见
> [BuildStorm EXT4 稀疏写缓冲、顺序预读与锁统计收敛](./problem/buildstorm-ext4-sparse-write-readahead.md)、
> [BuildStorm 读路径、FsIndex 与 fstat 锁争用](./problem/buildstorm-read-path-lock-contention.md)
> 和 [开发日志](./开发日志.md)。

## 1. 当前结论

- 最新约 30 分钟样本 `tmp_06.ans` 已装载 P17 rename 写回子阶段与 interval delta。日志无
  panic/TFAIL/TBROK/ERROR/SIGSEGV/rustc error，但最后为 `t=1750.035s`、Cargo `Building 54/446`，
  没有 BUILDSTORM_COMPILE、测试组 END 或 shutdown!，因此仍不是完整 BuildStorm 验收样本。
- 吞吐确实随运行时间下降：`596.509s` 为 33/446，`872.646s` 为 38/446，`1173.788s` 为 44/446，
  `1579.319s` 为 54/446；此后至少 `170.716s` 没有 crate 进度。36 -> 37、44 -> 45 分别约耗时
  `201s`、`149s`，不能用五分钟样本的 4--5 crates/min 外推后半程。
- 最后 `170.716s` interval 不是空闲或纯用户态计算：`ext4_write_open_lock` 的 136 次获取累计等待
  `399.685s`、持锁 `12.727s`，且全局最大等待从此前 `28.964s` 跃升到 `175.954s`；同时 find、fstat、
  namespace 仍分别完成 39、27、17 次操作。并发等待时间不能与 wall-clock 相加，但一个 write-open
  几乎跨越整个静默窗口，结合当前“先解锁、再 wake_one”实现，说明 mount-wide gate 存在插队/饥饿放大的高风险。
- 后段还有第二层退化：最后 interval 的 create 8 次耗时 `10.667s`、metadata_apply 7 次耗时
  `17.993s`、unlink 9 次耗时 `19.665s`、mode 9 次耗时 `18.528s`、ext4_stat_get 27 次耗时
  `27.617s`。因此公平交接可以降低长尾，但不能替代对 lwext4 路径查询、目录操作、块分配和 journal
  事务本体的继续拆分。
- P17 仍是重要但非唯一候选：截至 `t=1579.319s`，93 次 rename dense write-back 已提交
  `79,225,183 B`、累计 `119.466s`、最大 `25.577s`；最后 171 秒只新增一次 `13,148 B / 3.074s`
  dense write-back，不能解释整个静默窗口。
- 页缓存不是下一轮优先项：末尾 resident_pages=79776/98304、capacity_bypass_pages=0，仍未触顶；
  不应继续扩大 32 MiB 文件准入或 96K 页容量。

## 2. 已固定优化

| 阶段 | 状态 | 保留结论 |
| --- | --- | --- |
| P1 写路径 | 已实施 | write quota 移出 EXT4_OP_LOCK；write open/data 锁拆分；unlink/drop 中 MNT_TABLE 与 EXT4_OP_LOCK 不再反向嵌套。 |
| P4/P5 dentry/stat | 已实施 | 正 dentry 被 FsIndex path 命中绕过，不恢复正向 dentry fast path；负 dentry 保留；目录 stat cache 受 epoch 保护。 |
| P9 文件页缓存 | 已实施 | regular-file read 准入固定为 32 MiB，全局页缓存固定为 96K 页；容量满时直读但不发布，不能返回 ENOMEM 或旧数据。 |
| P10/P11 读来源 | 已实施 | inode_read_source 覆盖 mmap fill、page-cached cold run、direct bypass、other；未对齐 ELF 段改为最大 64 KiB 分块读。 |
| P12/P13 mmap | 已实施 | mmap 来源拆分 demand/prefetch；EOF 检查改为页偏移与 inode.size() 判断，避免普通 fault 的重复页缓存查询。 |
| P15 目录 epoch | 已实施 | 目录自身 metadata 只推进本 inode directory_stat_epoch；rename/link/unlink/delayed remove 等保守边界继续推进全局 epoch。 |
| P16 create 路径 | 已实施 | perf 报告增加 interval delta/create 子阶段；新 inode 的 mode/owner 合并为一次路径事务，root 0/0 owner 省略；普通文件和目录以底层原子 `O_EXCL` 创建，删除重复 exist check。 |
| P17 rename 写回归因 | 已实施 | 写回拆为 sparse flush、dense byte-cache 与 path-cache discard；记录子阶段 total/max、实际提交字节及零字节快路径，不改 rename 顺序或锁边界。 |
| BuildStorm 入口 | 已调整 | RUST_MIN_STACK=33554432 避免 tmp_07 的 rustc 栈不足崩溃；initproc 当前为直接运行 buildstorm::compile::run() 的定向入口。 |

## 3. 不变约束

- EXT4_OP_LOCK 继续串行化所有 lwext4 block cache 与 path/file C API；不改 rwlock，不允许多 hart 并发进入 lwext4。
- 保持锁序简单：write_state -> io_state -> EXT4_OP_LOCK；不得在持有 MNT_TABLE 时获取 EXT4_OP_LOCK，也不得反向嵌套。
- 不扩大 P9 参数：保持 32 MiB 文件准入、96K 页全局容量、四页预读上限，除非新样本证明容量触顶或预读 miss 明确主导。
- 不牺牲文件系统语义：quota reserve/rollback、ENOSPC 小 chunk 回退、sparse overlay、st_blocks、mtime/ctime、
  rename/truncate/unlink/write 的 cache 失效必须保持。
- 未出现完整结束标记前，所有定时样本只可用于方向性取证，不能报告端到端加速。

## 4. 下一轮 P18

### P18.1：先修 EXT4 gate 公平性

1. 只为 mount-wide `EXT4_OP_LOCK` 增加低开销取证：queued acquisitions、当前/最大队深、FIFO handoff、
   fast-path barging、被取消 waiter 和排队时长分桶。现有 per-operation wait/hold 继续保留，用于区分
   “排队没拿到锁”和“拿锁后遇到长事务”。
2. 将 `EXT4_OP_LOCK` 从“释放 primitive lock 后再唤醒 waiter”改为显式 FIFO/ticket handoff：存在已登记
   waiter 时，新调用者不得走 try_lock 插队；锁所有权只转交队首。实现必须处理 waiter 取消、任务退出、容量上限
   和 unlock/register 竞态，不得因 stale waker 丢失锁或永久阻塞。
3. 公平模式先仅作用于 `EXT4_OP_LOCK`，不改变每 inode `TaskMutex`，更不能把 lwext4 改成 rwlock；
   `write_state -> io_state -> EXT4_OP_LOCK` 及 mount-wide 单线程串行约束保持不变。
4. 先做锁级压力测试，再跑同配置 BuildStorm。第一验收指标是消除 `>=100s` 的 gate 饥饿，且不再有 waiter
   连续跨多个报告周期；同时比较队深、barging=0、总 wait/hold、Cargo 固定检查点和完整编译耗时。

### P18.2：把新 inode 元数据并入创建事务

1. 当前 P16 只把 mode+owner 合为一次创建后的 pathname transaction；`tmp_06` 累计 create 为
   `110.912s`，metadata_apply 为 `178.286s`。下一候选是在 `ext4_generic_open2()`/目录创建的同一
   transaction 中直接写入最终 mode、uid、gid，避免创建后第二次路径查询和 journal 更新。
2. 普通文件与目录分别实现，保留原子 `O_EXCL`、umask、非 root owner、父目录 S_ISGID 继承和失败回滚；
   不能把后续 chmod/chown 的通用路径错误地并入 create fast path。
3. 验收比较 create 的 `dir_mk_or_file_open`、`metadata_apply`、mode、namespace gate hold 与磁盘元数据；
   新建文件/目录、既有目标 EEXIST、非 root、S_ISGID 和 ENOSPC 回滚必须定向覆盖。

### P18.3：受限 rename dense-cache re-key

1. 先增加 rename 覆盖、rename 后立即 read/exec、旧 fd 继写、失败 rename、fsync/sync、hardlink 和
   unlink-open-close 回归；P17 的本 workload sparse_flush=0 不能外推到其他负载。
2. 只对可证明单链接的 regular file 启用：rename 成功前保留旧路径 cache，成功后在
   CACHE_TABLE/FIFO_TABLE 的既有锁序下将 source cache 原子 re-key 到 target，并丢弃被覆盖 target cache；
   失败路径保留 source/target，硬链接或所有权不明确时回退当前“先写回再 rename”。
3. 验收看 dense_write_back bytes/total/max、rename gate hold 和上述语义回归。该项可消除 P17 已定位的
   `122.540s` 累计成本，但不得宣称它能单独解决最后 171 秒停滞。

### P19：继续拆分 lwext4 后段长事务

1. 若公平交接后 create/unlink/mode/stat 的单次耗时仍随进度上升，在 C 层增加 transaction、path lookup、
   directory scan、block allocation、journal commit 和 block-cache flush 的聚合计时，不逐操作打印。
2. 用早期/后期相同操作的 interval 平均与 max 判断退化来自目录规模、分配器/journal、缓存写回，还是宿主
   overlay I/O；结论明确前不扩大页缓存、不提升 BuildStorm 并发度，也不拆开 lwext4 全局串行边界。

## 5. 验收边界

构建与静态检查：

    cargo fmt --manifest-path os/Cargo.toml --all -- --check
    git diff --check
    make perf TARGET_ARCH=riscv64
    make perf TARGET_ARCH=loongarch64
    make TARGET_ARCH=riscv64
    make TARGET_ARCH=loongarch64

运行期验收必须看测试自身结束，而不是外层 timeout：

    BUILDSTORM_COMPILE mode=multi ok=true elapsed_s=<...>
    #### OS COMP TEST GROUP END buildstorm ####
    shutdown!

如果下一轮改动触及写入、rename、truncate、unlink、mmap 或 stat 语义，还需补定向回归：

- mmap16、lseek11 的 SEEK_DATA/SEEK_HOLE；
- fstat/statx 的 st_blocks、mtime/ctime；
- write-read、rename、truncate、unlink-open-write-close、fsync/sync；
- 文件映射部分尾页、完整越界页和并发 truncate 的 SIGBUS。

公平锁改动还必须验证：无竞争 fast path、64 个以上 waiter、队首任务取消/退出、跨 hart 连续交接，以及
持锁任务被抢占时没有 lost wakeup 或永久 reservation。
